# B마트 프로젝트 — 3단계. 전체 도메인 × PART 1\~12 통합 설계

5개 업무 영역 · 담당 PART 12개 · 구현 기능 / 데이터 / 권한 / 연동 / 예외 / 복구 통합

## 1. 통합 설계의 목적

이번 단계의 목적은 1단계에서 분석한 B마트 전체 업무 흐름과 2단계에서 구분한 PART 1\~12의 세부 설계 규칙을 연결하여 실제 팀 프로젝트의 구현 책임과 검증 기준을 명확하게 하는 데 있다.

분석 기준은 다음과 같다.

| 자료     | 구성                | 사용 목적                            |
| ------ | ----------------- | -------------------------------- |
| 전체 도메인 | ZIP 5개, 193장      | 서비스 기능과 업무 흐름 파악                 |
| 담당 범위  | PART 1\~12, 58장   | 공통 규칙·데이터 정합성·운영 기준 파악           |
| 통합 결과  | 5개 도메인 × 12개 PART | 구현 기능, 담당 주체, 연동 계약, 예외·복구 기준 도출 |

기존 자료는 기획 제안 및 설명용 예시이므로 실제 B마트의 **확정 정책과 구분한다** 미확정된 승인 기준·시간 제한·선택 기능·성능 목표는 팀 결정 사항으로 남긴다.&#x20;



### 1-1. 이번 통합에서 가장 중요한 구분

A. 도메인별 직접 구현 기능

고객 앱, 상품, 재고, 주문·결제, 배송·CS 담당 개발자가 자신의 도메인에서 실제로 구현하는 기능.

B. 도메인 간 공통 적용 규칙

데이터 정합성, API·이벤트 계약, 권한, 상태 변경, 멱등성, 장애 복구 등 여러 도메인이 함께 준수하는 규칙.

C. 팀의 정책 결정·검증 업무

MVP 범위, 취소 가능 시점, 승인 기준, 배포 방식, 테스트 합격 조건 등 구현 전에 확정해야 하는 사항.

**중요** : B 영역의 규칙을 한 사람이 모두 코딩한다는 의미는 아니다. 예를 들어 재고의 동시성 제어는 재고 담당 개발자가 구현하고, 주문 담당 개발자는 재고 예약 API의 결과에 따라 주문 상태를 올바르게 처리해야 한다.

따라서 PART 1\~12는 독립적인 하나의 서비스라기보다 여러 개발자가 공통으로 준수해야 하는 설계 기준을 제공한다. 단, 권한 관리나 운영·감사 기능처럼 실제 구현 대상이 되는 공통 기능도 포함한다.

## 3. 세부 주제별 통합 및 5개 도메인 교차 분석

### 3-1. PART 1\~12가 전체 시스템에 적용되는 위치

표의 각 셀은 해당 PART가 해당 도메인에 제공하는 주요 구현·검증 기준을 의미한다. 빈 영역 없이 모두 동일한 기능을 구현한다는 뜻은 아니다.

| PART        | 고객 앱         | 상품·가격·혜택   | 공급·재고·물류    | 주문·결제·환불     | 배송·CS       |
| ----------- | ------------ | ---------- | ----------- | ------------ | ----------- |
| 1. 권한·승인·감사 | 계정·접근        | 변경 승인      | 센터·작업 권한    | 환불·정정 승인     | CS·배송 권한    |
| 2. 데이터·이력   | 주문 조회·주소     | 주문 가격 원본   | 피킹·포장·출고 연결 | 주문·거래 원본     | 배송·클레임 연결   |

예를 들어 PART 5는 마지막 재고 동시 주문, 결제 후 주문 실패, 취소와 기사 인계 충돌을 다루지만 다음과 같이 실제 구현 책임이 나뉜다.

- 마지막 재고 예약: 재고 도메인
- 주문 확정 실패 판단: 주문 도메인
- PG 거래 확인·환불: 결제 도메인
- 인계 가능 상태 확인: 물류·배송 도메인
- 각 단계의 연결·보상 순서: 팀 공통 업무 계약

가령 멱등성 자체는 공통 원칙으로 정리하되, 주문 중복 생성 차단과 PG 중복 환불 차단은 각각 독립적인 구현 검증 항목으로 유지한다.

## 4. 업무 주체와 권한

### 4-1. 업무 권한의 7가지 유형

| 권한    | 의미                         | 적용 예시             |
| ----- | -------------------------- | ----------------- |
| 조회    | 허용된 업무 데이터 확인              | 담당 주문·재고·배송 조회    |
| 작업    | 정해진 정상 업무 수행               | 피킹, 포장, 기사 인수 등록  |
| 변경    | 상품·가격·업무 데이터 수정            | 가격 변경 요청, 재고 조정   |
| 승인    | 다른 주체가 요청한 변경을 검토·허가       | 가격 변경, 예외 환불 승인   |
| 강제 처리 | 예외 상황에서 통상 절차 밖의 제한된 조치 수행 | 검증된 상태 정정·복구 실행   |
| 감사 조회 | 업무 변경 및 접근 이력 열람           | 승인·실행·거절·복구 기록 확인 |
| 긴급 접근 | 장애 등으로 제한적인 임시 접근 부여       | 특정 센터의 장애 대응 권한   |

각 권한은 상하 관계가 아니다. 조회 권한을 보유했다고 변경 권한을 보유하는 것은 아니며, 승인 관리자라는 이유로 모든 작업을 직접 수행할 수 있는 것도 아니다.

### 4-2. 업무 주체별 권한·데이터·범위

다음은 PART 1\~12의 요구사항을 반영한 통합 권한 설계안이다. 세부 승인 한도 및 조직별 역할 배분은 팀 확정이 필요하다.

| 피커        | 배정 작업 조회, 피킹·결품·스캔 기록             | 소속 센터의 배정 작업                      |

| 출고·인계 담당자 | 출고·포장 확인, 출고 확정, 기사 인계            | 담당 센터·대상 포장, 배송 완료 임의 확정 불가       |
| 배송기사      | 배정 배송 조회, 인수·시도·전달 결과 등록          | 본인 배정 배송, 업무 종료 후 개인정보 접근 제한      |
| CS 담당자    | 담당 문의·주문·배송 조회, 취소·환불·보상 요청       | 담당 문의의 필요 범위, 임의 PG 거래 수정 불가      |

### 4-3. 공통 권한 검증 순서

사용자 또는 서비스 요청 → 인증·계정 상태 확인 → 역할 확인 → 업무별 권한 확인 → 센터·조직·대상 소유권 확인 → 임시 권한 만료 여부 확인 → 대상 업무의 현재 상태·버전 확인 → 승인 필요 여부 판단 → 자기승인·승인 내용 변경 여부 확인 → 업무 실행 → 처리 결과 및 감사 이력 기록

단순 조회·정상 피킹·정상 결제마다 별도 관리자 승인을 요구하는 구조는 기본안으로 삼지 않는다.

일반 업무는 사전에 부여된 작업 권한과 시스템 검증으로 처리하고, 가격 변경이나 재고 강제 조정, 예외 환불, 장애 복구 등 고위험 조치에 대해서만 별도 승인 규칙을 정의하는 방향이다.

### 4-4. 승인·긴급 접근 추가 조건

| 상황                  | 적용할 규칙                          |
| ------------------- | ------------------------------- |

| 승인 대기 중 요청 내용 수정    | 기존 승인 대상과 불일치하므로 재승인            |

| 요청자 또는 승인자 권한 회수    | 실행 시점의 현재 권한 재검증                |
| 임시 권한 만료            | 기존 세션 유무와 관계없이 후속 요청 차단         |

## 6. 정상 업무 흐름 및 시스템 간 연동

### 6-1. 판매 준비

상품 담당자 — 상품·SKU 등록

승인 관리자 — 필요한 상품·가격 정책 검토

발주 담당자 — 공급사 발주

입고·검수 담당자 — 실물 수량·품질 검증

재고 시스템 — 합격 수량·로트·센터·위치 반영

상품·재고 시스템 — 판매 가능 여부 제공

판매 가능 여부를 결정할 때에는 상품 판매 상태와 재고 상태를 함께 확인해야 한다.

상품 등록이 완료된 경우에도 검수 미완료 상품이나 품질 격리 재고를 판매 가능으로 전환해서는 안 된다.

### 6-2. 고객 주문·결제

고객 주문 요청 → 인증·배송 가능 지역 확인 → 상품·SKU·수량 확인 → 유효 가격·혜택·쿠폰 확인 → 요청키 확인 → 판매 가능 재고 예약 → 결제 요청 → PG 결과 확인 → 주문 확정 → 주문 이벤트 발행 → 물류 작업 생성

설계 결정 필요: 결제 승인과 재고 예약의 세부 실행 순서, 임시 예약의 만료 시간, 주문 확정 조건.

어느 순서를 채택하든 결제만 성공하거나 예약만 성공한 상태를 식별하고 복구할 수 있어야 한다.

### 6-3. 물류·배송

주문 확정 이벤트 수신 → 동일 이벤트 처리 여부 확인 → 센터별 작업 생성 → 피커 배정 → 상품 위치·수량 확인 → 피킹 완료 → 포장 담당자 검수 → 포장 구성 및 라벨 등록 → 출고 확정 → 배송 대상 생성 → 기사 배차 → 포장·수량 인계 → 배송 시도 → 고객 전달 완료 → 주문 및 고객 앱에 결과 반영

피커, 포장 담당자, 출고 담당자, 인계 담당자, 배송기사의 완료 권한은 서로 다르다.

### 6-4. 취소·환불·클레임

고객 또는 CS 담당자 요청 → 본인·담당 업무 권한 검증 → 주문·피킹·출고·인계·배송 상태 확인 → 요청 유형 및 가능 범위 판단 → 취소·반품·재배송·보상 경로 결정 → 필요한 승인 → 각 소유 도메인에 후속 처리 요청 → PG·재고·물류 결과 확인 → 고객·CS 화면에 확정 결과 반영 → 이력·감사 저장

부분 취소와 반품은 동일한 흐름으로 강제 통합하지 않는다. 출고 전의 수량 취소와 이미 배송된 실물의 회수는 다른 업무이다.

### 6-5. 도메인 간 연동 계약

| 연동         | 요청·이벤트              | 처리 책임과 검증               |
| ---------- | ------------------- | ----------------------- |
| 고객 앱 → 주문  | 주문 요청, 요청키          | 인증 사용자·금액·주소·중복 검증      |
| 주문 → 상품·혜택 | 유효 가격·할인 조회 및 쿠폰 처리 | 적용 정책 버전 및 할인 조건 확인     |
| 주문 → 재고    | 예약·해제 명령            | 센터·SKU·수량, 원자성·멱등성      |
| 주문 → 결제    | 결제 승인 요청            | 원거래 연결, 재전송 방지          |
| 결제 → 주문    | 거래 결과               | PG 확정 여부, 결과 불명과 실패 구분  |
| 주문 → 물류    | 주문 확정·취소 이벤트        | 주문 버전·이벤트 중복·취소 상태 확인   |
| 물류 → 주문    | 피킹·결품·출고 결과         | 주문상품별 처리 수량·상태 검증       |
| 물류 → 배송    | 출고·포장·인계 요청         | 출고 상태, 포장 수량, 기사 인수     |
| 배송 → 주문    | 배송 시도·전달 결과         | 배송 ID, 상태 버전, 중복 이벤트 검증 |
| CS → 주문·결제 | 클레임·취소·환불 요청        | 원주문·거래·승인·금액 검증         |
| 반품 → 재고    | 회수·검수 결과            | 품질 판정·재판매 가능 여부         |

**공통 계약 필드 제안: 요청 ID, 업무 ID, 처리 주체, 센터 ID, 대상 버전, 이벤트 ID, 이벤트 발생·처리 시각, 추적 ID, 처리 상태, 실패 사유.**

### 7-2. 핵심 업무 불변 조건

재고

- 보유 재고의 음수 방지
- 예약 수량이 예약 가능 재고를 초과하지 않도록 제어
- 검수·격리·폐기 대상 재고의 판매 제한
- 동일 예약 해제의 중복 수량 반영 금지
- 로트·센터별 수량 혼합 방지

주문·물류

- 출고 전 취소 수량과 정상 출고 수량이 최초 주문 수량을 초과하지 않도록 검증
- 피킹한 수량이 포장·출고 대상과 일치하는지 확인
- 포장 미완료·출고 불가 상태의 기사 인계 제한
- 취소 확정 후 과거 이벤트에 의한 피킹 재개 차단
- 배송 완료를 근거로 이전 작업 단계를 임의 재실행하지 않도록 제어

결제·환불

- 동일 결제 업무에 대한 추가 승인 중복 방지
- 동일 원거래의 환불 가능 금액 초과 방지
- 이미 완료된 환불과 진행 중인 환불을 함께 고려
- 결과 불명인 PG 거래를 임의 실패 또는 성공으로 확정하지 않음
- 결제·환불 실행 결과를 원주문과 연결

권한·승인

- 자기승인 금지 대상에 대한 요청자·승인자 동일성 검증
- 요청 내용 또는 버전 변경 시 승인 유효성 재확인
- 임시·긴급 권한의 실행 시점 만료 확인
- 다른 센터·다른 기사·다른 고객의 데이터 접근 차단

### 7-3. 시스템이 원자적으로 처리해야 하는 구간

| 상황               | 필요한 처리 방식                    |
| ---------------- | ---------------------------- |
| 마지막 재고 동시 예약     | 수량 확인과 예약 반영을 하나의 원자적 처리로 구현 |
| 동일 요청 중복 주문      | 요청키와 기존 결과를 함께 저장·확인         |
| 주문 상태 변경 경쟁      | 상태·버전을 조건으로 한 변경 처리          |
| 동일 PG 환불 중복 요청   | 원거래 및 환불 요청 식별자로 중복 처리 차단    |
| 동일 이벤트의 작업 중복 생성 | 이벤트 또는 업무 기준 고유 제약·처리 이력 활용  |
| 승인 후 내용 변경       | 승인한 요청의 내용·버전과 실행 대상 비교      |

서로 다른 서비스의 여러 DB 변경을 단일 DB 트랜잭션처럼 가정해서는 안 된다.

서비스를 분리하는 경우에는 멱등 처리, 결과 조회, 보상 처리, 이벤트 발행 신뢰성 등을 함께 설계해야 한다. 트랜잭셔널 아웃박스와 같은 패턴은 이러한 요구를 구현하는 방법 중 하나로 검토할 수 있다.

## 9. 실패 시 처리·재처리·복구

PART 3, 5, 6, 9, 10의 복구 요구사항은 공통 원칙으로 연결하되, 실패 원인과 복구 대상이 다르므로 실행 절차는 구분한다.

### 9-1. 실패 유형별 처리

| 검증 조건 미충족    | 업무 거절      | 입력·권한·상태 조건 수정 후 새 요청  | 원데이터 불변      |

| 잘못된 정책 배포    | 배포 확대 중단   | 코드·설정·정책 복귀 및 영향 거래 처리 | 신규·기존 주문 검증  |

### 9-2. 복구 시 금지해야 할 처리

- PG 응답이 없다는 이유만으로 동일 결제를 다시 승인 요청하는 처리
- 환불 완료 확인 없이 원거래가 환불되었다고 표시하는 처리
- 주문 복구를 위해 이미 성공한 모든 단계를 처음부터 다시 실행하는 처리
- 이미 출고한 재고를 단순한 예약 해제만으로 판매 가능 수량에 복원하는 처리
- 서버 복구 완료만으로 센터·실물 작업도 복구 완료라고 판단하는 처리
- 코드 롤백만으로 기존 주문 금액과 결제 내역이 복원된다고 가정하는 처리
- 감사 기록을 삭제하거나 원본 변경 이력을 덮어쓰는 처리



### 9-3. 통합 복구 흐름

장애 발생 이후 기존 처리 결과를 확인하고, 복구 유형에 따라 필요한 단계만 실행한다.

**① 장애·실패 감지**

- 처리 주체: 운영 관리자, 모니터링 시스템
- 처리 내용: 장애 발생 여부와 영향 범위 확인
- 생성 데이터: 장애 ID, 발생 시각, 오류 유형, 영향 서비스

↓

**② 영향 대상과 처리 단계 확인**

- 처리 주체: 운영 관리자, 각 도메인 담당자
- 확인 데이터: 주문 ID, 결제 ID, 예약 ID, 이벤트 ID, 작업 ID
- 처리 내용: 정상 완료된 단계와 미완료·실패 단계를 구분

↓

**③ 외부·내부·실물 상태 대조**

- 처리 주체: 결제 담당자, 재고 담당자, 물류 담당자
- 확인 항목:
  - PG 거래 승인·취소·환불 결과
  - 주문 확정·취소 상태
  - 재고 예약·해제 상태
  - 피킹·포장·출고 상태

**핵심 원칙**

복구 작업은 기존 업무를 처음부터 다시 실행하는 방식이 아니라, 이미 성공한 단계를 확인하고 미완료된 부분만 복구하는 방식으로 처리한다.

원거래 근거가 부족하거나 실물 확인·금액 강제 변경이 필요한 경우에는 자동 처리 대신 승인·보류 절차를 적용한다.
최종 대사 · 고객 안내 · 미해결 업무 배정 · 감사

예외 복구 작업은 무조건 자동화하거나 무조건 관리자 수동 처리로 설계해서는 안 된다. 위험도가 낮고 결과가 확실한 재처리는 자동 수행할 수 있지만, 원거래 근거가 부족하거나 실물 확인·금액 강제 변경이 필요한 상황은 승인·보류 경로가 필요하다.

**④ 시스템 검증 조건**

- 조회자의 현재 계정 및 역할 확인
- 센터·조직·담당 업무 범위 검증
- 개인정보 마스킹 및 원문 조회 권한 구분
- 주문·결제·재고·물류·배송 상태의 독립 조회
- 원천 데이터와 화면 표시 데이터의 일치 여부 확인
- 각 데이터의 마지막 갱신 시각 확인
- 재처리 실행 시 현재 상태·버전·승인 여부 재검증

**⑤ 예외상황 및 처리**

| 예외상황 | 처리 방법 |
|---|---|
| 주문은 확정됐지만 결제 결과가 불명확함 | PG 원거래 조회 후 결과 확정 |
| 결제는 승인됐지만 재고 예약이 없음 | 주문 확정 조건 확인 및 복구·보상 절차 |
| 물류 작업이 생성되지 않음 | 주문 이벤트·작업 생성 이력 확인 후 재처리 |
| 관리자 화면과 원천 데이터의 상태가 다름 | 갱신 지연·이벤트 누락·버전 충돌 확인 |
| 동일 작업의 재처리 요청이 반복됨 | 기존 처리 결과 확인 및 중복 실행 방지 |
| 권한 없는 관리자가 다른 센터 주문 조회 | 접근 거절 및 감사 이력 기록 |

**⑥ 관리자 화면 설계 원칙**

하나의 주문번호로 여러 도메인의 처리 상태를 연결 조회할 수 있도록 구성한다.

다만 각 업무 상태는 해당 도메인의 원천 데이터를 기준으로 판단하며, 관리자 화면에서 임의로 상태를 변경하지 않도록 통제한다.

재처리가 필요한 경우에도 원거래 상태 확인, 권한 검증, 필요한 승인, 실행 결과 기록 절차를 준수한다.

운영자별 권한에 따라 조회 항목과 재처리 명령 노출 범위를 달리 적용. 실제 원거래 상태 확인 없는 임의 강제 변경 불가.

실제 관리자 화면에서는 하나의 주문번호로 전체 상태를 연결 조회하더라도, 각 상태를 관리하는 원천 시스템과 마지막 갱신 시각을 표시해야 한다.

조회 화면에 나타나는 값이 서로 다르다면 임의로 하나를 선택하지 않고, 원천 데이터·동기화 지연·이벤트 누락 여부를 확인해야 한다.

### 11-2. 이력 유형은 분리

업무 이력: 주문·결제·피킹·배송·환불 등이 실제로 발생한 기록.

감사 이력: 누가 어떤 권한과 근거로 업무를 조회·변경·승인했는지 확인하는 기록.

운영 로그: 장애 원인, 처리 지연, API·이벤트 실패 등을 진단하는 기록.

검증 이력: 어떤 환경·버전에서 어떤 테스트를 실행했고 결과와 증거가 무엇인지 확인하는 기록.

서로 다른 목적의 이력을 단일 로그 테이블 하나로 모두 대체하는 방식은 적절하지 않다. 공통 추적 ID 등으로 연결하되, 각 기록의 접근 권한과 개인정보 보존 정책을 구분해야 한다.

배송 주소나 고객 전화번호를 운영 로그에 불필요하게 반복 저장하지 않도록 설계해야 한다.

### 12-3. 구현 우선순위 제안

모든 기능을 같은 시점에 구현하면 도메인 간 의존성과 변경 충돌이 증가할 수 있다. 따라서 공통 기준과 핵심 흐름부터 확정하는 방식이 적절하다.

1순위 — 공통 계약·핵심 모델 확정

도메인 소유권, 주문·재고·결제 상태, 식별자, 공통 오류 형식, 요청 멱등키, 주요 권한 범위.

2순위 — 정상 주문 흐름 구현

상품 등록·입고·재고 확보 → 고객 주문 → 결제 → 피킹 → 포장 → 출고 → 배송 완료.

3순위 — 필수 예외·정합성 구현

마지막 재고 경합, 중복 주문, 결제 응답 유실, 취소·인계 경합, 피킹 결품, 중복 환불.

4순위 — 운영·복구·관리자 기능

조회·승인·감사, 실패 작업 확인, PG 대사, 재처리, 접근 제한, 기본 장애 대응.

5순위 — 통합·부하·복구 검증

정상·실패·중복·역순·권한·장애 시나리오의 실제 실행 및 결과 확인.

보안과 데이터 정합성의 기본 검증은 후순위까지 미루지 않는다. 4순위는 이를 운영자가 관리하기 위한 고도화 화면·절차를 의미한다.
