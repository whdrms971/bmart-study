### PART 1의 업무 순서

업무 요청 → 역할 검증 → 센터·조직 범위 확인 → 계정·권한 만료 검증 → 요청 내용 및 현재 데이터 버전 검증 → 별도 승인자의 검토 → 업무 적용 → 감사 이력 저장 → 반영 결과 확인

### 권한 및 운영 조건

조회·변경 요청·승인·강제 처리·감사 조회·긴급 접근 권한의 별도 관리 필요.

### PART 3의 정상 흐름

고객 주문 요청 → 인증 사용자 확인 → 요청키 중복 여부 확인 → 상품·가격·재고 검증 → 기존 결제 거래 조회 → 필요한 경우 PG 승인 → 주문 확정 → 이벤트 발행 → 물류 작업 생성 → 피커 작업 → 처리 결과 반영

### 반드시 구별할 식별자

- `requestId` 또는 멱등키: 동일 업무 요청의 재전송 판별
- `eventId`: 이벤트 중복 수신 판별
- `traceId`: 여러 서비스의 로그 연결
- `version`: 오래된 변경 요청과 현재 데이터를 비교
- `pgTransactionId`: 외부 PG에서 처리된 원거래 식별

추적 ID만으로 멱등 처리 자동 보장 불가.

1단계 도메인 연결: 고객 앱의 결제 중복 요청 시 주문·결제 중복 효과 차단 필요. 물류 시스템에서 동일 주문 확정 이벤트 반복 수신 시 작업 1건만 생성.&#x20;

- PART 6의 복구: 장애 이후 데이터·거래·실물의 불일치를 복원하는 기술·업무 절차

- PART 11의 검증: 구현 결과가 요구사항에 맞게 동작하는지 실제 시험하고 증거를 확보하는 과정

이미지별 기대 결과와 실제 검증 완료 여부의 엄격한 구분 필요.
