**나눈 PART 5개 업무 영역에 걸쳐 적용되는 설계·검증 기준**으로 연결

예를 들어 **‘상품 가격 변경’은 ② 상품·가격·혜택의 기능**이지만, 그 기능을 만들 때 **PART 1의 변경·승인 권한, PART 2의 과거 가격 보존, PART 10의 정책 변경 기준**을 함께 적용하는 구조

**1. PART 1~12와 5개 영역의 연결**

- **◎:** 해당 PART에서 직접적으로 다루거나 우선 확인해야 할 영역
- **○:** 기능과 데이터가 연결되어 함께 확인할 영역
- **공통:** 5개 영역 모두에 적용되는 기준

| PART | 주제 요약 | ① 고객 앱 | ② 상품·가격·혜택 | ③ 공급·재고·물류 | ④ 주문·결제·환불 | ⑤ 배송·고객지원 |
|---|---|:---:|:---:|:---:|:---:|:---:|

| **4** | 주문·결제·재고·배송 상태 분리 | ◎ | ○ | ◎ | ◎ | ◎ |

| **6** | 장애 복구·백업·서비스 재개 | ○ | ○ | ◎ | ◎ | ◎ |

**표에서 ○라고 해서 중요하지 않다는 뜻은 아님** 

해당 PART의 중심 사례가 다른 영역에 있다는 의미

 예를 들어 상품·가격·혜택도 장애 복구와 개인정보 검토가 필요하지만, 정리본의 직접적인 사례는 주문·결제·배송 쪽에 더 많이 분포

**2. 각 PART가 실제로 어디에 쓰이는지**

| PART | 각 영역에 연결되는 구체적인 내용 |
|---|---|
| **1. 권한·승인·감사** | **②** 상품 가격을 누가 변경하고 승인하는지 / **③** 어느 센터의 재고를 수정할 수 있는지 / **④** 누가 환불·강제 처리를 할 수 있는지 / **⑤** CS가 어디까지 조회·처리할 수 있는지 |
| **2. 데이터 구조·이력** | **②↔④** 현재 상품 가격과 주문 당시 가격 구분 / **③↔④↔⑤** 주문상품·피킹·포장·출하·배송·반품·환불 연결 / **①** 연결된 결과를 주문 상세에 표시 |
| **3. API·이벤트 계약** | **①↔④** 결제 버튼 중복 클릭과 요청 재전송 / **④↔③** 주문 확정 후 물류 작업 생성 / **③↔⑤** 작업·배송 결과 전달 / 공통 오류 형식과 중복 처리 방지 |
| **4. 상태 분리** | **④** 결제 승인과 주문 확정, 취소 확정과 환불 완료 구분 / **③** 예약·피킹·포장·출하 구분 / **⑤** 기사 인계와 고객 전달 구분 / **①** 각 상태에 맞는 안내 표시 |
| **5. 동시 요청·부분 실패** | **③↔④** 마지막 재고 동시 주문, 결제 성공 후 주문 확정 실패 / **④↔⑤** 취소와 기사 인계의 충돌 / **④** 반복 요청에 의한 중복 환불 방지 |
| **6. 장애 복구** | **④** 결제됐지만 누락된 주문 복구 / **③** 누락된 물류 작업 복구·센터 운영 불가 대응 / **⑤** 배송 가능 여부 확인과 고객 안내 / **①** 접수 제한·재개 반영 |
| **7. 개인정보** | **①** 배송지·연락처 입력 / **④** 주문에 필요한 개인정보 보관 / **⑤** 배정 기사에게 필요한 정보만 제공, CS 마스킹 조회 / 업무 종료 후 접근 회수·삭제 처리 |
| **8. 피크 수요·수용량** | **③** 피킹·포장 대기량 확인 / **④** 신규 주문 접수 제한 / **⑤** 기사 대기·배송 지연 확인 / **①** 예상 도착 시간과 주문 가능 여부 안내 |
| **9. 장애 대응·운영 인수** | **④** 결제 결과 불명 주문 조사·PG 대사 / **①** 재결제 전 결과 확인 / **⑤** 고객 안내와 미해결 문의 관리 / 교대 담당자에게 미처리 건 전달 |
| **10. 배포·정책 변경** | **①** 구버전 앱의 주문 기능 유지 / **②** 가격·쿠폰·배송비 정책 변경 / **④** 기존 주문에 적용된 금액·정책 보존 / 연결 시스템의 호환성 확인과 롤백 |
| **11. 통합 시험·출시 판단** | **③** 현장 결품 기록 → **④** 부분 취소·환불 → **①** 고객 표시 → **⑤** CS 확인까지 같은 결과인지 시험. 다른 영역의 기능에도 동일한 검증 방식 적용 |
| **12. 범위·정책 결정** | 5개 영역에서 이번에 구현할 기능 선정. 분할배송·부분 취소 같은 선택 기능의 범위와 비용·안내·처리 기준 결정 후 관련 요구사항 갱신 |

이렇게 보면 **한 PART가 한 영역에만 들어가는 형태가 아니라, 하나의 기능에 여러 PART가 붙는 형태**

**3. 5개 영역 담당자가 자료를 보는 방법**


| 담당 영역 | 먼저 연결해 볼 PART | 실제 확인할 질문 |
|---|---|---|
| **① 고객 앱** | 3·4·7·8·9·10 | 어떤 API를 호출하는가? 결제 결과를 모르면 무엇을 표시하는가? 고객정보를 어떻게 다루는가? 주문 제한·지연을 어떻게 안내하는가? |
| **② 상품·가격·혜택** | 1·2·10·12 | 누가 가격을 바꾸는가? 할인 정책은 언제 적용되는가? 가격이 바뀌어도 기존 주문은 유지되는가? |
| **③ 공급·재고·물류** | 1·2·3·4·5·6·8 | 재고를 언제 예약·차감하는가? 중복 작업을 어떻게 막는가? 취소와 피킹이 충돌하면 어떻게 하는가? 센터가 멈추면 어떻게 하는가? |
| **④ 주문·결제·환불** | 2·3·4·5·6·9·10 | 결제 승인과 주문 확정을 어떻게 연결하는가? 응답 유실·중복 요청·부분 환불을 어떻게 처리하는가? |
| **⑤ 배송·고객지원** | 1·2·4·5·7·8·9 | 인계 이후 취소 가능한가? 기사에게 어떤 정보를 보여주는가? 배송 실패·재배송·환불을 어떻게 연결하는가? |

**PART 11은 각 담당자가 만든 기능을 함께 시험할 때, PART 12는 구현 범위와 미정 정책을 합의할 때 공통으로 사용**

또한 ③의 **공급·발주·입고 자체에 관한 상세 규칙**은 해당 영역의 인포그래픽에서 확보해야 합니다. 종근님 PART의 중심 사례가 주문 이후 재고·물류에 많으므로, 이것만으로 공급 업무 전체가 정의되지는 않습니다.
