**1. 이번 파트의 목적과 핵심 개념**

목적: **서비스 정상화 및 장애 기간에 발생한 주문·결제 미처리 문제 추적**.

결제 서버 정상화 이후에도 다음 문제 잔존 가능.

- 결제는 승인되었지만 주문이 확정되지 않은 경우
- 결제 요청 결과를 받지 못해 성공 여부가 불명확한 경우
- 복구 작업은 끝났지만 고객 안내가 누락된 경우
- 담당자가 교대하면서 미결 주문이 빠진 경우

서비스 정상화·주문별 복구·고객 안내·운영 인수의 연결 관리 필요.

| 핵심 개념 | 의미 | 구분해야 할 사항 |
|---|---|---|
| 장애 | 여러 주문이나 서비스에 영향을 주는 공통 문제 | 개별 주문의 처리 상태와 구분 |
| 영향 주문 | 장애와 관련하여 조사·복구가 필요한 주문 | 장애 시간 안에 생성된 주문만으로 한정하지 않음 |
| 결제 결과 불명 | 성공·실패를 확정할 근거가 부족한 상태 | 결제 실패와 구분 |
| 결제 대사 | 내부 결제 기록과 PG 기록을 비교하는 작업 | 단순히 서버가 정상인지 확인하는 작업과 구분 |
| 주문 재확정 | 이미 승인된 결제 등을 근거로 누락된 주문 확정을 복구 | 신규 결제와 구분 |
| 재조회 | 기존 거래의 결과를 다시 확인 | 결제 요청을 다시 보내는 것과 구분 |
| 멱등 처리 | 같은 작업을 반복 요청해도 업무 결과가 중복되지 않게 처리 | 버튼 비활성화만으로 보장하지 않음 |
| 운영 인수 | 처리 결과와 남은 업무의 책임을 다음 담당자에게 전달 | 문서 작성만으로 인수 완료로 보지 않음 |

**2. 이미지 42 — 장애 발견부터 운영 인수까지**

**[이미지 내용] 전체 흐름**

장애 발견 → 온콜 담당 확인 → 신규 결제 보호 조치 → PG 조회·원거래 대조 → 기존 주문 처리 → 기존 거래 재조회 → 운영 인수

온콜 담당자: 장애 발생 시 연락을 받고 대응하는 담당자.

| 단계 | 원본 예시 | 업무 내용 | 주체·권한 |
|---|---|---|---|
| ① 장애 발견 | 14:00, INC01 | 결제 결과 불명 증가 감지. 주문 결제 처리 지연 가능성 확인 | 모니터링 시스템이 감지하고 운영 담당자가 확인 |
| ② 온콜 확인 | 14:05 | 상황과 영향 범위 파악, 관련 팀 소집 | 온콜 담당, 운영, 결제팀 |
| ③ 신규 결제 보호 | 14:12 | 추가 피해 방지를 위해 신규 결제 일시 제한 정책의 승인 요청 | 온콜 담당이 요청하고 관련 승인자가 검토 |
| ④ PG 조회·대조 | 14:20 | PG 상태와 내부 원거래를 비교하여 결제 결과 확인 | 결제 조회·대사 담당 |
| ⑤ 기존 주문 처리 | 14:35 | 결제 확인이 끝난 안전한 기존 주문을 정상 처리 | 센터 작업자·피킹 담당 |
| ⑥ 기존 거래 재조회 | 15:10 | 동일 거래를 다시 확인하며 추가 결제 없이 결과 안내 | 결제 시스템, 고객 화면, CS |
| ⑦ 운영 인수 | 이후 | 조사 내용, 미확정 주문, 적용 조치, 후속 모니터링 전달 | 기존 대응 담당자 → 운영 인수 담당자 |

**① 장애 알림과 담당자 확인**

원본 온콜 채널 예시 순서:

- 14:05 운영: 결제 결과 불명 증가 확인 요청
- 14:06 온콜 담당: PG 상태 및 영향 범위 확인
- 14:08 결제팀: 로그 확인

단순히 오류 알림을 확인하는 데서 끝나지 않고, **누가 PG 상태를 확인하고 누가 내부 로그를 조사하는지 역할을 나눕**

**② 신규 결제 보호 조치와 승인**

원본 요청 화면 내용:

| 항목 | 원본 내용 |
|---|---|
| 조치 구분 | 신규 결제 일시 제한 |
| 적용 범위 | B마트 전체 |
| 사유 | 결제 결과 불명 증가(INC01), 추가 손실 방지 |
| 요청자 | 온콜 담당 |
| 승인 진행 | 정책 승인 요청 → 리스크팀 검토 → 최종 승인 대기 |
| 최종 승인 담당 표기 | 서비스운영 |

**[결정 필요] 원본 내부의 시각·상태 불일치**

승인 이력에는 14:16 검토 중, 14:18 최종 승인 대기로 표시되지만 인수인계 예시에는 보호 조치 승인 시각이 14:12로 기재되어 있음

**14:12를 실제 승인 완료·조치 적용 시각으로 확정 불가.** 요청 시각·승인 시각·실제 적용 시각의 개별 저장 필요

**③ PG 조회와 원거래 대조**

원본 PG 조회 예시:

| 항목 | 값 |
|---|---|
| 거래일시 | 2024-05-20 14:03 |
| 주문번호 | BMT12345678 |
| 금액 | 4,000원 |
| 거래상태 | 승인 확인 |

원거래 대조 화면: 내부 주문 시스템과 PG의 주문·거래 상태 표시. 내부 거래번호 `ORD1234`, PG 거래번호 미확인

**[구현 보완]**

양측 상태가 ‘승인 확인’이어도 동일 거래로 단정 금지. 주문번호·금액·가맹점 거래 식별자·PG 거래 식별자 등 근거 대조 및 미확인 항목 유지 필요

**④ 기존 주문 처리와 추가 결제 없는 재조회**

기존 주문 처리 예시:

- 주문번호: `BMT12345678`
- 상품: 삼다수 2L × 2
- 주문 상태: 결제확인완료
- 작업 상태: 피킹 진행 중

이후 재조회 화면: 동일 주문의 4,000원 거래에 **‘추가 결제 없음’** 표시. 로그 예시: `payment query`, `NO_ADDITIONAL_PAYMENT` 결과

**[구현 보완]**

- 재조회 기능은 기존 거래를 조회하는 기능으로 구현
- 조회 실패나 시간 초과를 신규 결제 실행의 근거로 사용하지 않음
- ‘추가 결제 없음’과 ‘원결제 승인 확인’은 서로 다른 정보로 관리
- 신규 결제 제한 중에도 기존 주문을 어디까지 처리할지는 별도 정책으로 판단

**⑤ 운영 인수 항목**

원본 포함 내용:

- 장애 발생 시각과 장애 ID
- 원인 분석 진행 상황
- 적용한 보호 조치와 승인 정보
- 기존 주문 처리 결과
- 미확정 주문 목록
- 고객 CS 대응 현황
- 추가 모니터링 필요 사항

**3. 이미지 43 — 장애·영향 주문·복구 작업의 연결**

이 이미지는 **장애 한 건에서 여러 영향 주문을 추적하고, 주문별로 다른 처리를 수행하는 구조**를 설명

**[이미지 내용] 장애 정보**

| 항목 | 원본 예시 |
|---|---|
| 장애 ID | INC01 |
| 발생 시각 | 2024-05-20 09:12 |
| 영향 범위 | 온라인 주문 결제 처리 지연·누락 |
| 상태 | 조사 중 |

**① 영향 주문 확인**

| 주문번호 | 주문시각 | 금액 | 확인된 문제 |
|---|---|---|---|
| 9001 | 09:10 | 11,000원 | 주문 확정 누락 |
| 9002 | 09:11 | 23,000원 | PG 결과 조회 중 |

원본의 영향 주문 조회 조건은 다음과 같음습

- 장애 시간대에 생성된 주문
- 결제 상태가 비정상인 주문: 누락·조회 중 등
- 실제 조회 조건은 정책에 따름

**[결정 필요] 영향 시간 범위**

표의 주문들은 장애 발생 표기 시각인 09:12보다 먼저 생성되었습 따라서 발생 시각 이후 주문만 조회하면 원본 예시의 9001·9002가 빠집

**[구현 보완]** 장애 감지 이전의 처리 중 주문까지 포함할 수 있도록 조사 시간 범위를 설정하고, 주문 생성 시각뿐 아니라 결제 요청·응답 시각과 미확정 상태도 조회 조건으로 사용

**② 주문 9001 — 결제 승인 후 주문 확정 누락**

원본 PG 기록:

- 결제금액: 11,000원
- 결과: 승인
- 승인시각: 09:10:12

복구 흐름:

**PG 승인 확인 → 주문 확정 누락 확인 → REC01 재확정 처리 → 고객 정상 접수 안내**

| 항목 | 원본 내용 |
|---|---|
| 복구 작업 | REC01 |
| 대상 주문 | 9001 |
| 처리 사유 | PG 승인 확인 후 재확정 |
| 담당자 | 김OO, 운영팀 |
| 고객 안내 | 주문이 정상적으로 접수되었음을 안내 |

**[구현 보완]**

재확정 실행 전에 현재 주문 상태를 다시 확인 필요 조사하는 동안 이미 주문이 확정되었거나 취소·환불 처리가 진행되었을 수 있기 때문

또한 재고 예약이 해제되었거나 주문 이행이 불가능한 경우에는 결제 승인만을 근거로 주문을 강제 확정하지 않고 별도 후속 처리로 연결

**③ 주문 9002 — 결제 결과 조회 중**

원본 처리 흐름:

**PG 결과 조회 중 → 확인 중 상태 유지 → 주기적 재조회 → 결과에 따른 후속 처리**

| 항목 | 원본 내용 |
|---|---|
| 주문번호 | 9002 |
| 결제금액 | 23,000원 |
| PG 결과 | 조회 중 |
| 승인시각 | 미확인 |
| 다음 확인 시각 | 10:00 |
| 담당자 | 이OO, 운영팀 |
| 고객 안내 | 결제 결과를 확인 중이며 확인되는 대로 안내 |

**PG 결과를 아직 모른다는 이유로 실패 처리하거나 재결제를 실행하지 않음**

**④ 추적·승인·담당자·고객 안내 연결**

원본 식별자:

| 식별자 | 역할 |
|---|---|
| INC01 | 장애 |
| 9001 / 9002 | 영향 주문 |
| REC01 | 복구 작업 |
| TR01, `TR-20240520-001` | 추적 ID 예시 |
| AUD01 | 승인 이력 |
| MSG01 | 고객 안내 |

연결 관계:

**장애 → 영향 주문 → 복구 작업 → 승인 이력 → 처리 담당자 → 고객 안내**

**[구현 보완]**

PG 결제 승인과 운영자의 복구 작업 승인은 서로 다른 개념. `AUD01` 구현 시 승인 종류 구분 및 각 승인 근거 연결 필요

`MSG01`의 반복 등장에 따라 개별 발송 고유 ID와 안내 유형 코드 중 의미 확정 필요

**⑤ 장애 종료 기준**

원본 제시 조건:

- 영향 주문 모두에 대해 정상·복구 완료 또는 확인 불가에 따른 인수 등 처리 방향 판정
- 미결 주문을 인수 목록으로 이관

따라서 **장애 종료와 모든 주문의 최종 해결은 같은 의미가 아닙니다.** 미결 주문이 남는다면 담당자와 후속 처리 책임이 이어져야

**4. 이미지 44 — 장애 알림·복구·인수 검증**

이 이미지는 대응 과정에서 지켜야 할 원칙과 검증할 상황을 포함

**① 동일 장애의 중복 알림 묶기**

**[이미지 내용]**

| 시각 | 알림 | 발생 경로 |
|---|---|---|
| 10:12 | 결제 서버 오류 | 자동 모니터링 |
| 10:13 | PG 결제 실패 알림 | 외부 연동 |
| 10:14 | 고객 문의 급증 | CS 인입 |

원본은 같은 장애에서 발생한 알림을 하나의 `INC01`로 묶습

장애 예시 정보는 다음과 같음습

- 발생 시각: 2024-05-12 10:12
- 영향 서비스: 결제
- 증상: 결제 승인 실패
- 상태: 조사 중
- 등록자: 시스템 자동

**[구현 보완]**

- 개별 알림은 삭제하지 않고 대표 장애에 연결
- 시간대·서비스·증상·거래 정보를 근거로 묶습
- 잘못 묶은 알림을 분리가능해야 함
- 단순히 비슷한 시각에 발생했다는 이유만으로 서로 다른 장애를 합치지 않음

**② PG 불명은 실패로 단정하지 않기**

원본 결제 이력 예시:

| 주문번호 | PG사 | 결과 |
|---|---|---|
| A1001 | PG-A | 실패 |
| A1002 | 미확인 | 불명 |
| A1003 | PG-B | 실패 |
| A1004 | PG-A | 성공 |
| A1005 | 미확인 | 불명 |

원본 확인 항목:

- PG 연동 상태와 장애 여부
- 네트워크·타임아웃 여부
- 주문 상태와 결제 상태 교차 확인
- 고객 문의 내용의 패턴
- 추가 로그와 PG사 확인

**PG사 미확인과 결제 결과 미확인은 별도 정보.** PG사 정보가 없다는 사실만으로 결제 실패를 확정 불가

**[구현 보완]**

이미 결제된 주문은 **결제 재실행 대상에서는 제외**하지만, 주문 확정 누락 등의 복구 대상에서는 제외하지 않음

**8. 대응 흐름과 상태 구분**

**[구현 보완] 기본 대응 흐름**

장애 감지 → 중복 알림 연결 → 담당자 배정·영향 판단 → 필요한 보호 조치 승인·적용 → 영향 주문 조사 → 주문별 복구 → 고객 안내 → 정상화 확인 → 미결 인수 → 종료 승인 → 후속 모니터링

보호 조치, 영향 주문 조사, 고객 공지는 상황에 따라 병행가능

**주문별 처리 분기**

| 확인 결과 | 처리 |
|---|---|
| PG 승인 확인 + 주문 미확정 | 현재 주문·재고·취소 상태를 검증한 뒤 주문 재확정 |
| PG 승인 확인 + 주문 확정 완료 | 중복 확정·결제 없이 결과 기록 |
| PG 결과 불명 | 확인 중 유지, 기존 거래 재조회, 담당자·다음 확인 시각 지정 |
| PG 실패 확인 | 실패 근거 기록 후 정책에 따른 후속 처리 |
| 내부 기록과 PG 기록 불일치 | 불일치 건으로 관리하고 추가 대사 |
| 주문 취소·환불 진행 중 | 해당 상태와 충돌하지 않는 별도 복구 절차로 연결 |

| 대상 | 상태 예시 |
|---|---|
| 장애 | 감지, 조사 중, 조치 중, 정상화 확인 중, 종료 |
| 영향 주문 조사 | 미판정, 확인 중, 판정 완료 |
| 복구 작업 | 대기, 실행 중, 성공, 실패, 결과 불명 |
| 보호 조치 | 요청, 승인, 적용 중, 적용 완료, 해제 완료, 실패 |
| 인수인계 | 작성, 전달, 수락 |

영향 주문의 ‘확인 중’을 주문의 배송·피킹 상태와 같은 필드에 섞지 않음 인수 완료 여부도 별도 관리하여, **인수되었지만 아직 해결되지 않은 주문**을 표현가능해야 함

**9. 검증 조건과 예외·실패 처리**

아래 항목: 프로젝트 추가 검증 대상 **[구현 보완]**, 검증 미실행.

| 상황 | 필요한 검증·처리 | 담당 주체 |
|---|---|---|
| PG 조회 시간 초과 | 실패로 확정하지 않고 기존 거래 재조회 예약 | 결제 담당·시스템 |
| 조사 중 승인 결과가 늦게 도착 | 최신 결제 상태 재확인 후 예정된 재처리 조정 | 결제 시스템 |
| 두 담당자가 동시에 재확정 | 한 번만 확정되도록 상태 조건·동시성 제어 적용 | 주문 시스템 |
| 재확정 성공 후 응답 유실 | 동일 작업 조회·재요청 시 기존 결과 반환 | 주문·복구 시스템 |
| 복구 도중 취소·환불 발생 | 현재 상태를 다시 검증하고 충돌 작업 중단 | 주문·결제 담당 |
| 재고 예약 해제·결품 | 주문 강제 확정 없이 정책에 따른 후속 처리 | 주문·재고·운영 |
| 승인 없는 보호 조치 실행 | 실행 거절, 요청 기록 보존 | 권한·정책 시스템 |
| 승인 완료 후 조치 적용 실패 | 승인 상태와 실제 적용 상태를 구분하여 재대응 | 운영·기술 담당 |
| 보호 조치 기간 만료 | 연장·해제 정책에 따라 처리하고 실제 상태 확인 | 승인자·운영 |
| 복구 후 고객 안내 실패 | 복구는 유지하고 안내 발송만 별도 재시도 | CS·알림 시스템 |
| 미결 주문 인수자가 미수락 | 인수 완료로 표시하지 않고 기존 책임 유지·재통보 | 인계·인수 담당 |
| 종료 후 동일 증상 재발 | 이전 장애와 연결하여 재개·신규 등록 여부 판단 | 온콜·운영 |

복구 작업은 **마지막으로 성공이 확인된 지점을 기준으로 필요한 단계만 다시 수행** 고객 안내 실패 때문에 결제를 다시 실행하거나, 응답을 못 받았다는 이유로 주문 확정을 무조건 반복하지 않음
