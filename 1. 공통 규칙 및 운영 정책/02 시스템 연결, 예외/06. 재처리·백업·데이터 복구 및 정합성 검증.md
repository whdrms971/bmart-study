

**1. PART의 목적**

**장애 발생 후 서버 재기동과 실제 업무 복구 완료 구분.**

- 결제는 성공했지만 주문 저장 누락 가능.
- 주문은 존재하지만 출하 작업을 생성하는 이벤트 누락 가능.
- 백업 이후 발생한 주문·취소·환불 기록이 복원 데이터 누락 가능.
- 데이터는 정상이어도 센터 정전으로 피킹·포장·출하가 업무 불가능 가능성.
- 복구 과정에서 이벤트를 다시 처리하면 작업·환불 중복 위험.

PART 목적: **데이터·현장 상태 동시 확인, 필요한 범위의 제한적 복구, 주문 확정 또는 취소·환불까지 처리**.

전체 처리 흐름:

장애 감지  
→ 영향 범위 확인 및 필요한 접수·쓰기 제한  
→ 주문·결제·이벤트·현장 상태 조회  
→ 재처리 / 백업 복원 / 대체 운영 선택  
→ 누락·중복·취소·재고 대조  
→ 복구 반영 승인  
→ 서비스 재개 승인  
→ 고객 안내 및 사후 모니터링

**3. 이미지별 세부 주제**

**3-1. 29 — 데이터 손실 여부별 복구 경로**

**이미지의 핵심 내용**

주문번호 `9001`, 결제금액 `11,000원`, PG `PG01`인 사례에서 **결제는 승인되었지만 주문 저장이 실패한 상황**을 제시.

복구 경로: 세 가지.

| 경로 | 이미지의 처리 내용 | 판단 기준 |
|---|---|---|
| 2-A. 데이터가 존재하는 경우 | 기존 PG 결제 내역 조회 → 동일 요청 K01 재처리 → 주문 1건 복구 | 기존 요청을 확인하고 재처리할 수 있는가 |
| 2-B. 데이터가 손실된 경우 | 쓰기 중단 → B01 격리 복원 → PG·주문 대조 → 서비스 재개 | 필요한 원본 데이터가 손실되었는가 |
| 2-C. 센터 운영이 불가능한 경우 | 기사·현장 업무 확인 → 대체 운영 전환 → 고객 안내 | 센터에서 실제 작업을 계속할 수 있는가 |

최종적으로 고객은 앱에서 **주문 확정 또는 환불 완료 결과**를 확인.

**업무 주체와 권한**

| 주체 | 역할·권한 | 접근 범위 |
|---|---|---|
| 운영 관리자 | 장애 주문 조회, 복구 경로 판단, 복구 요청 | 담당 센터 또는 별도로 부여된 장애 대응 범위 |
| 결제 담당자·권한을 가진 운영자 | 기존 PG 승인·취소·환불 내역 조회 | 대상 주문에 연결된 거래 |
| 시스템 | 중복 확인, 주문 복구, 상태 반영 | 승인된 복구 대상 |
| 인계 담당자·배송기사 | 실제 인계·배송 출발 여부 확인 | 자신이 담당하는 주문 |
| 센터 현장 담당자 | 피킹·포장·출하 진행 상황 확인 | 담당 센터 |
| 승인 관리자 | 복구 반영·대체 운영·예외 조치 승인 | 승인 권한이 부여된 센터·업무 |
| 고객·CS 담당자 | 고객은 결과 확인, CS는 진행 상황 안내 | 본인 주문 또는 상담 대상 주문 |

**사용·변경 데이터**

- 사용: 원본 주문 요청, PG 거래번호, 승인금액·시각, 주문 저장 상태, 백업 정보, 현장 작업 상태.
- 변경: 복구 주문, 복구 처리 상태, 담당 센터, 취소·환불 상태, 고객 안내 이력.

**구현 시 보완할 사항**

1. **“데이터가 존재한다”는 표현을 구체화 필요.**  
   주문이 이미 존재하는지, 주문은 없지만 원본 요청이 남아 있는지에 따라 조치 구분 필요. 주문이 있다면 주문을 새로 만들지 않고 누락된 후속 처리만 복구.

2. **PG 승인 내역만으로 주문 전체를 재구성 금지.**  
   상품·수량·가격·할인·배송지 등 신뢰할 수 있는 주문 원본이 필요. 결제 정보만 남아 있다면 추가 대조 또는 취소·환불 검토가 필요.

3. **복구 주문도 재고·배송 가능 여부를 확인 필요.**  
   기존 예약 재고가 남아 있다면 이를 연결하고, 이미 해제되었다면 재확보 가능 여부를 확인 필요. 무조건 예약을 추가하면 이중 예약 위험.

4. **세 경로는 동시에 필요할 가능.**  
   센터 정전과 데이터 손실이 함께 발생하면 격리 복원과 대체 운영을 병행필요.

5. **환불 요청과 환불 완료를 구분 필요.**  
   외부 PG 처리 결과가 확정되기 전에는 고객에게 완료로 표시미실행.

**정상 흐름**

운영 관리자 장애 주문 확인  
→ 결제 담당자가 기존 PG 거래 확인  
→ 시스템이 주문·원본 요청·중복 여부 확인  
→ 필요한 복구 실행  
→ 현장 처리 가능 여부 확인  
→ 주문 확정 또는 승인된 취소·환불 처리  
→ 고객 결과 안내

**3-2. 30 — 재처리·백업 복원·재해 복구의 선택**

세 가지 장애 유형을 각각 독립 시나리오로 구분.

**A. 이벤트 E01 누락**

원문 사례에서는 주문 `9001`이 이미 존재하지만 이벤트 `E01`이 누락되어 존재.

주문 존재 확인  
→ 이벤트 누락 확인  
→ E01 재전송 요청  
→ 수신 시스템에서 TASK01 중복 여부 확인  
→ 필요한 작업 1건 생성  
→ 재전송·처리 결과 확인

- **운영 관리자:** 주문·이벤트 조회 및 재전송 요청.
- **시스템:** 동일 업무의 작업이 이미 있는지 확인하고 중복 생성을 차단.
- **현장 작업자:** 생성된 작업을 확인하여 수행.
- **승인 관리자:** 위험도에 따라 수동·대량 재전송 승인. 원문에는 구체적인 승인 정책이 없음.

**추가 설계**

- 이벤트 로그가 없다는 이유만으로 현장 작업까지 없다고 단정미실행.
- 이미 피킹·출하 작업이 생성되었다면 해당 작업과 연결 상태를 확인.
- 취소된 주문이나 완료된 주문은 현재 상태에 맞지 않는 이벤트 재실행을 차단.
- 이벤트 전송 성공, 수신 성공, 작업 생성 성공을 따로 기록.
- 고객에게 추가 결제를 요청미실행.

**B. 주문 데이터 삭제**

원문 사례에서는 주문 `9002`가 조회되지 않아 B01 격리 환경 복원 사례.

삭제·누락 범위 확인  
→ 격리 환경에 B01 복원  
→ 복원 시점 이후 거래 대조  
→ 중복·취소·재고 영향 확인  
→ 담당자 승인  
→ 운영 반영

- **복구 담당자:** 백업 조회, 격리 복원, 차이 분석.
- **결제 담당자:** 복원 시점 이후 결제·취소·환불 대조.
- **재고 담당자:** 실물 및 예약 재고 확인.
- **승인 관리자:** 검증 결과를 확인하고 운영 반영 승인.
- **시스템:** 승인 대상과 실제 반영 대상이 동일한지 확인.

이미지의 복원 데이터 `120건`, 이후 거래 `15건`, 중복 의심 `0건`은 **설명용 예시 수치**.

**추가 설계**

- 단순 조회 실패가 실제 삭제인지, 조회 장애·권한 문제인지 먼저 확인.
- 과거 백업을 통째로 덮어쓰면 정상적인 최신 거래가 사라질 가능.
- 주문을 복구한다고 재고 자동 증가 금지.
- 운영 데이터가 검증 이후 변경되면 차이를 다시 확인하고 필요 시 재승인.

**C. 센터 G01 정전**

센터 G01 정전  
→ 영향 지역 신규 주문 접수 제한  
→ 고객 안내  
→ 현장 안전 확인  
→ 진행 주문 및 배송기사 연락  
→ 대체 처리 또는 정상화 판단

- **현장 책임자:** 전원·설비·작업자 안전 확인.
- **운영 관리자:** 접수 제한 및 진행 주문 관리.
- **배송기사:** 배송·인계 현황 보고.
- **CS 담당자:** 접수 제한과 주문별 변경 사항 안내.
- **승인 관리자:** 센터 전환·운영 재개 등 정책상 필요한 승인.

**추가 설계**

- 접수 제한 범위를 센터·배송 지역별로 관리.
- 이미 포장되었거나 기사에게 인계된 주문을 별도로 구분.
- 다른 센터로 넘길 때 재고, 배송 범위, 처리 여력, 기존 센터의 작업 중단 여부를 확인.
- 두 센터가 같은 주문을 동시에 출하하지 않도록 처리 주체를 확정.
- 전원 복구 후에도 냉장·냉동 설비와 상품 상태를 확인 필요.

**3-3. 31 — 백업·복구·대사 기록 연결**

**이미지의 핵심 내용**

백업 이후에 발생한 주문은 **백업만으로 복원 불가** 사례.

시간순 사건 정렬:

| 시각 | 사건 | 의미 |
|---|---|---|
| 10:00 | B01 백업 완료 | 해당 시점까지 데이터 보관 |
| 10:05 | 주문 9001 및 11,000원 결제 발생 | B01에는 포함되지 않은 후속 거래 |
| 10:10 | 시스템 장애 | 주문 처리·조회 중단 |
| 10:20 | B01 격리 복원 | 주문 9001이 없는 상태 확인 |
| 10:25 | PG01 대사 | 복원 데이터에 반영되지 않은 결제 발견 |
| 10:30 | REC01 승인 복구 | 주문 복구 기록 생성 |
| 10:31 | E01 재전송·TASK01 생성 | 누락된 후속 업무 연결 |
| 전체 | A01 감사 로그 | 모든 처리의 연결 관계 기록 |

이미지에서는 장애 화면 뒤에 10:05 주문 화면이 배치되어 있지만, **실제 시간순으로 주문 발생이 장애보다 앞섬**.

**코드별 역할**

| 코드 | 이미지에서의 의미 | 연결할 정보 |
|---|---|---|
| B01 | 백업 | 백업 시점, 대상 데이터, 복원 작업 |
| PG01 | PG 결제·대사 참조 | 거래번호, 금액, 상태, 대사 결과 |
| REC01 | 주문 복구 | 복구 대상, 근거, 처리자, 승인 결과 |
| K01 | 주문 조회 화면 | 복구 전·후 주문 조회 결과 |
| E01 | 주문 승인 이벤트 | 대상 주문, 재전송 및 수신 결과 |
| TASK01 | 출고 작업 | 생성된 작업, 담당자, 진행 상태 |
| A01 | 감사 로그 | 장애·복원·대사·승인·이벤트·작업 기록 |

**원문 표기상 주의점**

29번에서는 `K01`을 **동일 요청의 재처리 코드**처럼 사용하지만, 31번에서는 **주문 조회 화면 코드**로 사용.

따라서 프로젝트에서는 다음 식별자를 별도로 정의하는 방안 권장.

- 화면 식별자
- 원본 요청 식별자 또는 멱등 키
- 복구 작업 식별자
- 이벤트 식별자
- 현장 작업 식별자

또한 `PG01`, `E01`, `TASK01`도 유형 코드인지 개별 거래·이벤트·작업의 고유번호인지 분리필요.

**업무 주체와 승인**

- 복구 담당자는 B01을 격리 복원하고 누락 후보 추출.
- 결제 담당자는 PG 거래와 주문 대조.
- 승인 관리자는 복구 근거와 반영 범위를 확인.
- 시스템은 승인된 주문을 복구하고 후속 이벤트를 처리.
- 현장 담당자는 TASK01을 수행.
- 감사 담당자는 전체 연결 이력을 조회.

**추가 설계**

- PG 결제 존재만으로 현재도 주문 이행이 필요한지 확정미실행. 후속 취소·환불까지 확인.
- 백업 이후 거래는 PG뿐 아니라 주문 원본, 취소 기록, 이벤트 기록, 현장 기록을 함께 대조.
- 이미지의 승인 복구 완료는 **주문 복구 완료**이며, 배송 완료를 뜻미실행.
- TASK01 생성 후 전송이 실패했다면 작업을 새로 만들지 않고 기존 작업의 전달 재시도.
- 복구 실행자와 승인자는 별도로 기록하고, 자기승인은 차단하는 정책을 권장.

**3-4. 32 — 복구 후 중복·누락·재고 대조 검증**

이 이미지는 네 개의 독립적인 검증 시나리오를 제시. 아래 결과는 **실제 테스트 통과 결과가 아닌 기대 결과**.

| 검증 | 초기 조건 | 기대 결과 |
|---|---|---|
| 주문 누락 복구 | PG 결제 11,000원 존재, 연결 주문 없음 | 근거 확인 후 주문 1건 복구, 추가 청구 0원 |
| 중복 이벤트 수신 | 동일 주문의 동일 E01이 두 번 전달 | 필요한 작업 1건, 추가 작업·주문 0건 |
| 취소 누락 복구 | 복원 데이터에 C01 취소 기록 없음 | 원기록 대조 후 확인된 취소 상태·이력 보완 |
| 재고 대조 | 실물 10개, 예약 2개, 판매 가능 8개 | 복구 후에도 실제 업무 상태와 수량 일치 |

**① 주문 누락 복구 검증**

결제 담당자 PG 거래 확인  
→ 운영 관리자 원본 주문 확인  
→ 시스템 기존 주문·환불·복구 이력 확인  
→ 승인된 복구 실행  
→ 주문 1건·추가 청구 0원 확인

추가 검증:

- 같은 복구 요청을 두 번 실행해도 주문이 한 건만 남는가?
- 동일 결제가 다른 주문에 이미 연결되어 있지 않은가?
- 이미 취소·환불된 결제를 주문 확정으로 되살리지 않는가?
- 상품·수량·금액·배송지의 근거가 보존되어 있는가?

**② 중복 이벤트 수신 검증**

시스템 E01 수신  
→ 처리 이력 및 업무 대상 확인  
→ 최초 처리면 필요한 작업 생성  
→ 동일 이벤트 재수신이면 추가 생성 방지  
→ 기존 처리 결과 반환

추가 검증:

- 두 이벤트가 동시에 도착해도 중복 생성되지 않는가?
- 작업 생성 직후 시스템이 중단되어도 재시도 시 기존 작업을 찾는가?
- 이벤트 처리 완료 기록과 작업 생성 결과가 불일치하지 않는가?

단, **같은 주문번호라는 이유만으로 모든 이벤트를 중복 처리 금지.** 주문에는 승인·취소·상태 변경 등 서로 다른 정상 이벤트 발생 가능.

**③ 취소 누락 복구 검증**

원기록 확인  
→ 취소 요청·취소 확정·환불 상태 구분  
→ 현재 출하·인계 상태 대조  
→ 확인된 상태와 이력 보완  
→ 후속 작업 차단·재고 예약 해제·환불 결과 대조

이미지에는 “고객 취소 요청(C01)”과 “환불 처리”가 함께 나옵니다. 구현에서는 다음을 구분 필요.

| 상태 | 의미 |
|---|---|
| 취소 요청 | 고객이 취소를 요구함 |
| 취소 확정 | 정책과 주문 상태에 따라 취소가 확정됨 |
| 환불 요청 | PG에 환불 처리를 요청함 |
| 환불 완료 | PG 결과까지 확인됨 |

취소 요청 기록만 보고 주문을 취소 확정으로 바꾸거나, 이미 완료된 환불을 재실행 금지.

또한 **백업 이후에 발생한 취소라면 그 이전 백업에는 기록이 없음.** 후속 로그·이벤트·PG 기록 등에서 근거를 확보필요.

**④ 재고 수량 대조 검증**

이미지의 단순 수량 관계:

**판매 가능 수량 8개 = 실물 수량 10개 − 예약 수량 2개**

- 재고 담당자: 실물 확인 및 차이 사유 조사.
- 시스템: 예약 주문과 예약 수량의 연결 확인.
- 승인 관리자: 재고 조정 승인.
- 운영 관리자: 차이가 해소되지 않은 상품의 판매 제한.

추가 검증:

- 취소된 주문의 예약이 복구 과정에서 다시 살아나지 않는가?
- 출고된 상품이 재고에 다시 포함되지 않는가?
- 동일 주문의 예약이 중복 생성되지 않는가?
- 불량·폐기·검수 대기 등 판매 제외 수량이 반영되는가?

실제 재고 모델에 판매 제외 수량이 있다면 위 단순 공식만으로 판매 가능 수량을 계산해서는 금지.

**3-5. 33 — 복구 목표·승인·재개 기준 결정**

**이미지의 핵심 내용**

팀 회의에서 복구 기준 결정  
→ 백업 관리  
→ 결제·중복·실물 검증 후 재처리 승인  
→ 누락 거래 확인 후 재개 승인  
→ 서비스 재개 및 고객 안내

이미지는 주문·결제·재고·상품 이미지별 RPO·RTO를 제시하지만, **모든 값 미정**.

| 단계 | 이미지의 요구사항 | 구현 보완 |
|---|---|---|
| 목표 결정 | 서비스 영향과 고객 경험을 고려하여 기준 합의 | 데이터별 책임자, 측정 기준, 우선순위 기록 |
| 백업 관리 | 저장 위치 분리, 암호화, 복원 훈련 검토 | 백업 무결성, 복호화 가능 여부, 접근 권한 확인 |
| 재처리 승인 | PG 조회, 중복 방지, 실물 대조 | 대상·버전·예상 변경 내용과 승인 연결 |
| 재개 승인 | 누락 거래 0건, 담당자 승인 | 검증 대상 전체를 조회했는지 확인 |
| 서비스 재개 | 승인 후 정상화 및 고객 안내 | 단계적 개방과 재장애 모니터링 |
| 미해결 | 접수 제한 유지, 해결 상황 안내 | 보류 사유·담당자·다음 확인 시점 관리 |

**중요한 예외**

- PG 조회가 실패하여 결과가 비어 있는 경우는 “누락 거래 0건”이 아님.
- 복원은 되었지만 개인정보 복호화나 주문 조회가 실패하면 복구 완료가 아님.
- 데이터 검증이 끝나도 센터 안전이 확인되지 않으면 현장 업무를 재개할 수 없음.
- 승인 후 대상 데이터가 달라졌다면 기존 승인으로 실행 금지.
- 재개 후 다시 오류가 증가하면 접수 제한 상태로 전환할 수 필수.

**승인 분리 권장안**

복구 요청자  
→ 복구 담당자 검증  
→ 승인 관리자 복구 반영 승인  
→ 시스템 반영  
→ 운영·현장 책임자 최종 확인  
→ 재개 승인  
→ 서비스 개방

원문은 승인 절차를 제시하지만 **요청자·승인자의 분리, 자기승인 금지, 임시 권한 만료 정책까지 미확정.** 이 부분은 프로젝트 설계로 추가 설계 필요.

| 변경 | 승인된 주문 복구 반영, 재고 조정 |
| 승인 | 복구 반영·환불·서비스 재개 승인 |

| 감사 조회 | 누가 어떤 근거로 복구했는지 확인 |
| 긴급 접근 | 장애 대응 기간에만 부여되는 임시 접근 |

**센터·조직 범위와 임시 권한**

- 다른 센터 데이터에 접근하려면 별도 범위가 필요.
- 센터 전환 시 주문 처리 권한의 소유 주체를 명확하게 변경.
- 권한은 화면 진입뿐 아니라 실행 시점에도 확인.
- 임시 권한에는 장애번호, 대상 범위, 허용 행위, 승인자, 만료시각을 연결.
- 긴급 권한으로 실행한 조치는 사후 검토 대상에 포함.
- 강제 처리 권한도 중복 결제·중복 환불 같은 핵심 제약을 무시하는 권한으로 설계미실행.

| 재고 | 센터·상품별 실물·예약·판매 제외 수량 | 실사 결과, 조정 요청 및 승인된 변경 |
| 승인 | 요청자, 대상, 사유, 검증 결과 | 승인·반려·만료·철회 이력 |
| 고객 안내 | 대상 주문·고객, 안내 사유 | 발송 결과, 재시도 및 상담 이력 |
| 감사 | 사용자, 권한, 센터, 관련 업무 식별자 | 변경·실행·승인·실패 기록 |

복구 기록은 최소한 다음 관계를 추적할 수 필수.

**장애 → 백업·복원 → 대사 → 복구 승인·실행 → 주문 → 이벤트 → 현장 작업 → 고객 안내**

**6. 정상 업무 흐름**

| 순서 | 담당 주체 | 처리 | 다음 단계 진입 조건 |
|---|---|---|---|
| 1 | 시스템·운영 관리자 | 장애 감지 및 영향 범위 확정 | 영향 센터·기능 파악 |
| 2 | 운영 관리자·시스템 | 필요한 접수·쓰기 제한 | 추가 손실·중복 위험 통제 |
| 3 | 결제·복구·현장 담당자 | 주문·PG·이벤트·현장 상태 확인 | 복구 근거 확보 |
| 4 | 운영 관리자 | 재처리·복원·대체 운영 경로 선택 | 장애 유형에 맞는 계획 수립 |
| 5 | 복구 담당자 | 격리 복원 또는 재처리 대상 준비 | 변경 대상과 영향 확인 |
| 6 | 결제·재고·현장 담당자 | 누락·중복·취소·재고 대조 | 불일치 해결 또는 대상 보류 |
| 7 | 승인 관리자 | 복구 반영 승인 | 승인 대상·범위·근거 확정 |
| 8 | 시스템·복구 담당자 | 승인된 복구 실행 | 실행 시점 권한·상태 재확인 |
| 9 | 시스템·현장 담당자 | 후속 이벤트·작업 정상화 | 필요한 작업이 중복 없이 연결 |
| 10 | 운영·현장 책임자 | 데이터·시스템·현장 최종 점검 | 재개 기준 충족 |
| 11 | 재개 승인자·시스템 | 서비스 개방 | 유효한 재개 승인 존재 |
| 12 | CS·시스템 | 고객 안내·사후 모니터링 | 실제 처리 결과와 안내 일치 |

**상태값별 분리 관리 권장.**

- 복구 작업: `요청 → 조사 중 → 검증 중 → 승인 대기 → 실행 중 → 완료 / 실패 / 보류`
- 서비스: `정상 → 접수 제한 → 복구 중 → 재개 검증 → 재개 승인 → 정상`
- 주문·결제·현장 작업은 각자의 상태를 유지하고 복구 상태와 연결.

주문의 배송 상태를 단순히 “복구 완료”로 덮어쓰기 금지.

**9. 실패 시 처리와 복구 원칙**

| 실패 지점 | 처리 방법 |
|---|---|
| 백업 복원 실패 | 운영 반영을 중단하고 다른 유효 백업·복구 자료 검토 |
| 백업 무결성 검증 실패 | 해당 백업 사용 보류, 손상 범위 조사 |
| PG 조회 불가 | 결제 상태 미확정으로 보류, 중복 결제·환불 요청 방지 |
| 일부 주문만 복구 성공 | 성공·실패 대상을 분리하고 실패 건만 재처리 |
| 이벤트 전송 실패 | 같은 업무 식별 관계를 유지하여 재전송 |
| 현장 작업 수신 확인 불가 | 새 작업 생성 전 기존 작업 수신·진행 여부 확인 |
| 재고 불일치 | 해당 상품·센터 판매 제한 및 실사 |
| 승인 반려·만료 | 운영 반영 중지, 사유 보완 후 재요청 |
| 고객 안내 실패 | 실제 주문 상태는 보존하고 안내만 재시도 |
| 서비스 재개 후 재장애 | 영향 범위 접수 제한, 진행 주문 보호 및 원인 재확인 |

**복구 실패 시 운영 DB 전체를 과거 시점으로 복원하는 방식은 최신 정상 거래 손실 위험 존재.** 반영 범위와 변경 내역을 기록하여 재처리·보정 대상을 특정필요.

외부 PG에서 이미 완료된 결제·환불이나 실제 출고·인계는 내부 DB 롤백만으로 되돌릴 수 없으므로, 현재 상태를 확인한 후 별도의 보정 절차로 처리.

**11. 감사 이력**

| 구분 | 남겨야 하는 정보 |
|---|---|
| 실행 주체 | 사용자·시스템 계정, 당시 역할·권한, 소속·대상 센터 |
| 대상 | 장애 ID, 주문 ID, PG 거래 ID, 백업·복구·이벤트·작업 ID |
| 시간 | 원본 업무 발생 시각, 복구 요청·승인·실행·완료 시각 |
| 근거 | 장애 사유, 원본 기록, 대사·실사 결과, 선택한 복구 경로 |
| 변경 내용 | 변경 전후 상태·수량·금액, 데이터 버전 |
| 승인 | 요청자·승인자, 승인 범위, 승인·반려 사유, 유효기간 |
| 실행 결과 | 성공·실패·일부 성공, 오류, 재시도, 중복 차단 결과 |
| 긴급 조치 | 임시 권한 발급·사용·만료·회수, 강제 처리 사유, 사후 검토 |
| 고객 안내 | 안내한 실제 상태, 발송 시각·결과 |

복구 시 **원래 업무 발생 시각과 복구 기록 보완 시각 모두 기록 필수.** 취소가 과거에 발생했다면 과거 취소 사실과 현재 복구 행위를 별도 이력 추적.

감사 로그에 개인정보·결제 민감정보를 불필요하게 복제하지 않고, 감사 조회 권한과 업무 변경 권한 분리.
