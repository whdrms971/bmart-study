
**1. PART의 목적**

신규 앱·API·판매 정책의 운영 적용 시 보장할 사항

- 구버전 고객 앱에서도 허용된 기본 주문 기능이 정상 동작 보장 필요
- 주문마다 어떤 앱·API·정책·배포 버전으로 처리됐는지 추적 가능성 확보
- 정책이 변경되더라도 기존 주문의 금액과 처리 이력이 임의로 바뀌면 안 됨
- 동일한 주문 요청이 재전송돼도 주문·결제 결과가 중복 생성되면 안 됨
- 오류가 발생하면 배포를 중단하거나 이전 코드로 롤백 가능성 확보 필요
- 코드 롤백으로 해결되지 않는 데이터 변경은 별도 복구 절차로 처리 필요
- 배포 요청·승인·실행·중단·복구의 권한 주체와 감사 이력이 구분 관리 필요

전체 업무 연결

개발·호환성 검증  
→ 배포 검토 및 승인  
→ 일부 대상에 적용  
→ 주문에 적용 버전·금액 기록  
→ 고객 앱·관리자·PDA 결과 확인  
→ 지표 관찰  
→ 확대 / 중단 / 롤백 판단  
→ 필요 시 데이터 복구·환불  
→ 정상화 확인 및 사후 검토

| 배포 버전 | 실제 운영에 적용한 실행 코드·설정의 식별 정보 | 주문을 처리한 서버 구현을 추적하는 데 필요 |

| 단계적 배포 | 일부 대상부터 변경을 적용하고 범위를 늘리는 방식 | 적용 대상과 비율, 관찰 시간, 확대 기준이 필요 |
| 배포 중단 | 추가 배포나 확대를 멈추는 조치 | 이미 적용된 코드를 이전 버전으로 되돌리는 것과 차이 존재 |
| 코드 롤백 | 실행 코드를 이전 버전으로 되돌리는 조치 | 주문·결제·배송 데이터가 자동 취소되는 것은 아님 |
| 데이터 복구 | 변경되거나 손상된 데이터를 정해진 절차로 회복하는 작업 | 코드 롤백과 별도 계획·검증이 필요 |
| 정정·환불 | 특정 거래의 오류를 별도 업무 절차로 바로잡는 처리 | 원주문 기록을 덮어쓰는 처리와 구분 필요 |
| 재요청 처리 | 동일한 업무 요청의 재전송을 식별하고 기존 결과를 반환하는 처리 | 같은 장바구니로 새 주문을 만드는 것과 차이 존재 |

**앱·API·정책·배포 버전은 각각 별개의 정보**. 단일 `version` 값으로 통합 시 장애 원인·적용 정책의 정확한 추적 곤란

**롤백 시 보존해야 하는 사항**

[원문]

[설계 보완]

코드와 정책 설정이 별도로 운영된다면 **코드만 되돌려도 정책이 V1으로 복귀하는지 확인 필요.** 롤백 계획에는 코드·정책 설정·기능 활성화 설정의 복귀 대상을 각각 명시 필요

**주요 예외**

| 상황 | 필요한 처리 |
|---|---|
| V2에서 결제 실패가 증가 | 확대 중단 → 영향 주문 확인 → 승인된 절차로 롤백 |

**3-2. 47 — 앱·API·정책·배포 버전 기록 연결**

**핵심 주제**

주문 생성 당시의 버전과 금액을 기록하고, 고객·관리자·현장 단말에서 같은 주문을 일관되게 확인

**원문 업무 순서**

고객 앱 A2에서 주문  
→ API S2로 전달  
→ 정책 P1로 금액 계산  
→ 주문·금액·버전 정보 저장  
→ 관리자·PDA에서 확인

이미지 예시

| 구분 | 주문 9001 | 주문 9002 |
|---|---|---|
| 앱 버전 | A2 | A2 |
| API 버전 | S2 | S2 |
| 정책 버전 | P1 | P2 |
| 상품 금액 | 10,000원 | 10,000원 |
| 배송비 | 2,000원 | 2,500원 |
| 총 결제금액 | 12,000원 | 12,500원 |

**같은 앱 A2·API S2에서도 정책 P1·P2에 따라 금액 차이 발생**. 앱·API 버전만으로 주문 금액 재현 불가

**업무 주체와 권한**

| 주체 | 역할 | 접근 범위 |
|---|---|---|
| 고객 | 주문 요청, 본인 주문·금액 확인 | 본인 주문 |
| 주문 시스템 | 입력 검증, 실제 적용 정책 결정, 계산 결과 저장 | 해당 주문 처리에 필요한 데이터 |
| 운영 관리자 | 주문별 버전·금액·장애 영향 확인 | 부여된 조직·센터·업무 범위 |
| 현장 PDA 사용자 | 배정된 주문의 출고·배송 관련 정보 확인 | 소속 센터·배정 작업 |
| 정정 요청 담당자 | 오류 근거를 확인하고 정정·환불 요청 | 담당 주문·민원 범위 |
| 승인 관리자 | 정정·환불 요청의 타당성 승인 | 별도 승인 권한 범위 |
| 감사 담당자 | 변경·승인·복구 이력 조회 | 부여된 감사 범위 |

고객·관리자·PDA가 동일한 주문 정보를 확인한다는 것은 **화면에 노출되는 모든 필드와 권한이 같다는 뜻은 아님.** 주문 금액·상태의 원본은 같되, 불 필요한 개인정보와 관리 기능은 역할별로 제한하는 것이 적절

**버전 기록의 신뢰 기준 — [설계 보완]**

이미지의 API 요청에는 앱·API 버전이 포함됨. 구현에서는 다음을 구분 필요

- 앱이 보낸 앱 버전: 호환성 판단·추적을 위한 정보
- 실제 요청을 처리한 API 버전: 서버가 확인해 기록
- 실제 적용 정책 버전: 서버의 계산 결과를 기준으로 기록
- 실제 배포 버전: 처리 서버의 배포 식별 정보를 기준으로 기록

클라이언트가 보낸 정책·금액·버전 값을 그대로 믿고 저장 금지

또한 여러 서비스가 주문·결제·출고를 따로 처리한다면, 주문 최초 생성 버전과 이후 작업을 처리한 버전을 **작업 이력별로 추가 기록**하는 것이 권장

**코드 롤백과 정정·환불의 분리**

[원문]

API S2 → S1 롤백  
→ 기존 주문 9002의 정책 P2·금액 12,500원 유지

금액 오류가 확인된 경우에는 별도 절차를 사용

관리자의 정정 요청  
→ 별도 승인  
→ 환불 처리  
→ 처리 결과 기록

[설계 보완]

원주문 금액은 보존하고, 정정 사유·환불 금액·환불 결과를 연결된 별도 기록으로 관리. 실제 환불 연동에는 결제 시스템·외부 PG가 참여하며, 승인과 PG 환불 성공은 서로 다른 상태로 관리 필요

**배포 이력과 복구 이력**

이미지의 참조 코드

| 원문 표기 | 이미지상 용도 | 주의점 |
|---|---|---|
| REL01 | 릴리스 검토·승인·배포 관련 참조 | 실제 시스템의 고유 ID 규칙은 별도 설계가 필요 |
| AUD01 | 배포 변경·승인 이력 관련 참조 | 승인 기록과 감사 기록의 연결 구조를 정 필요 |
| REC01 | 장애 회복 절차 관련 참조 | 구체적인 복구 단계·실행 권한은 추가 정의가 필요 |

이 표기를 곧바로 DB 테이블명이나 확정된 상태 코드로 간주하지는 않음

**주요 예외**

- 주문에 정책 버전이 누락돼 금액 계산 근거를 확인할 수 없는 경우
- 고객 앱과 관리자 화면의 금액·상태가 다른 경우
- 배포 기록과 실제 처리 서버 버전이 다른 경우
- 롤백된 서버가 신규 주문 데이터 형식을 해석하지 못하는 경우
- 환불 승인 후 PG 응답이 끊겨 성공 여부가 불명확한 경우

마지막 경우는 실패로 단정해 다시 환불하지 않고, 기존 거래의 실제 결과부터 조회 필요

| 코드 롤백 후 | 기존 결제금액·배송 상태 보존 | 롤백이 주문 데이터를 과거 상태로 되돌리지 않는지 |
| 관리자 교차 확인 | 고객 앱과 상품·금액·상태 일치 | 조회 결과가 같은 주문 원본을 반영하는지 |
| 필수 변경 미지원 버전 | 업데이트 안내 후 해당 접근 차단 | 선택 기능 미지원과 필수 기능 미지원을 구분하는지 |

**① 선택 필드를 지원하지 않는 구버전**

[원문]

구버전 A1은 새 선택 필드를 표시하지 못하더라도 기본 옵션으로 결제가 가능하도록 호환성 확보 필요

[설계 보완]

- 서버는 해당 필드가 없는 요청을 처리할 기본값을 정의
- 최신 앱에서 선택한 옵션은 주문에 함께 저장
- 사용자가 보지 못한 유료 옵션을 자동 선택해 금액을 추가하지 않음
- 필수 선택이 필요한 상품이라면 같은 기본값 처리로 해결하지 말고 별도 호환 정책을 적용

**② 정책 적용 전후의 가격 차이**

[원문]

같은 SKU01이라도 정책 P1과 P2의 적용 시점에 따라 표시 금액이 달라지는지 검증

[결정 필요]

- 정책 적용 기준 시점
- 장바구니 가격의 유효기간
- 주문 생성 후 결제까지 정책이 바뀌었을 때 처리
- 고객에게 가격 변경을 알리고 재확인받는 조건

**화면에 표시한 금액과 실제 결제 요청 금액이 달라지면 조용히 결제하지 않도록 설계 필요.**

**③ 동일 요청 K01 재전송**

[원문]

최초 요청 K01에 P1·12,000원이 적용됐다면, 동일 요청 K01을 재전송해도 기존 결과를 유지

[설계 보완]

이를 구현하려면 요청 식별자만 저장하는 것보다 다음 정보가 필요

| 저장 정보 | 목적 |
|---|---|
| 요청 식별자 | 같은 요청인지 구분 |
| 요청자·업무 종류 | 다른 고객·다른 작업의 요청과 구분 |
| 요청 내용의 비교 정보 | 같은 키로 다른 상품·수량을 보내는지 검증 |
| 처리 상태 | 진행 중·성공·실패·결과 확인 필요 상태 구분 |
| 생성 주문 ID | 기존 주문으로 연결 |
| 확정 정책·금액·응답 | 재요청에 같은 결과 반환 |
| 생성·만료 시각 | 재요청 보장 기간 관리 |

동일 요청 K01 재전송  
→ 기존 요청 기록 조회  
→ 요청자·요청 내용 일치 확인  
→ 완료 상태라면 기존 주문·금액 반환  
→ 처리 중이면 중복 실행 방지

**같은 장바구니라도 새 요청으로 주문하면 정책이 달라질 수 있음.** 기존 금액 유지의 기준은 단순히 상품 구성이 같다는 것이 아니라, 동일한 업무 요청으로 인정되는지

추가로 같은 K01에 수량이나 배송지가 달라졌다면 기존 결과를 무조건 반환하지 말고 충돌로 처리 필요

**④ 롤백 후 원기록 보존**

[원문]

주문 9001·요청 K01의 결제금액 12,000원과 배송 중 상태는 코드 롤백 후에도 유지됨

[설계 보완]

‘보존’은 이후 상태 변경까지 막는다는 뜻이 아님

- 배송 중 → 배송 완료 같은 정상 업무 진행은 허용
- 코드 롤백 때문에 배송 중 → 결제 완료로 과거 상태를 덮어쓰면 안 됨
- 기존 주문 처리 이력은 유지하면서 새로운 작업 이력을 추가

**⑤ 필수 변경을 지원하지 않는 구버전**

[원문]

구버전 A0처럼 필수 변경을 지원하지 못하는 경우에는 업데이트 안내 후 접근을 차단하는 정책을 검토

| 선택 기능 미지원 | 필수 기능 미지원 |
|---|---|
| 기본 구매가 가능하도록 호환 처리 | 안내 후 해당 기능·서비스 접근 제한 가능 |
| 신규 필드가 없어도 처리 가능 | 필수 조건을 만족하지 못하면 처리 불가 |
| 불 필요한 전체 차단 방지 | 업데이트 경로·안내 메시지 제공 |

차단할 앱 버전과 기능 범위는 **미정**. 앱 전체를 차단할지, 주문 기능만 제한할지, 기존 주문 조회·CS 접근은 유지할지도 정 필요

**3-4. 49 — 배포 승인·적용 시점·중단 기준**

**핵심 주제**

앞선 이미지의 실행 흐름을 운영하기 위해, 배포 전후의 승인 기준과 정책 결정 항목을 정리

**원문 업무 순서**

서비스 담당자의 검토  
→ 배포 승인 요청  
→ 운영 담당자의 단계적 배포  
→ 운영·개발의 모니터링  
→ 이상 시 운영 담당자의 중단  
→ CS 안내  
→ 원인 분석·복구 또는 재배포 판단

**배포 전 확인사항**

| 확인 항목 | 확인 내용 | 판단 |
|---|---|---|
| 수용 기준 | 변경 기능이 요구된 동작을 만족하는지 | 결과와 근거 필요 |
| 데이터 변경 영향 | 기존 데이터의 의미·형식·값이 바뀌는지 | 영향 분석 필요 |
| 구 앱 호환성 | 지원 버전에서 주문·결제가 동작하는지 | 검증 결과 필요 |
| 복구 계획 | 실패 시 어떤 순서로 되돌릴지 | 비가역 변경이면 별도 복구 계획 필요 |
| CS 준비 | 고객 안내·문의 대응 방법이 준비됐는지 | 안내 내용·대응 경로 필요 |

이미지의 화면에서 일부 항목이 체크되지 않은 것은 예시이며, 실제 검증이 완료됐다는 증거는 아님

**정책 적용 시점 — 두 안 모두 보존**

| 구분 | 주문 생성 시 적용 | 결제 확정 시 적용 |
|---|---|---|
| 정책 확정 기준 | 주문이 만들어진 시점 | 결제가 확정되는 시점 |
| 원문상 특징 | 주문 단계부터 새 정책 적용 가능 | 실제 결제 완료 주문을 기준으로 적용 |
| 주요 고려사항 | 주문 후 취소·변경 처리 | 주문 생성~결제 사이 정책 불일치 |
| 추가 설계 | 미결제 주문의 가격 유지 기간 | 결제 전 최종 금액 확인·재동의 |
| 경계 상황 | 적용 직전 생성 후 적용 직후 결제 | 결제 처리 중 정책이 변경되는 경우 |

[설계 보완]

어느 안이든 결제 요청에 사용한 금액과 최종 확정 금액의 관계가 명확 필요. 특히 PG 결제 후 정책을 다시 계산해 결제금액을 임의로 바꾸는 방식으로 구현 금지

또한 정책 적용 시점은 고객 단말의 시각에만 의존하지 않고 서버의 확정 기준으로 판단 필요

**배포 비율·관찰 시간·중단 임계값**

원문에 1%·5%·10%·50%·100%가 제시되지만 **모두 예시이며 정책은 미정**

[결정 필요]

- 배포 대상을 고객·주문·센터 중 무엇으로 나눌지
- 비율을 어떤 모집단 기준으로 계산할지
- 각 단계에서 얼마나 관찰할지
- 최소 주문·결제 건수를 요구할지
- 어떤 오류율·성공률·지연을 중단 기준으로 사용할지
- 자동 중단과 운영자 수동 중단을 어떻게 구분할지
- 확대·재개·롤백 최종 권한을 누구에게 줄지

**DB 변경과 복구 계획**

[원문]

다음과 같은 비가역 변경이 포함되면 별도 복구 계획 없이 배포하지 않음

- 기존 데이터 의미 변경
- 기존 값 삭제 또는 덮어쓰기
- 되돌릴 수 없는 구조 변경

복구 계획에는 백업 방안·복원 절차·되돌리는 데 필요한 시간·영향 범위·담당자·승인 절차가 포함 필요

[설계 보완]

운영 중 새 주문이 계속 들어왔다면 DB 전체를 과거 백업으로 덮어쓰는 복구는 정상 거래까지 잃게 가능. 복구 계획에서 **보존할 정상 거래와 수정할 손상 데이터를 구분**필요

| 주문 버전 정보 | 앱·API·정책 버전, 최초 처리 배포 ID, 정책 확정 시각 | 주문 시스템 |
| 정책 버전 | 규칙, 적용 범위, 유효 시각, 승인 정보 | 정책 담당자·승인자·시스템 |
| 배포 기록 | 코드 식별자, 환경, 대상, 비율, 설정, 실행 시각·결과 | 배포 운영자·시스템 |
| 승인 기록 | 요청자, 승인자, 검토 대상 버전, 사유, 시각 | 요청자·승인자 |
| 호환성 기준 | 지원 앱/API, 선택·필수 필드, 기본값, 제한 기능 | 개발·서비스 담당자 |
| 재요청 기록 | 요청 키, 요청자, 요청 내용 비교값, 상태, 기존 결과 | 주문 시스템 |
| 모니터링 기록 | 오류·실패·지연·재고 이상, 측정 기간, 적용 대상 | 모니터링 시스템 |
| 정정·환불 기록 | 원주문·결제 ID, 사유, 승인, 환불 금액·PG 결과 | CS·승인자·결제 시스템 |
| 복구 기록 | 사고 ID, 대상, 복구 계획, 실행자, 결과·검증 | 복구 담당자·시스템 |
| 감사 기록 | 주체, 작업, 대상, 변경 전후, 승인 연결, 결과 | 시스템 |

**확정된 주문 금액·정책 정보는 당시 결과로 보존하고, 주문 상태는 정상 업무에 따라 변경 이력을 남기며 진행.**

**6. 정상 업무 흐름과 상태**

원문 흐름을 구현 가능한 상태로 정리한 **설계 제안**

**배포 흐름**

변경안 작성  
→ 개발·호환성·데이터 영향 검증  
→ 승인 요청  
→ 승인  
→ 부분 배포  
→ 관찰  
→ 확대  
→ 안정화 확인  
→ 완료

배포 상태 예시:

`작성 중 → 검증 중 → 승인 대기 → 승인됨 → 부분 적용 → 관찰 중 → 확대 중 → 완료`

이상 발견 시:

`부분 적용 / 관찰 중 / 확대 중 → 중단 → 롤백 중 → 복귀 검증 → 롤백 완료`

배포 중단 상태와 롤백 완료 상태를 하나로 합치지 금지

**주문 흐름**

고객 요청  
→ 앱/API 지원 여부 확인  
→ 동일 요청 여부 확인  
→ 상품·수량·센터 조건 검증  
→ 정책 적용 기준 판정  
→ 금액 확정  
→ 주문·버전 기록  
→ 결제·재고 등 후속 처리  
→ 고객·관리자·현장 조회 반영

결제·재고의 구체적인 처리 순서는 해당 도메인 설계와 연결 필요. 이 이미지들만으로 전체 주문 트랜잭션 순서가 확정되지는 않음

**복구 흐름**

장애 감지  
→ 배포 확대 중단  
→ 영향 주문·결제·데이터 확인  
→ 코드·설정 롤백 또는 별도 데이터 복구 판단  
→ 권한·승인 확인  
→ 실행  
→ 주문·결제·재고·출고 정합성 확인  
→ 정상화 판단  
→ 고객 안내·사후 검토

**7. 시스템 검증 조건**

| 검증 시점 | 반드시 확인할 조건 |
|---|---|
| 승인 요청 | 테스트 결과·호환성·데이터 영향·복구 계획이 준비됐는지 |
| 승인 | 승인자의 범위·권한, 자기승인 여부, 검토 대상 버전 |
| 배포 실행 | 승인받은 코드·설정·대상과 실제 실행 내용이 같은지 |
| 부분 배포 | 대상 선정 기준·비율이 의도대로 적용되는지 |
| 주문 수신 | 앱/API 지원 여부, 필수 입력, 고객·센터 접근 조건 |
| 정책 확정 | 적용 시점·대상·정책 버전이 모호하지 않은지 |
| 재요청 | 같은 요청자·같은 업무·같은 내용인지 |
| 결제 | 고객이 확인한 금액과 결제 요청 금액이 일치하는지 |
| 확대 | 정해진 관찰 기간·표본·지표 기준을 충족했는지 |
| 중단·롤백 | 중단 조건, 실행 권한, 복귀 대상, 기존 데이터 호환성 |
| 환불 | 승인, 이미 환불한 금액, 기존 PG 처리 결과 |
| 복구 완료 | 코드 기동뿐 아니라 주문·결제·재고·출고가 정상인지 |

부분 배포 대상을 요청마다 무작위로 다시 뽑으면 같은 고객의 조회·주문·결제에 서로 다른 조건이 적용될 수 있음. **대상 선정의 일관성과 주문에 확정한 정책 보존을 함께 설계 필요.**

**9. 실패 시 처리와 복구**

장애가 발생했다고 항상 같은 조치를 취 금지

| 문제 종류 | 우선 조치 | 후속 처리 |
|---|---|---|
| 신규 배포에서 오류 증가 | 확대 중단 | 코드·설정 롤백 검토 |
| 잘못된 정책으로 신규 주문 계산 | 문제 정책의 추가 적용 중단 | 영향 주문 추출, 정정·환불 검토 |
| 이미 결제된 금액 오류 | 원결제 결과 확인 | 별도 승인 후 환불 등 처리 |
| 주문 처리 중단·이벤트 누락 | 현재 처리 상태 확인 | 중복 방지 조건 아래 미완료 단계 재처리 |
| 데이터 손상 | 영향 확산 차단·증거 확보 | 승인된 복구 계획 실행 |
| 구버전 필수 기능 미지원 | 안내·해당 접근 제한 | 업데이트 유도 및 고객 지원 |
| 고객 불편·문의 발생 | 정확한 영향 범위 확인 | CS 안내 및 진행 상황 제공 |

**재처리와 신규 실행도 구분 필요.** 이미 완료된 결제·재고 차감을 반복하는 대신, 기록을 확인해 완료되지 않은 단계만 이어서 처리 필요

복구 완료는 “서버가 켜졌다”가 아니라, 영향 주문의 금액·결제·재고·배송 상태가 맞고 신규 주문도 정상 처리되는지로 판단 필요

**12. 핵심 정리 및 구현 전 결정사항**

이미지 4장의 독립적인 역할 구분

| 이미지 | 유지해야 할 독립 주제 |
|---|---|
| 46 | 개발 → 승인 → 부분 배포 → 관찰 → 확대·롤백, 기존 주문 보존 |
| 47 | 주문별 앱·API·정책·배포 기록, 관리자·PDA 연결, 별도 정정·환불 |
| 48 | 선택 필드 호환성, 정책 경계, 동일 요청 재처리, 롤백 후 원기록, 필수 변경 차단 |
| 49 | 배포 승인 조건, 적용 시점 선택, 배포·관찰·중단 기준, DB 복구 계획 |

구현 전 팀 내 확정 필요 항목

1. **정책 확정 시점**: 주문 생성 / 결제 확정 및 중간 가격 변경 처리
2. **배포 대상 기준**: 고객 / 주문 / 센터, 비율 계산 방식
3. **관찰·중단 기준**: 시간, 최소 표본, 오류·결제·지연 지표
4. **승인 권한**: 요청·승인·실행 분리, 자기승인, 긴급 조치 범위
5. **구버전 지원 정책**: 기본 구매 허용 범위, 필수 변경 차단 범위
6. **재요청 정책**: 요청 키 범위·보존 기간·내용 불일치 처리
7. **롤백 범위**: 코드·정책·설정·DB별 복귀 방법
8. **정정·복구 절차**: 환불 승인, 데이터 보존, 복구 후 정합성 검증

이 PART의 핵심 구현 기준은 **“운영 변경은 통제하고, 각 주문에 확정된 거래 기록은 보존하며, 필요한 정정과 복구는 별도 권한·절차·이력으로 수행한다”**
