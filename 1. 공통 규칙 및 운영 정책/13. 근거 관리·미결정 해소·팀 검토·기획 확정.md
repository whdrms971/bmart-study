**PART 13. 근거·출처 관리와 팀 검토를 통한 기획 확정**  


핵심은 **주장과 근거를 연결하고, 미결정 사항과 자료 간 충돌을 추적하여 요구사항·화면·테스트에 반영하는 과정**.



아래에서 **‘원문’은 이미지에 제시된 내용**, **‘설계 보완’은 프로젝트 적용을 위해 추가한 기능·규칙·예외 처리 제안**을 의미.

---

**1. PART의 목적**

| 목적 | 관리 대상 |
|---|---|
| 주장과 사실의 구분 | 확인된 사실, 추정, 기획 제안, 확인 필요 항목 |
| 근거 추적 | 출처, 관찰 조건, 자료 버전, 확인 시점 |
| 미결정 사항 관리 | 열린 질문, 충돌하는 정책, 결정 담당자, 후속 조치 |
| 팀 검토 | 기획·고객 UX·상품·물류·결제·운영 관점의 의견 |
| 변경 영향 관리 | 요구사항, 고객 앱, 관리자 화면, PDA, 계산 로직, 테스트 |
| 기획 확정 | 결정 근거, 승인 범위, 미결 항목, 명세 버전 |
| 검증 결과 구분 | 시나리오 작성, 테스트 실행, 결과 확인 |

이 PART의 직접적인 구현 대상은 **요구사항·근거·검토·결정 이력을 관리하는 기능**. 배송비 계산이나 분할배송 자체는 여기에서 정책과 영향 범위를 정리한 뒤, 해당 업무 도메인에서 구현하는 대상.

별도의 관리 시스템 구축 여부는 프로젝트 범위에 따라 결정 가능. 문서·이슈 관리 도구를 사용하더라도 아래 정보와 연결 관계의 유지 필요.

**2. 핵심 개념**

| 개념 | 의미 | 구분 기준 |
|---|---|---|
| 주장 | 문제나 개선 방향에 관한 설명 | 근거 확인 전에는 사실로 확정 불가 |
| 근거·출처 | 주장을 뒷받침하는 문서·관찰·데이터 | 작성 주체, 버전, 적용 범위 확인 필요 |
| 관찰 조건 | 화면이나 동작을 확인한 환경 | 앱 버전, OS, 지역, 로그인 상태, 확인 시점 등 |
| 요구사항 | 구현하거나 충족해야 할 조건 | 연관 주장·근거·결정과 연결 |
| 미결정 사항 | 아직 결론이 나지 않은 질문 | 담당자, 미결 사유, 후속 조치 관리 |
| 결정 | 근거와 검토를 바탕으로 선택한 방안 | 결정자, 적용 범위, 적용 시점 기록 |
| 화면 시안 | 요구사항을 시각적으로 표현한 자료 | 실제 구현·실제 운영 확인과 구분 |
| 테스트 케이스 | 검증 조건·절차·예상 결과 | 작성만으로 검증 완료 처리 불가 |
| 변경 영향 | 정책 변경이 연결 항목에 미치는 영향 | 화면·데이터·로직·운영·테스트까지 확인 |

**상태는 관리 대상별로 분리 필요.**

| 관리 축 | 상태 예시 |
|---|---|
| 내용의 확실성 | 확인된 사실 / 추정 / 확인 필요 |
| 제안·명세 진행 | 작성 중 / 검토 중 / 확정 / 보류 |
| 결정 진행 | 미결 / 부분 확정 / 확정 |
| 검증 진행 | 미실행 / 실행 중 / 통과 / 실패 |
| 자료 용도 | 관찰 자료 / 설계 참고 / 설명용 시각 자료 |

‘기획 제안’, ‘미결’, ‘미실행’은 서로 다른 의미. 하나의 상태 필드에 혼합하면 기획 확정 여부와 검증 완료 여부의 혼동 가능.

**3. 이미지별 세부 주제**

**13-1. 근거·미결정·팀 검토 추적 — 이미지 59**

**핵심 주제**

주장 등록부터 요구사항·화면 설계·팀 검토·테스트 케이스·결과 추적까지 연결하고, 근거가 부족한 정책은 미정으로 유지하는 과정.

**원문에 제시된 단계**

| 단계 | 주요 내용 | 생성·변경 정보 |
|---|---|---|
| 주장 등록 `CLM01` | 문제와 개선 주장 등록, 제안서·외부 기사 연결 | 주장 내용, 관련 근거, 추정 상태 |
| 요구사항 작성 `REQ01` | 주장을 구체적인 요구사항으로 전환 | 제목, 요청 배경, 연관 주장, 첨부파일 |
| 화면 설계 `SCR01` | 요구사항을 화면과 정책 선택 항목으로 표현 | 화면 시안, 설계 메모, 미정 표시 |
| 팀 검토 `VIS01` | 6명의 관점에서 의견 수집 | 검토자, 의견, 검토 상태 |
| 테스트 케이스 `TC01` | 정책 표시 검증 절차 작성 | 사전조건, 절차, 예상 결과 |
| 결과 추적 | 단계별 상태와 후속 작업 확인 | 미해결 항목, 최종 결정 상태 |

원문의 테스트 예시는 **관리자 로그인 → 정책 화면 이동 → 미정 상태 표시 확인**. 예상 결과는 ‘미정’ 표시이며, 실행 결과는 없는 상태.

**근거 없는 정책의 처리**

정책값 표시  
→ 근거 존재 여부 확인  
→ 근거 미확인  
→ 기획 문서·시안의 상태를 ‘미정’으로 변경  
→ 근거 보완 요청  
→ 검토 후 결정

이미지의 배송비 2,000원은 근거 없는 확정값의 예시.

**설계 보완**

- 근거 미확인과 실제 운영 정책의 즉시 중단은 구분 필요.
- 기획 자료의 ‘미정’ 전환만으로 운영 중 배송비 설정을 자동 변경하지 않도록 분리.
- 운영 정책 변경은 별도의 영향 분석·승인·적용 절차 필요.
- 팀원 한 명의 검토 승인과 최종 정책 확정의 구분 필요.
- 근거 변경 시 연결된 요구사항·화면·테스트에 재검토 필요 표시.

**주요 예외**

| 상황 | 처리 |
|---|---|
| 주장에 근거가 없음 | 추정 또는 확인 필요 상태 유지 |
| 설계 시안의 숫자가 실제 정책으로 인용됨 | 설명용 표시, 정책 근거와 분리 |
| 검토자가 승인했으나 다른 필수 검토가 남음 | 최종 확정 보류 |
| 테스트 케이스만 작성됨 | 미실행 유지 |
| 근거가 삭제되거나 접근 불가 | 근거 확인 불가 표시, 재수집 담당자 지정 |

**13-2. 출처·관찰 조건·결정 이력 연결 — 이미지 60**

**핵심 주제**

어떤 자료를 어떤 조건에서 확인했으며, 해당 관찰이 어떤 질문과 결정으로 연결되었는지 추적하는 과정.

**원문의 자료 구분**

| 식별자 | 원문상 의미 | 현재 조건·상태 |
|---|---|---|
| `OBS01` | 관찰·캡처·원천 기록을 담는 증거대장 | 확인일·앱 버전·OS·지역·로그인 정보 부족 |
| `SRC01` | 사용자 제공 사전조사 이미지 | 실제 운영 검증 전 설계 참고 자료 |
| `CLM01` | 배송비 조건 관련 확인 이슈 | 확인 필요 |
| `DEC01` | 배송비 조건에 관한 결정 | 미결 |
| `REQ01` | 배송비 조건 확인을 위한 기획안 | 작성 중 |
| `VIS01` | 설명을 위한 시각 자료 | 설명용 |

**관찰 경로**

장바구니  
→ 주문서  
→ 배송비 노출 조건 확인

원문에서는 장바구니에서 주문서로 이동한 경로만 확인 가능하며, 동일 조건 재현에 필요한 환경 정보는 부족한 상태.

**보완해야 할 관찰 정보**

| 정보 | 필요한 이유 |
|---|---|
| 확인일·시각 | 과거 화면과 현재 정책 구분 |
| 앱 버전 | 버전별 화면·정책 차이 확인 |
| OS·단말 환경 | 플랫폼별 동작 차이 확인 |
| 지역·배송지 범위 | 지역별 배송 가능 여부·배송비 차이 확인 |
| 로그인 상태 | 회원·비회원 조건 차이 확인 |
| 주문 구성 | 상품 유형·수량·금액에 따른 조건 확인 |
| 진입 경로 | 관찰한 화면까지의 재현 절차 확보 |

**원문의 후속 조치**

1. `OBS01` 필수 정보 보완.
2. 지역·주문금액·상품 유형 등 배송비 부과 조건 확인.
3. 공식 정책 문서 또는 내부 자료 확인.
4. 동일 조건 재현을 위한 계정·환경 준비.
5. 확인 결과를 바탕으로 `DEC01` 결정 진행.
6. 결과에 따른 기획 상세화 및 개발·운영 협의.

**미실행 검증 시나리오**

| 시나리오 | 확인 대상 |
|---|---|
| A | 서로 다른 지역의 배송비 노출 조건 |
| B | 로그인·비로그인 상태에 따른 배송비 변화 |
| C | 앱 버전별 화면 및 정책 차이 |

**설계 보완**

- 관찰 환경이 다르면 동일 정책의 모순으로 바로 판정하지 않고 조건 차이부터 확인.
- 개인정보가 포함된 캡처는 마스킹 후 공유.
- 원본 자료와 해석·요약을 별도 관리.
- 자료의 최신성뿐 아니라 해당 센터·상품·고객 조건에 적용되는 자료인지 확인.

**식별자 관련 주의**

이미지 59에서는 `SCR01`이 화면 설계, `VIS01`이 팀 검토에 사용되지만 이미지 60에서는 `VIS01`이 설명용 시각 자료에 사용됨. 프로젝트에서는 이미지별 예시 ID를 그대로 통합하기보다 **자료 유형별 식별 규칙을 먼저 확정**할 필요.

**13-3. 근거 누락·충돌·변경 영향 검증 — 이미지 61**

이 이미지의 네 가지 주제는 서로 다른 검증 문제이므로 독립적인 관리 필요.

| 세부 주제 | 원문 문제 | 필요한 처리 |
|---|---|---|
| 수치 근거 누락 | 배송비 2,000원의 출처 없음 | 정책 문서·시스템 설정·계약·과거 이력 확인 |
| 자료 간 충돌 | 재고 예약 유지시간 600초와 300초가 혼재 | 적용 정책·버전·범위 확인 후 담당자 결정 |
| 가격 변경 영향 | 상품 가격 2,000원 → 2,500원 예시 | 화면·주문·환불·할인·테스트 영향 분석 |
| 시안과 실제 화면 차이 | 기획서 화면만으로 실제 구현 판단 불가 | 고객 앱·관리자·PDA·운영 화면 직접 확인 |

**① 배송비 수치의 근거 누락**

화면에 2,000원이 표시된 사실과, 2,000원이 올바른 정책값이라는 판단은 별개.

확인 대상:

- 해당 화면이 실제 운영 화면인지 설명용 시안인지.
- 적용 정책 문서와 버전.
- 실제 시스템 설정값.
- 관련 계약 조건.
- 변경·승인 이력.
- 적용 지역·고객·상품·주문 조건.

근거 확보 전에는 ‘확인 필요’ 유지.

**② 재고 예약 유지시간 충돌**

원문 예시:

- 자료 A: 운영 정책서 v1.2의 600초.
- 자료 B: 커뮤니케이션에서 합의한 300초.

자료 충돌 발견  
→ 두 자료의 작성·승인·적용 시점 확인  
→ 상품·센터·주문 유형별 적용 범위 비교  
→ 담당자 재확인  
→ 적용값 결정  
→ 관련 명세·설정·테스트 갱신

**설계 보완**

- 최신 메시지라는 이유만으로 정책서를 자동 대체하지 않도록 처리.
- 300초와 600초가 서로 다른 대상에 적용되는 값인지 우선 확인.
- 이미 생성된 예약의 만료 시각까지 변경할지 별도 결정.
- 예약 만료와 결제 성공이 동시에 발생하는 경우의 처리 정책 연결.
- 설정 변경 후 예약 해제 작업과 화면 안내가 동일 기준을 사용하는지 검증.

**③ 가격 정책 변경의 연쇄 영향**

원문에서는 변경 대상이 특정 카테고리이며 적용 시점은 미정.

| 영향 영역 | 확인 사항 |
|---|---|
| 고객 화면 | 상품 목록·상세·장바구니·주문서의 가격 표시 |
| 관리자 화면 | 가격 변경 대상·금액·적용 시점 |
| 주문 | 변경 전 생성 주문과 변경 후 주문의 금액 기준 |
| 취소·부분 환불 | 기존 결제 가격과 변경 가격 중 적용 기준 |
| 쿠폰·할인 | 할인율·할인금액·최저가 조건 영향 |
| 테스트 | 가격 노출·주문·취소·환불 회귀 검증 범위 |

**설계 보완**

- 주문 당시 상품 금액·할인·배송비·결제금액의 스냅샷 보관.
- 환불 시 현재 상품 가격을 그대로 사용하지 않고 주문 당시 거래 정보와 확정 환불 정책 참조.
- 정책 버전 및 적용 시점을 주문·환불 판단과 연결.
- 가격 변경 승인과 실제 운영 반영 완료를 구분.

**④ 시안과 실제 구현 검증**

화면 시안 완성  
→ 실제 고객 앱 확인  
→ 관리자 화면 확인  
→ PDA 확인  
→ 운영 화면 확인  
→ 정책·상태·기능 차이 기록

화면이 유사하더라도 실제 권한 검증, 상태 변경, 금액 계산의 일치 여부는 별도 확인 필요.

**13-4. 팀 검토·미결정 해소·기획 확정 — 이미지 62**

**핵심 주제**

분할배송과 배송비 재계산 문제를 여섯 가지 업무 관점에서 검토하고, 결론이 나지 않은 항목은 미결로 유지하면서 명세·화면·시험에 연결하는 과정.

**업무 관점별 검토**

| 주체 | 주요 질문 | 검토 자료·결과 |
|---|---|---|
| 기획 담당자 | 분할배송이 필요한가? 우선 시나리오는 무엇인가? | 서비스 목표, 범위, 우선순위 |
| 고객 UX 담당자 | 고객이 분할배송을 이해할 수 있는가? | 화면 흐름, 안내 문구, 메시지 |
| 상품 담당자 | 상품별 출고 가능 정보가 정확한가? | 상품 정책, 재고·출고 데이터 |
| 물류 담당자 | 여러 센터 출고가 경로·작업량에 미치는 영향은 무엇인가? | 센터 운영, 배송 경로, 작업 영향 |
| 결제 담당자 | 배송비를 어떤 기준으로 재계산할 것인가? | 과금 정책, 결제·환불 영향 |
| 운영 담당자 | 문의 증가에 어떻게 대응할 것인가? | 운영 가이드, FAQ, 클레임 사례 |

**원문의 검토 단계**

조사 담당자 지정·출처 수집  
→ 재현 조건 기록  
→ 관점별 충돌 지점 토론  
→ 결정 또는 미결 기록  
→ 명세·버전 반영  
→ 화면 시안·테스트 시나리오 연결

이미지의 시간 표시는 진행 예시이며 필수 소요 시간이나 실제 일정이 아님.

**열린 질문 `Q01`**

“분할배송 시 배송비는 어떻게 재계산하는가?”

| 결정 항목 | 미결 내용 |
|---|---|
| 적용 대상 | 전체 주문 분할인지 일부 상품 분할인지 |
| 계산 단위 | 주문 단위인지 배송 단위인지 |
| 고객 안내 | 화면·문자·이메일 안내 필요 여부 |
| 상품 데이터 | 상품별 출고 가능 신호의 정확성 |
| 운영 준비 | 운영 가이드·FAQ 작성 |
| 정책 근거 | 내부 배송비 재계산 정책 확인 |

**원문의 결정 결과**

배송비 재계산 기준에 대한 추가 정책 검토가 필요하여 **미결 유지**.

기획 명세 v0.3 예시는 일부 미결 사항을 포함하며, 화면 시안과 테스트 시나리오의 준비가 실제 구현·테스트 완료를 의미하지 않음.

**설계 보완**

- 부분 확정 시 확정 범위와 미결 범위를 항목별 분리.
- 미결 사항에 조사 담당자·결정 담당자·기한·다음 행동 지정.
- 미결 정책을 임의 기본값으로 운영에 적용하지 않도록 통제.
- 미결 항목이 남아도 진행 가능한 화면 작업과, 정책 확정이 선행되어야 하는 계산 로직을 구분.
- 운영상 이유로 분할배송이 발생한 경우 고객 추가 부담 여부도 별도 검토.

**4. 업무 주체와 권한**

이미지에는 상세 접근 권한·센터 범위·자기승인 정책이 명시되어 있지 않음. 아래는 **프로젝트 설계 보완안**.

| 주체 | 조회·작업·변경 권한 | 승인·특수 권한 | 접근 범위 |
|---|---|---|---|
| 기획 담당자 | 주장·요구사항·질문 등록, 검토 요청, 초안 수정 | 지정된 범위의 기획 승인만 허용 | 담당 프로젝트·업무 |
| 조사·관찰 담당자 | 근거 수집, 관찰 조건·재현 절차 등록 | 최종 정책 승인과 분리 | 배정된 조사 대상 |
| 고객 UX 담당자 | 화면·안내 문구 작성, UX 검토 | UX 검토 의견 확정 | 관련 서비스 화면 |
| 상품 담당자 | 상품 정책·출고 조건 검토 | 위임받은 상품 정책 범위 | 담당 상품·카테고리·센터 |
| 재고·물류 담당자 | 예약 시간·센터 출고·작업 영향 검토 | 위임받은 물류 정책 범위 | 담당 센터·물류 업무 |
| 결제 담당자 | 배송비·과금·환불 영향 검토 | 지정된 금액 정책 승인 | 결제·정산 관련 업무 |
| 운영·CS 담당자 | 문의 사례·FAQ·운영 의견 등록 | 고객 금액 정책 임의 확정 불가 | 담당 운영·고객지원 범위 |
| 승인 관리자·정책 책임자 | 근거·검토 결과 확인 | 정책 승인·반려·부분 확정 | 위임된 정책 범위 |
| 개인정보 담당자 | 캡처·첨부의 개인정보 노출 검토 | 민감자료 접근·공유 통제 | 지정된 개인정보 처리 범위 |
| 감사 담당자 | 승인·변경·접근 이력 조회 | 감사 조회 권한 | 감사 대상 범위 |
| 시스템 | 연결 누락·권한·상태·버전 검증 | 사람의 정책 결정을 임의 대행하지 않음 | 부여된 서비스 권한 |

**권한별 통제**

- **조회 권한:** 참여 프로젝트와 허용 센터·조직 범위의 자료 조회.
- **작업 권한:** 주장·근거·검토 의견·테스트 결과 등록.
- **변경 권한:** 담당 초안 수정. 확정본은 개정 버전 생성.
- **승인 권한:** 정책별로 지정된 책임자에게 부여.
- **강제 처리 권한:** 잠금 해제·담당자 재배정 등에 한정. 근거 없는 정책 확정이나 테스트 통과 조작 금지.
- **감사 조회 권한:** 업무 수정 권한과 분리.
- **긴급 접근 권한:** 사유·범위·만료 시각을 지정한 임시 권한.

배송비·환불·예약 시간 등 중요 정책은 **요청자와 최종 승인자 분리 및 자기승인 금지**를 적용하는 설계 제안. 원문에 이미 확정된 규칙으로 제시된 내용은 아님.

고객·피커·포장 담당자·배송기사 등은 정책 영향 확인이나 현장 의견 제공의 대상이 될 수 있으나, 정책 승인 권한을 자동 부여할 근거는 없음.

| 명세 갱신 실패 | 결정 기록과 명세 반영 상태를 분리하여 재처리 |
| 알림 전송 실패 | 결정 결과 유지, 알림만 재전송 |
| 연결 관계 일부 갱신 실패 | 영향 항목을 반영 대기로 표시, 누락 목록 재처리 |
| 정책 적용 실패 | 기획 승인 완료와 운영 적용 실패를 구분 |
| 테스트 환경 장애 | 기능 실패와 환경 오류를 분리하여 기록 |
| 감사 기록 저장 실패 | 중요 변경은 기록 보장 방식에 따라 보류하거나 내구성 있는 기록 후 처리 |
| 긴급 복구 필요 | 기간·범위 제한 권한 부여, 조치 후 사후 검토 |

재처리는 기존 기록 삭제가 아니라 **원래 요청·실패 원인·재시도 결과를 연결하는 방식**으로 관리.

| 화면 | 주요 기능 |
|---|---|
| 근거·출처 관리 | 자료 유형, 출처, 버전, 관찰 조건, 정보 누락 표시 |
| 주장·요구사항 상세 | 근거·결정·화면·테스트 연결 조회 |
| 미결정 목록 | 질문, 담당자, 기한, 차단 기능, 다음 행동 확인 |
| 자료 충돌 비교 | 서로 다른 값, 적용 범위·시점, 승인 상태 비교 |
| 팀 검토 | 업무 관점별 의견, 필수 검토 누락, 검토 버전 표시 |
| 결정·승인 | 확정·부분 확정·보류·반려, 사유·근거·적용 범위 입력 |
| 변경 영향 | 연결된 화면·로직·운영 문서·테스트의 갱신 현황 |
| 테스트 관리 | 시나리오와 실제 실행 결과 분리 표시 |
| 버전 이력 | 변경 전후 비교, 승인 당시 내용 조회 |
| 감사·권한 | 접근·변경·승인·긴급 접근 이력 조회 |

목록에서 우선 식별할 항목:

- 근거 없는 확정값.
- 담당자 없는 미결 질문.
- 기한이 지난 조사·검토.
- 승인 이후 변경된 명세.
- 정책 변경 후 갱신되지 않은 테스트.
- 미실행인데 완료로 표시된 검증.
- 만료되지 않은 긴급 접근 권한.

**11. 감사 이력**

| 구분 | 기록 정보 |
|---|---|
| 행위자 | 사용자 ID, 역할, 소속, 권한 범위 |
| 대상 | 주장·근거·요구사항·정책·결정·테스트 식별자 |
| 변경 | 변경 전후 값, 이전·새 버전 |
| 사유 | 변경 이유, 관련 질문·근거 |
| 승인 | 요청자, 승인자, 결과, 대상 버전, 승인 시각 |
| 적용 | 대상 센터·상품·고객 범위, 적용 예정·실제 시각 |
| 검증 | 실행자, 환경, 결과, 증적 |
| 장애 | 실패 원인, 재시도, 복구 결과 |
| 긴급 접근 | 부여자, 사용자, 사유, 범위, 만료·회수 시각 |

감사 기록은 일반 업무 수정 권한으로 덮어쓰거나 삭제할 수 없도록 분리. 잘못된 기록의 정정도 기존 이력과 연결하여 추가 기록.

**12. 핵심 정리**

| 이미지 | 독립적으로 보존해야 할 핵심 |
|---|---|
| 59 | 주장부터 요구사항·화면·검토·테스트까지 추적하고 근거 없는 확정을 방지 |

| 62 | 여섯 업무 관점의 검토를 통해 미결 질문을 관리하고 결정 내용을 명세에 반영 |

**이 PART의 산출물은 근거 목록, 관찰 기록, 미결 질문 목록, 팀 검토 의견, 결정 이력, 변경 영향 목록, 버전별 명세, 테스트 시나리오와 실행 결과.**

각 항목의 상태를 분리하고 **근거 → 요구사항 → 결정 → 구현 대상 → 검증 결과**의 연결을 유지하는 것이 핵심.
