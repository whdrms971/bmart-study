# BackOffice 비즈니스 로직 — 본사 관리·승인·통합 운영 관제 (상세)

문서 버전: 2.0 · 작성일·상세 보강일: 2026-10-21 · 상태: 기존 PMart 문서를 연결한 상세 설계안 / 운영값·공동 계약 승인 전

> **BackOffice는 본사와 운영자가 정책을 심사하고, 권한 범위에서 업무를 요청·승인하며, 여러 시스템에 남은 의무를 추적하는 업무 영역이다.** 화면에서 업무를 실행해도 주문은 OMS, 공급 결정은 SCM, CDC 수량은 WMS, 각 MFC 수량과 현장 작업은 MFC, 간선 운송은 TMS, 고객 배송·회수는 Delivery가 확정한다. BackOffice의 승인·접수·조치 기록으로 상대 원장의 성공을 대신 만들지 않는다.

**변경 이력**

- **v2.0 상세 보강 (2026-10-21):** 28개 업무의 기존 개요 뒤에 행별 입력·검토자료, 단계별 처리와 판단표, 경합/부분실행·복구 및 종결 증빙을 추가했다. 가격의 유효10분 초안 보호와 MD팀장 발의/본사 가격·영업총괄 승인, 예약시간 변경·PG불명 기존조회 절차를 구체화했다. 수용사례는 총100개이며 모두 제안·미실행이다. 신규 설계는 원정본을 대체하지 않는다. 보강 기록: `BackOffice_문서보강_20261021/검토결과.md` (원문 미보관)

### 0.1 읽는 순서와 근거

이 문서는 메뉴 목록이 아니라 **누가 어떤 근거를 확인하고, 무엇을 승인·요청하며, 상대 시스템의 어떤 결과까지 확인해야 업무가 끝나는지** 설명한다. 제1부는 공통 업무 기반, 제2부는 개요와 입력 자료·판단표·정상 순서·경합/부분실행·종결 근거를 함께 갖춘 28개 상세 기능, 제3부는 연계·수량·운영 화면·수용 사례·결정 대장, 제4부는 행별 업무 결정·승인선·발효·명령·감사와 전체 사례의 상세 계약이다. 기능은 논리적 업무 단위이며 서버·마이크로서비스·DB 개수를 뜻하지 않는다.

### 0.2 내용의 지위

- **원문 명시:** 위 문서에서 확인되는 책임·정책·제약. 원문 명시는 실제 서비스에서 검증됐다는 뜻이 아니다.
- **제안:** BackOffice의 논리 객체·상태·상세 절차·권한 모델·운영 화면·수용 사례. 이 문서 작성으로 운영 승인이나 구현이 완료되지 않는다.
- **가정:** 수량·금액·버전·날짜 사례의 설명용 입력. 운영 기본값이나 실제 사건이 아니다.
- **확인 필요:** 승인선·임계값·기한·보존기간·외부 연계·담당 서비스 등 미합의 항목. 미설정을 0·무제한·승인으로 치환하지 않는다.

고객 교환·반품 기한 등은 프로젝트 정책의 참조다. 법령·외부 서비스의 최신성이나 적법성을 이번 문서에서 별도로 검증한 것은 아니다. 실제 출시 전 정책 담당의 검토 결과와 버전을 연결한다.

### 0.3 현재 범위와 제외

**포함:** 운영자 계정·전사 역할/위임, 상품·기본가격·일반 전시의 승인, 센터·권역·운영 정책 심사, 승인함, 주문/공급/물류의 통합 조회, CS의 위임 업무, 품질·재고 차이·손실 심사, 사건 조율, 비용 근거 심사 연결, 불명 복구, 감사·교대·마감.

**현재 제외:** 프로모션·할인·쿠폰·포인트·멤버십·증정 엔진, 예정재고 고객 예약판매, 공급업체 발주/PO·공급사 포털·ASN·실제 CDC 외부 입고·매입/지급 시스템, MFC 간 재고이관, 출발 후 목적 MFC 전환·자동 CDC 반송·자동 환적/재출발, 별도 MFC용 WMS, BI 상세 구현. 교환 승인에 따른 고객 회수/후속 배송은 OMS·Delivery의 기존 범위로 유지한다.

BackOffice가 관련 증빙·결과를 보여 주는 것과 제외된 실행 기능을 새로 구현하는 것은 다르다. 향후 확장은 범위·정본·승인·실행·복구 계약을 먼저 승인한다.

### 0.4 기존 문서의 충돌을 다루는 방법

1. Commerce §1.0의 사용자 확정 **1차 할인·쿠폰 제외**를 현재 범위로 적용한다. OMS의 과거 쿠폰·할인 안분 상세는 후속/기존 거래 해석 자료이며 새 쿠폰 메뉴·권리 호출의 근거가 아니다. 실제 과거 할인 거래가 있다면 당시 불변 스냅샷으로 OMS가 판단하며 BackOffice가 기본가격 거래로 재작성하지 않는다.
2. MFC IF-06의 전사 SKU/환산 관리 역할은 **본사 등록·심사·승인 업무**로 해석한다. WMS·Commerce의 최신 기준대로 실제 공통 상품 발급/배포 서비스 배치는 미결정이다. BackOffice DB에 별도 SKU 정본을 임의 신설하지 않는다.
3. Delivery에 등장하는 외부 브랜드, 안심번호 유효시간, 연락 횟수, 층별 추가금·귀책별 지급 문구를 모두 PMart 확정 정책으로 승격하지 않는다. 현행 채택·계약·승인 근거가 없으면 참고/정책 확인으로 표시한다.
4. WMS v9.0의 신규 공동 계약은 승인 전 제안이다. 화면이 있다는 이유로 수령/손실 경합·사고 전기·원장 복구를 지원 완료로 표시하지 않는다.
5. 기존 확정 정책을 추가 결정 대장에 넣어 다시 미정으로 돌리지 않는다. 미정인 것은 담당·실행 계약과 실제 운영 입력이다. 이 문서는 다른 원본 파일을 자동 수정하지 않는다.

| 비용 | 근거 검토·이의·승인 참조와 미지급 상태 추적 | Delivery/TMS 근거, 지급은 회계/지급 담당 |
| 통합 사건 | 사건 번호·분류·총괄 담당·하위 업무·의무·교대/종결 근거 | BackOffice 사건 관리. 도메인 사고·클레임·수불은 원시스템 유지 |
| 통합 조회 | 원ID 연결·신선도·불명/불일치 표시·드릴다운 | 각 원시스템. BackOffice 조회 사본은 거래 정본 아님 |

**화면 위치와 소유권은 다르다.** SCM 승인 화면이 BackOffice 안에 있어도 승인 확정은 SCM의 같은 업무 경계에 도달해야 한다. 같은 사람이 본사 승인자와 센터 담당자 역할을 겸해도 행위별 권한·자기승인 분리·원장 소유권은 유지한다.

### 1.2 금지되는 통합 관리자 기능

- 주문 상태를 입력칸에서 `배송완료/환불완료`로 직접 바꾸는 기능.
- CDC/MFC 현물·예약·Transit 잔고를 숫자로 덮어쓰는 기능.
- TMS 배차를 고객 Delivery 배차로 복제하거나 다른 MFC 재고를 합쳐 주문을 강제 확정하는 기능.
- 타임아웃·기한 경과·알림 읽음으로 실제 인계·손실·PG 실패를 확정하는 기능.
- `관리자 강제 성공`·무근거 `검증 생략`·재고 차이를 맞추기 위한 임의 ADJ.
- 승인 없이 고객 주소 변경·새 할인·임의 보상금·반송/재출발을 실행하는 기능.

필요한 정정은 원사건을 조회하고 해당 주관 시스템의 유효 정정 명령·승인·증빙으로 처리한다. 일반 관리 권한은 이 경계를 우회하지 않는다.

`caseId`, `approvalId`, `actionRequestId` 등은 논리 필드명 제안이다. 외부 API 경로·DB 테이블·실제 발급 서비스는 미확정이다. `orderId`, 주문행, `claimId`, `paymentAttemptId`, PG 거래/취소 ID, `reservationId`, `shipmentId`, `pkgId/version`, `TRF/line/version`, `departureId`, `receiptId/line/postingVersion`, `tripId/stopId`, `executionId/commitId`는 의미가 다른 원천 식별자로 유지한다.

고객 주문 없는 CDC/MFC 작업·운송·품질 사건에 가짜 `orderId`를 만들지 않는다. 한 사건에 여러 주문/TRF가 걸리거나 한 주문이 여러 사건에 걸리는 다대다 관계를 허용한다. 같은 SKU라도 센터·LOT·단위가 다르면 별도 행이다.

### 3.1 역할별 기본 업무 [제안]

| 상품 담당/승인자 | 상품·바코드·규격·기초상품 연결 심사 | 요청자와 승인자 분리, 가격·품질 권한 별도 |

| 품질 승인자 | 영향 범위·품질 차단/해제·처분 근거 승인 | 실물 폐기 실행·수량전기·고객 환불과 분리 |

이 표는 실제 조직·인원 수를 확정하지 않는다. 역할 승인선·자기승인 예외·금액/수량 한도·대행 기간은 결정 대장에 등록한다.

### 3.2 행위 시점 검증

로그인, 목록 조회, 상세 조회, 증빙 다운로드, 개인정보 열람, 요청 제출, 승인, 실행 요청, 재처리, 내보내기는 별도 행위다. 서버는 행위마다 현재 역할·센터/업무 범위·대행 유효기간·대상 소유권·최신 상태를 확인한다. 버튼 숨김만으로 권한을 보장하지 않는다.

목록을 열 때 권한이 있어도 실행 전에 회수되면 새 명령을 차단한다. 이미 확정한 업무는 지우지 않으며 진행 결과와 다음 담당을 인계한다. 같은 사건의 승인자와 실행자가 분리돼야 하는 경우 한 계정의 역할 전환으로 자기승인을 우회하지 않는다.

### 3.3 긴급 대응

긴급 권한은 승인된 기능·대상·기간·사유 안에서만 사용한다. 임계값·추가 인증 방식·사후 검토 기한은 미결정이다. 미설정이면 광범위한 강제 변경을 허용하지 않는다. 생명·상품 안전을 위한 실제 현장 조치와 시스템상 승인·전기는 분리해 사실을 보존한다.

안전 차단은 지정된 권한과 계약으로 우선 요청할 수 있으나 **재개·품질 해제·새 출발·지급 성공을 자동 승인하지 않는다.** 이미 발생한 무허가 실제 사실은 삭제하지 않고 사고/정정 경로로 남긴다.

## 4. 승인과 실행의 공통 계약

### 4.1 승인 단위와 필수 입력

심사 대상은 `업무 종류 + 원객체/행 + 대상 범위 + 예상 버전 + 허용 행위 + 수량/금액/단위 + 조건 + 효력/만료`로 특정한다. 단순히 “이 사건 승인”이라고 전체 업무를 무제한 허용하지 않는다.

변경 전/후, 요청 사유, 정책 근거, 영향 주문·실물·운송·기존 승인, 필요한 검토자, 증빙·미확인 항목, 요청자와 승인자를 기록한다. 승인 당시 스냅샷은 보존하되 실제 실행 때의 최신 안전 제한은 다시 검사한다.

### 4.2 상태 축 [명칭 제안]

| 축 | 상태 후보 | 해석 |
|---|---|---|
| 요청 | DRAFT / SUBMITTED / WITHDRAW_REQUESTED / WITHDRAWN | 철회 요청과 실제 철회 완료 구분 |
| 심사 | REVIEW_PENDING / EVIDENCE_REQUIRED / APPROVED / PARTIALLY_APPROVED / REJECTED / EXPIRED / SUPERSEDED | APPROVED는 특정 행위 허용. 실물·원장 성공 아님 |
| 실행 | NOT_REQUESTED / VALIDATING / ACCEPTED / IN_PROGRESS / PARTIAL / APPLIED / REJECTED / UNKNOWN_RESULT | 상대 정본의 결과로 표시. 접수 ACK와 APPLIED 구분 |
| 전달 | PENDING / DELIVERED / ACKNOWLEDGED / RETRY_PENDING / FAILED | 업무 성공 이후 통지 실패도 가능 |
| 사건 | OPEN / ASSIGNED / ACTION_PENDING / MONITORING / RESOLUTION_REVIEW / CLOSED / REOPENED | 원도메인의 주문·운송 상태와 별도 |

타임아웃이면 실행 결과는 불명일 수 있다. 승인 만료는 이미 수행한 실물/거래의 취소가 아니다. 승인 철회·대상 변경이 실행과 경합하면 원시스템의 확정 순서를 조회하며 미실행 범위만 정리한다.

### 4.3 정상 승인 절차

1. 원요청·유효 버전·기결정·철회 여부와 원결과를 조회한다.
2. 요청자/승인자의 현재 권한·위임·자기승인 분리·필요 추가승인을 확인한다.
3. 대상 수량/금액·단위·센터·조건·증빙과 미해소 의무를 검사한다.
4. 승인 당시와 현재의 차이를 비교한다. 심사 결론에 영향을 주는 변화가 있으면 재심사한다.
5. 승인/부분승인/반려·근거·조건·미승인 잔량을 원도메인 계약에 맞게 확정한다.
6. 실제 실행은 원ID·승인 참조·예상 버전으로 해당 주관 시스템에 요청한다.
7. 실행의 성공/부분/실패/불명을 수신자별로 확인하고 남은 의무를 생성한다.
8. 실제 반영·대상/잔량·통지·후속 담당이 설명될 때 그 단계만 완료한다.

BackOffice 공통 승인함은 심사 흐름을 제공한다. SCM·OMS 등에 이미 승인 정본이 있으면 **원승인 ID를 확정 결과로 연결**하며, 공통 승인함에 별도 효력 있는 복제 승인을 만들지 않는다. 두 시스템의 저장을 한 DB 원자성으로 가정하지 않는다.

### 4.4 부분 집행의 보존

동일 승인행·단위에서 `승인량 = 누적 유효 집행량 + 승인된 미집행 취소량 + 열린 집행 잔량`을 유지한다. 실행된 양을 승인 철회로 없애지 않는다. 재심사로 변경된 허용량은 새 버전과 원승인 계보를 남긴다.

가정: 폐기 승인 5개 중 실제 3개가 확정됐다면 미실행은 2개다. 응답 유실 후 새 승인 5개를 만들거나 남은 2개를 원결과 조회 없이 실행하지 않는다. 이후 실물 1개가 발견되거나 처분 근거가 바뀌면 승인 잔량 2개를 재심사한다.

## 5. 통합 조회·사건·원천 신뢰

### 5.1 조회가 표시해야 할 정보

원천 시스템·센터/대상·원ID·원버전, 업무 발생시각 `occurredAt`, 원장 전기시각 `postedAt`, 수신/조회시각, 정정 버전, 마지막 확인 결과, 데이터 신선도, 직접 확인/사본/불명 여부를 함께 제공한다. 필드가 없으면 미제공으로 표시한다.

조회 실패를 0원·0재고·정상·실패·완료로 바꾸지 않는다. 원천별 기준시각이 다른 수량을 단순 합산하지 않는다. 예를 들어 MFC가 받은 10개와 아직 대사 전인 CDC Transit 10개는 같은 실물일 수 있으므로 원수령 연결 없이 전사 재고 20개로 발표하지 않는다.

### 5.2 사건을 나누는 기준

하나의 온도 사고가 품질 차단, 미수령 조사, 고객 클레임, 수행료 이의, 재고 정정 등 여러 의무를 만들 수 있다. 총괄 사건과 하위 사건을 연결하고 각각의 담당·대상·완료 근거를 둔다. 원인이 같다는 이유로 서로 다른 주문·원수령을 병합 전기하지 않는다.

동일 신고의 재접수는 기존 사건에 연결한다. 실제 다른 발생·다른 포장·새 피해는 같은 문구라도 별도 의무다. 중복 판정이 불명확하면 병합 후보로 두고 자동 삭제하지 않는다. 사건 병합/분리는 원ID와 기존 조치를 보존한다.

### 5.3 우선순위와 종결

안전·리콜/품질, 진행 실물의 보관 책임, 결제/인계 불명, 고객 약속·시간창, 장기 미완료와 데이터 지연을 구별해 정렬한다. 실제 등급·상신 시간·SLA는 승인 입력이다. 미등록이면 임의의 “30분 자동 종결” 등을 도입하지 않는다.

사건 전체 종결에는 영향 대상, 실제 사실, 승인/집행 결과, 수량·금액 대사, 실물 위치/보관 책임, 고객 대응, 외부 전달과 남은 의무의 인수 근거가 필요하다. 다른 담당에게 넘긴 의무는 **이관 완료/상대 처리 중**으로 표시하며 해결 완료로 위장하지 않는다. 늦은 원사실이 종결 근거를 바꾸면 새 이력으로 재개한다.

## 제2부 — 상세 비즈니스 로직

<a id="bo-01"></a>

## BO-01. 운영자 등록·권한 부여·회수

**목적·입력:** 신규 근무·인사 이동·퇴사·업무 변경 시 사내 신원, 소속/센터, 요청 역할·행위, 기간, 승인자·근거를 받아 접근 범위를 정한다. 고객 소셜 계정을 운영자 계정으로 자동 승격하지 않는다.

**정상 처리:** 중복 신원/휴면·퇴사 여부 확인 → 요청 범위와 승인자의 위임 가능 범위 비교 → 자기승인·역할 충돌 심사 → 유효 grant와 시작/종료 확정 → 대상 시스템의 권한 반영 확인 → 운영자에게 사용 가능 범위 안내 순이다. 전사 조회와 재고/환불 승인·개인정보 다운로드를 하나의 역할로 묶지 않는다.

**회수·예외:** 센터 A→B 이동이면 A 권한 종료와 B 권한 시작을 별도 추적한다. A의 진행 사건은 후임 인수 전 삭제하지 않는다. 권한 회수 통지가 MFC에 실패하면 “전체 회수 완료”가 아니라 미반영 대상을 표시하고 해당 시스템의 최신 권한 확인·실행 차단 계약으로 복구한다. 퇴사 계정의 과거 감사 행위자는 유지한다.

**완료:** 승인된 접근 범위·기간, 실제 반영/미반영 대상, 진행 업무 인계와 접근 이력이 연결돼야 한다. 전파 지연 중 권한을 계속 사용할 수 있는지 불명확하면 영향 변경 행위를 보류하고 기술 담당에 상신한다.

### 1) 권한 요청서의 행 단위

| 입력 | 검증과 사용 목적 |
|---|---|
| 사내 신원·고용/계약 상태 | 실제 근무자와 연결하고 퇴사/종료·중복 계정을 확인한다. 인사 연계 서비스 배치는 미결정이다. |
| 역할·업무·센터 집합 | `센터A 조회`와 `센터A 조정 요청`, `전센터 조회`를 분리한다. 이름이 비슷한 역할을 합치지 않는다. |
| 허용 행위·대상 필드 | 주문 조회·주소 원문·증빙 열람·승인·복구·파일 반출을 각각 승인한다. |
| 시작·종료·신청 근거 | 효력 전 접근을 막고 종료 뒤 신규 행위를 막는다. 기간 없는 신청의 허용 여부는 승인 정책이 필요하다. |
| 요청자·직속/업무 승인자 | 요청·심사·최종 부여의 사람과 위임 범위를 연결한다. |

### 2) 등록·변경·회수의 상세 순서

1. 신원 조회로 기존 계정·기존 권한을 찾는다. 기존 계정이 있으면 새 운영자 ID 대신 변경 요청으로 진행한다.
2. 신청 권한과 현재 권한의 차집합을 계산해 추가·유지·종료 대상을 보여 준다. 조회 권한 추가에 승인/다운로드 권한이 따라오지 않는다.
3. 센터 담당의 범위 확인과 업무 승인자의 권한 충돌 심사를 수행한다. 인사상 상사라는 이유만으로 품질·PG 실행 권한을 줄 수는 없다.
4. 승인한 권한행만 유효 grant로 확정한다. 거절/보완행은 승인행과 별도 사유를 갖는다.
5. 필요한 시스템에 원grant/버전·효력·회수 결과를 전달하고 대상별 검증·반영을 확인한다.
6. 접근 시 중앙/로컬 계약에 따라 현재 grant와 대상 범위를 재검증한다. 로컬 반영 지연을 캐시 영구 허용으로 처리하지 않는다.
7. 회수 시 활성 세션·예약된 대량작업·진행 승인/사건을 목록화한다. 새 실행을 막고 확정 결과/보관 책임은 후임에게 넘긴다.
8. 역할 변경의 감사 기록과 수신 시스템별 잔여 조치를 확인해 요청을 정리한다.

### 3) 경계 사례와 판정

| 상황 | 판정 | 운영자가 할 일 |
|---|---|---|
| A센터 권한을 B센터로 이전 | A 종료/B 시작을 구분 | A 미결 인수자를 지정하고 B 범위를 별도 승인 |
| 전사 조회 승인, 개인정보 원문은 미승인 | 전사 현황만 마스킹 조회 | 필요한 원문 열람은 사건/목적을 붙여 추가 요청 |
| 퇴사 회수는 확정, MFC 통지 불명 | 권한 상태 회수/전파 불명 | 원grant 조회·반영/세션 차단 상태 확인, 새 권한 생성 금지 |
| 같은 직원이 승인자 역할도 신청 | 역할 충돌 검토 | 자기 요청·자기 승인/실행 분리 규칙 유지 |

### 4) 저장 결과와 종결 근거

권한행마다 `신청 범위/승인 범위/현재 유효 범위`, 승인자·전후 grant·효력·수신자 결과를 남긴다. 실제 차단/전파를 확인하지 못한 대상은 열린 의무로 유지한다. 계정을 삭제해 과거 주문 조회·승인·금액/수량 변경의 행위자 이력을 잃지 않는다.

<a id="bo-02"></a>

## BO-02. 대행·교대·긴급 권한

**입력·조건:** 원권한자/대행자, 업무·센터·대상 범위, 유효기간, 원승인 근거·긴급 사유를 받는다. 대행자가 원권한자의 비밀번호·세션을 공유하지 않는다.

**처리:** 원권한 유효성·재위임 허용 여부 확인 → 동일 요청의 요청자/승인자 충돌 검사 → 기간/행위 한정 위임 → 각 명령에 실제 행위자와 대행 근거 저장 → 종료 시 신규 실행 차단·진행 결과 인계 순이다. 대행기간이 끝나도 이미 확정한 승인/원장 기록은 보존한다.

**예외·복구:** 만료 직전 제출한 명령이 응답불명이면 대행권을 연장해 새 명령을 만드는 대신 원요청을 조회한다. 후임은 현재 권한과 원잔량을 검증한 뒤 미실행분만 이어받는다. 긴급권한 발급 실패는 관리자 계정 공유로 우회하지 않는다.

**완료:** 원권한·대행·실행·미결 인수·만료가 설명되고 사후 검토 대상이 남는다. 긴급권한의 구체 한도와 승인선은 미설정 시 실행 권한으로 사용하지 않는다.

### 1) 대행을 허용할 범위

대행은 원권한 전체 복사가 아니라 `허용 업무×센터×행위×대상×유효기간`의 교집합이다. 원승인자가 공급 승인만 할 수 있으면 대행자에게 품질 해제·PG 취소 권한을 줄 수 없다. 재위임 허용 여부와 긴급 발급 승인선은 정책이 등록돼야 한다.

### 2) 대행 개시부터 종료까지

1. 원권한자의 현재 유효 범위와 부재/교대 사유를 확인한다.
2. 대행자의 독립 신원·근무·직무 충돌을 확인한다. 원권한자 계정으로 로그인하지 않는다.
3. 대행 허용 대상과 요청자 분리·추가승인 제한을 검증한다.
4. 위임 ID·기간·최대 범위를 승인하고 수신 대상 반영을 확인한다.
5. 실제 승인/명령에는 대행자의 행위자 ID와 원위임 ID를 모두 기록한다.
6. 종료 때 신규 승인·예약 실행을 차단하고 진행 요청의 원결과를 조회한다.
7. 후임이 원승인/잔량·실물/금전·미결을 수락한 뒤 인수 완료로 표시한다.

### 3) 만료·회수·응답불명 분기

| 상태 | 허용 조치 | 차단할 조치 |
|---|---|---|
| 유효기간 안, 실행 전 | 현권한/대상 재검증 후 제출 | 위임 범위 초과 승인 |
| 만료 뒤, 이미 승인 저장됨 | 원승인 조회·실행 책임자 인계 | 승인시각을 소급 수정 |
| 만료 뒤, 상대 실행 불명 | 원요청 조회·담당 상신 | 새 대행 ID로 같은 물리/금전 명령 반복 |
| 긴급 안전차단 필요 | 지정된 안전 역할/계약의 제한 요청 | 품질 해제·재출발·환불 성공까지 긴급 권한으로 합성 |

### 4) 수용 사례

가정: 대행이 18:00 종료이고 17:59 제출한 손실 승인 응답이 18:01 도착한다. 서버가 17:59에 확정했는지, 접수만 했고 승인 미확정인지 원결과로 구분한다. 접수시각만으로 승인 효력을 소급 인정하지 않는다. 확정 결과가 있으면 보존하고 미실행/불명 의무는 현재 권한자에게 넘긴다.

## BO-03. 상품·SKU·바코드·환산 기준 승인

**입력:** 기초상품 연결, E/B 구분, 판매단위·구성 낱개 수, 제조사/바코드, 규격·중량, 보관조건, 상품군·기한 근거, 변경 전/후와 증빙을 받는다. 발급 서비스의 배치는 결정 대장 항목이다.

**정상 처리:** 동일 실물/기존 SKU 검색 → 상품 담당·품질/물류 담당 검토 → 바코드 중복·단위/규격·중량 누락 검사 → 유효 상품안 승인 → 공통 마스터 담당에 원승인으로 반영 요청 → SKU/마스터 버전 결과 확인 → WMS/MFC/Commerce/OMS/SCM 등 필요한 수신자 반영 추적 순이다.

**식별 규칙:** E-/B-는 **전역 공유 8자리 일련번호**를 사용한다. 가정: E-00000001 다음 B 상품은 B-00000002이며 B-00000001을 따로 발급하지 않는다. B 밀봉 6입 1팩과 E 낱개 6개는 독립 SKU·재고이고 E↔B 변환은 초기 미지원이다. BOX/PLT는 물류 취급 단위이며 별도 판매 SKU로 자동 생성하지 않는다.

**변경 판단:** 오탈자와 실제 규격·판매단위 변경을 구분한다. 기존 SKU 유지/신규 발급은 마스터의 승인된 동일성 규칙으로 판단하며 임의 기준을 추가하지 않는다. 변경이 과거 주문 스냅샷·출발 매니페스트·확정 수불을 덮어쓰지 않는다.

**예외·복구:** 바코드 하나가 같은 조건에서 두 SKU를 가리키면 자동 선택하지 않고 충돌 심사한다. 승인 성공/검색 갱신 실패는 검색만 복구하며 새 SKU를 발급하지 않는다. 마스터 반영 불명은 원승인·원발급 결과를 조회한다. 미등록 단위나 중량은 0으로 채우지 않고 영향 판매/운송 적격을 보류한다.

**완료:** 승인안·실제 발급/변경 버전·각 수신자 반영과 미결이 연결된다. 상품 비활성은 현물 삭제·기존 주문 취소가 아니며 잔여 재고·진행 작업·고객 약속을 담당 영역에 연결한다.

### 1) 상품 등록에서 반드시 구별할 데이터

| 데이터 | 뜻과 확인 자료 | 잘못됐을 때 영향 |
|---|---|---|
| 기초상품 ID·판매 SKU | 같은 기초상품의 E/B 구매 상한 연결과 독립 실물 식별 | 구성 상한 우회·센터별 중복 SKU 발생 |
| 판매단위·구성 낱개 수 | E는 개, B는 밀봉팩 등. 상품 포장 원문·실물 규격 근거 | B1팩을 낱개 수만큼 과다 가격계산/재고 차감 |
| 제조사 바코드 매핑 | 스캔 조건과 유효기간·대상 SKU | 같은 스캔이 둘을 지칭하면 오피킹 |
| 상품 중량/규격 | 단위·포장 포함 범위·확인 출처 | 주문 중량 분할·차량/선반 적격 판단 불가 |
| 보관/상품군·기한 근거 | 품질 책임자가 검토할 실제 상품 조건 | 신선/가공 기한 공식·취급 규칙 오적용 |
| 물류 BOX/PLT 환산 | 같은 SKU의 포장 수량·유효 버전·승인 근거 | 상하위 중복 계수·총량 부풀림 |

### 2) 등록·변경의 상세 결정

1. MD 담당이 실물과 원자료를 대조해 등록/변경안을 제출한다. 비슷한 이름만으로 동일 SKU라고 결론 내리지 않는다.
2. 상품 담당은 기존 기초상품/SKU/바코드·폐기된 식별자의 이력을 조회한다.
3. 가격·품질·물류에서 검토해야 할 변경 항목을 분류하고 검토 결과를 요청행에 연결한다.
4. 오탈자 변경과 규격/포장/구성/판매단위 변경을 구분한다. 동일 SKU 유지/신규 발급 기준이 미승인인 변경은 보완 대기다.
5. 전역 일련번호·바코드 충돌·단위/중량/보관조건의 필수 근거를 검증한다.
6. 승인 범위/효력·마스터 발행요청을 확정하고 실제 마스터가 반환한 SKU/버전을 연결한다.
7. WMS·MFC의 기존 현물/작업, OMS의 진행 주문, Commerce 표시의 변경 영향을 확인한다.
8. 수신자별 반영 실패는 원승인/원발행으로 복구하고 상품/재고를 새로 생성하지 않는다.

### 3) 환산 검토 사례 [가정]

같은 E SKU에 1BOX=5개, 1PLT=6BOX이면 1PLT=30개다. 2PLT+3BOX는 60+15=75개이며 직접 PLT→개 경로와 PLT→BOX→개 경로를 더해150개로 만들지 않는다. 환산 승인으로 현재 현물을75개 늘리는 것도 아니다.

B5입 상품3팩은 재고 단위 B3팩·구성 낱개15개다. 가격은 승인 B팩 단가×3, 재고는 B3을 사용한다. E15 재고로 전환하거나 E와 B의 서로 다른 기본단가를 수량 할인 엔진으로 해석하지 않는다.

### 4) 비활성·단종·수정의 후속 업무

신규 판매 중지, 단종 계획, 마스터 오류 정정은 구별한다. 남은 현물·입고 예정·원예약·진행 주문·운송 화물과 과거 거래를 각각 확인한다. 단종을 이유로 예약 해제·전량 폐기·고객 주문 취소를 일괄 실행하지 않는다. 품질 이슈면 BO-15의 최신 제한을 즉시 연결한다.

### 5) 종결 증빙

요청안/검토 항목·승인안, 실제 마스터 발급/변경 결과, 전역 SKU/버전, 단위·바코드/환산 검증, 영향 진행분·수신자 반영과 잔여 담당이 있어야 한다. 발급 서비스 배치 미확정 상태에서는 등록안을 준비할 수 있지만 임의로 새 실행 정본을 만들지 않는다.

## BO-04. 기본 판매가격·구매 조건의 변경 승인

**입력·범위:** SKU별 기본단가, 통화/원 단위, 효력 시각, 변경 사유, 승인 정책과 영향 상품을 받는다. 초기 전사 동일 승인 기본가격을 유지하며 센터별 할인·쿠폰·행사가를 새로 만들지 않는다.

**처리:** 현행/예약 가격 버전 조회 → 기간 겹침·무효 SKU·단위 충돌·필수값 검사 → 가격 책임자 승인 → 가격 실행 담당에 반영 요청 → Commerce 표시와 OMS 견적/확정 참조 버전 확인 → 미반영 수신자 복구 순이다. 실제 가격 정본과 발효를 판정할 서비스는 구현 전 확정한다.

**진행 구매:** 장바구니/견적과 확정 주문을 분리한다. 발효 후 신규/만료 견적에는 변경 전/후와 재동의 필요를 OMS/Commerce 결과로 제공한다. 원초안 생성부터 유효한10분 안의 일반 가격은 유지하며 단순히 미확정 주문이라는 이유로 새 가격을 소급하지 않는다. PG 진행·불명인 원시도는 원거래 확인을 우선하며 금액을 몰래 변경하거나 새 결제를 시작하지 않는다. 확정 주문은 당시 가격을 유지한다.

**기존 확정 조건:** 최소 상품액 15,000원, 한집 배달팁 4,000원·알뜰/예약 3,000원, 상품액 30,000원 이상 또는 첫 구매 무료, 봉투 100원 주문당 1회라는 현재 문서 기준을 소비한다. 첫 구매 자격은 OMS의 동시 확보/이력 판정을 사용한다. BackOffice 승인 화면이 금액을 따로 계산해 OMS 확정액을 덮지 않는다.

**예외·완료:** 반영 일부 실패는 `승인됨/일부 적용`으로 표시한다. 과거 정책으로 되돌릴 때도 새 효력 버전으로 승인하며 원주문 가격을 소급 변경하지 않는다. 승인·발효·견적/노출 반영·미결이 대사될 때 완료다. 무료/0원 가격 허용 여부 등 미정 값은 임의 채택하지 않는다.

### 1) 가격 승인자가 보는 자료

원문 Commerce §8.1의 **MD 팀장 발의→본사 가격/영업 총괄 승인**을 유지한다. 기존 승인 기본단가·신규 단가·변경률/근거, SKU 판매단위, 전사 적용/효력시각, 동시 예약 가격·진행 견적·원주문 영향, 필수 검토 결과를 비교한다. 새로운 이익률·최저가·판매 마진 자동 반려 기준은 별도 원가/정책 근거 없이 도입하지 않는다.

### 2) 가격안의 처리 순서

1. 승인 SKU와 판매단위·전사 동일 가격 원칙을 확인한다. B팩의 구성 낱개 수로 단가를 다시 곱하지 않는다.
2. 현재/예약 가격의 유효기간을 조회해 겹침과 공백·미등록0원·음수·단위 오류를 검사한다.
3. 발의자가 변경 근거와 효력/대상 집합을 고정하고 승인자가 같은 버전을 심사한다.
4. 승인 후 가격 실행 담당이 새 가격 버전을 반영한다. 발송·예약·효력 도달·실제 적용을 구분한다.
5. Commerce의 현재 표시·장바구니 견적과 OMS 원초안/PG의 가격 참조를 대조한다.
6. 미반영 대상만 원승인으로 복구한다. 이미 확정된 주문 금액은 유지한다.

### 3) 가격 변경 시점별 판정

| 구매 단계 | 새 기본가격의 영향 | 운영자가 확인할 것 |
|---|---|---|
| 상품 카드/장바구니 참고값 | 현재 유효가격 재조회 | 표시 버전·SKU/수량·고객 주소 조건 |
| OMS 원초안의 유효10분 안 | 일반 가격 변경을 소급하지 않음 | 초안 생성·가격 만료·현재 품질/권한 제한 |
| 원초안10분 경과·PG 진입 전 | 최신 견적·고객 재확인 | 새 견적 동의·재고/슬롯 별도 유효성 |
| PG 진행/결과불명 | 원시도 금액으로 결과 조회 | 새로운 가격/새 결제 자동 생성 차단 |
| 주문 확정 후 | 원주문 가격 보존 | 부분품절/반품도 원가격으로 OMS 판단 |

가정: 10:00 생성한 초안에 10:05 가격이 바뀌어도 유효 구간의 원가격은 유지한다. 정확한 만료 경계·서버 시각과 PG 진행 상태는 OMS 원초안의 계약으로 판단한다. 안전/리콜 차단은 가격 동결과 관계없이 최신 기준을 적용한다.

### 4) 구매 조건 검토용 수치

| 조건 [원문 기준/가정 입력] | OMS 견적의 기대 결과 |
|---|---|
| 재구매·알뜰·상품16,000원 | 16,000+3,000+100=19,100원 |
| 한집·상품30,000원 | 무료배달 조건 충족,30,100원 |
| 첫 구매·한집·상품15,000원 | 첫 구매 자격확보 성공 시15,100원 |
| 상품14,500원·배달팁 포함은15,000원 이상 | 상품액 기준 미달,PG 진입 불가 |

이 표는 승인 가격/견적을 대사하기 위한 것이며 BackOffice에 별도 주문 계산 원장을 만들라는 요구가 아니다. 첫 구매 동시 확보·취소 후 복구도 OMS 원결과를 사용한다.

## BO-05. 일반 전시·콘텐츠·판매 제한의 연결

**입력:** 일반 배너·상품 테마·분류·노출 순서·문구/이미지·링크·대상 SKU·노출 기간을 받는다. 프로모션·할인·증정 전시는 현재 제외한다. 공통 상품의 취급/품질 속성과 고객용 설명을 구별한다.

**정상 처리:** 대상/기간·승인 상품/현재 제한 확인 → 문구·표시 근거와 링크 검수 → 권한자 게시 승인 → Commerce 전시 반영 요청 → 실제 노출 버전 확인 순이다. 여러 테마에 같은 SKU를 보여도 상품·재고가 복제되지 않는다.

**예외:** 배너 파일 실패는 배너만 보류하고 정상 상품 전체를 중단하지 않는다. 반대로 품질·리콜 차단은 전시 사본 갱신을 기다려 신규 구매를 허용하지 않는다. 검색 노출과 실제 구매 가능성은 Commerce/OMS의 최신 검증을 따른다. 미확인 “신선 보장/최저가” 문구를 임의 추가하지 않는다.

**완료:** 승인 콘텐츠와 실제 게시 버전·대상/기간·미반영이 연결된다. 리뷰 숨김/제재 기능이 필요하면 실제 도입 범위·사유/소명 정책을 먼저 승인하며 부정적 리뷰만으로 자동 삭제·라이더 제재하지 않는다.

### 1) 콘텐츠의 종류별 관리

| 종류 | 입력·검수 | 실제 반영 |
|---|---|---|
| 홈 일반 배너·상품 테마 | 제목/본문·이미지·접근성 설명·연결 대상·기간·대상 채널 | Commerce 게시 결과 |
| 카테고리/상품 배치 | 승인 상품 연결·중복/비취급·노출 순서·분류 근거 | Commerce 전시/검색 사본 |
| 상품 설명 정정 | 고객 설명인지 공통 규격/취급 변경인지 분류 | 규격 변경이면 공통 마스터 승인 선행 |
| 운영 공지·휴점 안내 | 대상 센터/권역·기간·원제한/승인 참조 | 공지는 제한 정본을 대신하지 않음 |
| 리뷰 관련 신고 | 실제 도입 기능·사유·증빙·소명 정책 확인 | 승인된 경우만 처리,새 검열 정책 자동 도입 없음 |

### 2) 게시·예약·철회의 처리

초안 작성→기본 형식/링크·상품 적격 검사→표현 근거/기간·권한 검토→확정 게시 버전 승인→Commerce 예약/게시 요청→실제 채널별 반영 확인→기간 종료/철회 반영을 추적한다. 이미 게시한 버전을 수정하면 새 버전과 전후 비교를 남긴다. 수정 중인 초안이 즉시 고객 노출을 바꾸지 않는다.

### 3) 제한·실패의 영향 범위

할인율·쿠폰·기간 특가·증정이 포함된 안은 현재 1차 범위에서 게시하지 않는다. 단순 이미지 오류·링크 오류는 해당 콘텐츠만 보류/대체하며 정상 주문 전체를 중지하지 않는다. 리콜·판매중지는 원정본에서 차단하고 관련 카드/배너의 노출도 복구한다. 게시 성공은 구매가능 승인이나 상품 마스터 변경 성공이 아니다.

### 4) 검수·종결

운영자는 실제 게시 화면/조회 결과에서 채널·대상·문구·기간·가격 안내·연결 버전을 확인한다. 고객에게 제공할 약속의 근거가 없는 문구는 승인하지 않는다. 철회 뒤에도 과거 게시안·승인·대상/실제 노출 근거를 남기고 알림/검색 갱신의 잔여 의무를 확인한다.

## BO-06. 센터 기준정보·취급·영업 캘린더 관리

**입력:** CDC/MFC 식별, 운영 주체·주소/위치 근거, 센터별 취급 SKU, 영업일/휴무, 고객 접수·현장 준비·수령·검수/적치·배송 가능 창의 변경안을 받는다. 고객 영업시간과 간선 하차·상품 사용준비 시각은 다르다.

**처리:** 센터 중복/폐점 이력과 유효기간 확인 → 현장·Delivery/TMS·SCM 영향 검토 → 담당 승인 → 해당 운영 정본 반영 요청 → 신규 주문/슬롯/공급/운송에 필요한 수신자별 적용 확인 순이다. 본사 센터 등록이 MFC 현장 용량·LOC 생성·작업 가능을 자동 확정하지 않는다.

**기존 약속:** 휴점·폐점 예정 시 미인계 주문·고객 회수품·입고 예정·운송 중 화물·미결 금액을 목록화한다. 기존 약속을 삭제하거나 타 MFC로 자동 재배정하지 않는다. 새 영업일 설정도 과거 주문의 약속시간을 바꾸지 않는다.

**불명·완료:** 주소/층별 반입/수령창이 불명인 센터는 해당 신규 실행을 보류한다. 조사자료의 26곳을 모두 검증된 공급 센터로 활성화하지 않는다. 승인안·로컬 운영 반영·기존 의무 인계가 설명돼야 변경이 완료된다.

### 1) 센터 정보의 심사 단위

센터 코드·명칭/유형, 실제 주소/위치 출처·현장 검증, 운영 주체, 취급 SKU/온도대, 개점·휴점·폐점 효력, 고객 주문 접수창·현장 준비창·간선 수령/검수창·사용준비 시각을 구분한다. 면적·인력·도크 수·수령 상한은 검증 자료/승인 버전이 있어야 실행 입력으로 사용한다.

### 2) 개점·취급 확장·시간 변경

1. 본사 등록안과 기존 센터/코드 이력을 대조한다. 이름만 바뀌었다고 새 센터 재고를 생성하지 않는다.
2. 현장 담당이 실제 주소·설비·접근/반입·시간별 작업 가능성을 확인한다.
3. Delivery는 고객 권역/운영 가능,TMS는 실제 반입·차량/하차창,SCM은 공급 조건을 검토한다.
4. MFC가 현장 운영·여력/슬롯·취급의 실행 설정을 확정하고 원결과를 제공한다.
5. 본사 승인/원정본 반영·수신자 준비가 충족된 범위만 신규 서비스에 적용한다.
6. 실제 서비스 가능 판정과 미충족 항목을 확인하고 미반영 담당을 지정한다.

### 3) 휴점/폐점 때 반드시 남기는 의무

| 진행 항목 | 담당에게 연결할 판단 |
|---|---|
| 결제 완료·미인계 주문 | OMS 약속/취소 가능·MFC 실물/중지·Payment 결과 |
| 라이더 인수 뒤 배송/회수 | Delivery 안전 수행·MFC 반납 수령 가능성 |
| CDC 기출발·MFC 입고 예정 | TMS 실화물·수령/보관 책임·SCM 영향 |
| MFC 현물/예약/격리·실사 미결 | 자기센터 MFC 원장·품질/처분/보관 담당 |
| 환불/기사비·사건·미전달 | 원거래/지급 담당·고객 안내·후임 인수 |

센터 운영을 닫는 것과 이 의무를 끝내는 것은 다르다. MFC간 이관·타센터 자동 재배정·CDC 반송을 폐점 처리의 기본 실행으로 만들지 않는다. 미지원 이동이 필요하면 별도 범위/실행 계약을 심사한다.

### 4) 사례

가정: 18:00 신규 접수 중지/20:00 현장 종료인데 19:00 간선 도착예정과 고객 회수1건이 있다. 접수중지를 이유로 둘을 취소 완료로 만들지 않는다. 실제 인수 가능한 창·현장 인력·상품 보관·후속 담당을 확인하고 불가한 경우 관련 주관자에게 미결을 상신한다.

<a id="bo-07"></a>

## BO-07. 고객 배송 권역·담당 MFC 매핑 승인

**입력·책임:** 고객 배송 권역의 검증 가능한 경계/주소 판정 근거, 담당 MFC, 유효기간, 중첩 우선순위, 배송 방식·시간 조건을 받는다. 본사 운영이 승인하고 Delivery가 실행 정본/조회 계약을 제공한다. 실제 마스터 서비스 배치는 미결정이다.

**처리:** 경계/좌표 근거·중첩·빈 구간 검토 → MFC 처리 여력·Delivery 운영 가능성과 영향 주문 확인 → 승인 → Delivery 반영 요청 → 시험 주소의 승인된 기대 판정과 실제 조회 비교 → Commerce/OMS에 유효 버전 제공 순이다. 실제 도로/주소 데이터의 품질 기준과 검증 절차는 담당 계약에 둔다.

**변경 경계:** 새 주소록 선택은 Commerce, 주문 당시 MFC/주소/매핑 버전 고정은 OMS다. 권역 변경으로 기존 결제 주문을 다른 MFC로 옮기지 않는다. 결제 후 주소·연락처·요청사항 변경 금지도 유지한다.

**예외·완료:** 중첩인데 우선순위가 없거나 매핑 조회가 불명이면 신규 구매를 확인 대기로 둔다. 가장 가까운 센터나 재고 많은 센터를 임의 선택하지 않는다. 이전 지도 캐시로 신규 주문을 강행하지 않는다. 승인 경계·Delivery 반영·Commerce/OMS 소비와 미결 주소가 확인되면 완료다.

### 1) 매핑 버전의 필수 내용

대상 주소/경계·좌표/정규화 출처, 고객 배송 가능 범위, 담당 MFC, 배송 방식·유효기간, 중첩 우선순위·경계주소의 판정 근거, 검토/승인자·이전 버전을 둔다. 라이더 활동 권역,간선 MFC 공급망,고객 서비스 권역은 같은 데이터가 아니다.

### 2) 승인 전 비교와 발효

1. 기존/신규 경계의 추가·삭제·담당 변경 주소 집합을 비교한다.
2. MFC 취급·운영/준비 여력과 Delivery의 실제 서비스 가능 조건을 확인한다.
3. 겹침·빈 구간·정확도 부족·변환 오류를 구분하고 모호한 주소는 보완 대상으로 남긴다.
4. 본사 운영 책임자가 범위·효력·중첩 규칙을 승인한다.
5. Delivery의 매핑 실행 정본에 반영하고 승인된 대표/경계 주소로 기대 결과와 실제 조회를 비교한다.
6. Commerce/OMS 소비 버전과 영향 신규 구매의 판정 결과를 확인한다.

### 3) 요청 단계별 적용

| 단계 | 판정 |
|---|---|
| 주소 저장 | Commerce의 주소록 처리. 저장 성공으로 배송 가능을 선언하지 않음 |
| 쇼핑 주소 선택 | 최신 승인 매핑·MFC/Delivery 운영 결과로 현재 가능성 조회 |
| 원초안/주문 확정 | OMS가 유효 매핑·지정센터·자원 결과를 검사하고 원조건 보존 |
| 결제 이후 | 권역 변경으로 원주소·담당MFC를 바꾸지 않음 |
| 매핑 조회 불명 | 영향 신규 구매만 확인 대기,기존 주문 조회/후속 처리 유지 |

### 4) 중첩 사례와 복구

가정: 같은 주소가 MFC A/B의 경계에 걸리고 우선 규칙이 없다. A재고가 많거나 고객과 가깝다는 이유로 임의 지정하지 않는다. 본사 보완 결정→Delivery 새 버전→원주소 조회 검증 후 신규 적용한다. 배포가 일부 실패하면 성공 소비자의 결과를 지우지 않고 미반영 범위를 추적한다.

<a id="bo-08"></a>

## BO-08. 운영 중지·안전 차단·승인 재개

**입력:** 센터/구역/SKU/LOT/업무 범위, 접수 중지·준비 중지·출발/인계 제한·품질 차단 중 유형, 사유·발생시각·승인 근거·영향 진행분을 받는다. CDC 운영 제한은 WMS, MFC 제한은 MFC, 고객 배송/라이더는 Delivery가 반영한다.

**처리:** 긴급성/권한 확인 → 영향 신규 행위 제한 요청 → 진행 주문·현물·운송·미확정 거래 식별 → 각 정본 제한 결과 확인 → 고객/현장 안내와 담당 지정 → 원인 해소·미결/품질·시설 근거 확인 → 필요한 승인 후 범위별 재개 요청 순이다.

**규칙:** 접수 중지는 기존 주문 취소가 아니다. 안전 작업 중지는 진행 실물과 원장 불명을 없애지 않는다. 여러 제한이 겹치면 하나 해제돼도 나머지는 유지한다. 시설 냉각 회복과 상품 품질 해제는 별도이며 시간 경과만으로 자동 재개하지 않는다.

**복구·완료:** 일부 센터만 차단 반영됐으면 대상별 미반영과 신규 실행 위험을 표시한다. 원 제한 ID로 조회/전달하며 반복 차단으로 수량을 여러 번 제외하지 않는다. 재개 승인·최신 제한·원시스템 결과·미결 담당이 맞아야 해당 범위만 재개 완료다.

### 1) 제한은 업무별로 지정한다

| 제한 종류 | 원정본 | 진행분의 취급 |
|---|---|---|
| 신규 주문/슬롯 접수 중지 | MFC·Delivery 조건을 OMS가 소비 | 기존 주문/예약·결제 의무 유지 |
| 현장 작업·구역/장비 안전 중지 | CDC WMS/자기센터 MFC | 현재 실물·완료분·미실행 잔량·보관 책임 보존 |
| SKU/LOT 품질·리콜 차단 | 지정 품질 승인과 WMS/MFC | 영향예약/BLOCKED·주문/공급 약속 연결 |
| 간선 출발/수령 제한 | WMS/TMS/MFC 각 범위 | 기출발 사실·운송중 안전수령과 분리 |
| 라이더 신규 배차/인계 제한 | Delivery·MFC 인계검증 연계 | 이미 받은 상품/반납·정산 의무 유지 |

### 2) 차단의 적용 단계

신고/증빙 접수→지정 권한/긴급 계약 검사→대상·행위/효력 특정→각 원정본 제한 요청→원제한 ID·버전·반영 범위 확인→미반영/진행분 영향 조사→안내/보관/후임 조치 순이다. 전체센터 중지와 일부SKU 신규피킹 중지는 다른 명령이다.

### 3) 재개 승인에서 확인할 자료

원인 해소 증빙,시설/설비의 현재 적격,상품 품질의 별도 판정,미전기/미인계 실물·원예약·진행단말의 상태,여전히 남은 다른 제한,유효 재개 승인·대상 범위·최신 버전을 확인한다. 하나가 불명이면 해당 범위 재개를 보류한다. 이미 안전한 다른 업무까지 무조건 닫을 필요는 없다.

### 4) 동시성·늦은 결과

원제한 이후 신규 작업 시작이 경합하면 주관 시스템의 실행 순서를 확인한다. 화면 반영 지연을 실제 제한 미존재로 해석하지 않는다. 해제 통지보다 새로운 차단이 먼저 적용됐다면 구해제로 새 차단을 지우지 않는다. 자동 만료/재개를 도입하려면 재개 조건·진행실물 확인 계약이 별도로 필요하다.

### 5) 완료 기준

반영 대상별 제한/재개 결과·현재 제한 합성·영향 진행분·보관 책임·고객/운송 안내·미반영 담당이 일치해야 한다. `본사 승인 완료`와 `현장 재개 완료`를 별도 표시한다.

## BO-09. 정책 등록·심사·발효·반영 추적

**입력:** 정책 종류·소유 시스템·대상(센터/SKU/역할/업무), 값·단위·효력, 우선순위·기존 버전·영향, 요청/승인 근거를 받는다. 공급 안전량·배분은 SCM, 고객 구매/클레임 판단은 OMS 등의 소유권을 유지한다.

**처리:** 정책 범위·제약 검사 → 동순위/기간 충돌·미정 항목 식별 → 담당자의 심사 → 원소유 시스템에서 유효 버전 확정 → 수신 대상별 접수/검증/반영/거절 추적 → 발효 이후 신규 처리의 참조 버전 확인 순이다. 정책 레지스트리는 승인/참조를 연결하며 모든 도메인의 계산 엔진을 복제하지 않는다.

**설정 판단:** 명시적 0과 미등록을 구별한다. 배수 0·음수 안전량·최소>최대·승인선 누락은 보류다. 과거 50% 추가승인, 일반 6시간/긴급 2시간, 고정 회차·손실 금액 등의 후보를 현재 운영값으로 되살리지 않는다.

**변경 영향:** 일반 정책은 승인된 적용 기준으로 신규 건에 적용한다. 안전/리콜은 진행분까지 영향 평가하되 과거 정상 사실을 삭제하지 않는다. 롤백은 새 버전이며 과거 전기를 역실행하지 않는다. 소비자 일부 반영 실패는 `부분 적용`으로 남긴다.

**완료:** 정책의 소유·승인·효력·실제 반영 범위와 미반영 담당이 확인돼야 한다. 발송 성공만으로 전센터 적용 완료가 아니다.

### 1) 정책 정의와 실행 설정을 분리

정책안에는 소유 업무·값/단위·선택 규칙·적용 범위/기간·우선순위·검토자/승인자·미설정 처리·변경 영향·실행 반영 대상을 둔다. 동일 정책을 본사와 도메인에서 각각 다르게 저장해 둘 다 유효하다고 만들지 않는다. BackOffice는 원정책 ID·승인/반영 상태를 연결한다.

### 2) 유효 정책 선택의 검토

| 검사 | 보완/거절 사유 |
|---|---|
| 값·단위 | 미등록과 명시적0 혼동,음수 보호량,배수0,다른SKU 단위 합산 |
| 범위 | 센터/SKU/업무 조건이 겹치나 선택 규칙이 없음 |
| 기간 | 같은 우선순위의 유효기간 중복·효력 공백 |
| 정책 종류 | 보호기간 목표와 Min/Max를 동시에 중복 실행하려 함 |
| 권한/분리 | 정책 발의자가 자기 한도를 늘리고 직접 승인하려 함 |
| 실행/진행 영향 | 기존 예약·승인·실출발을 새 정책으로 지우려 함 |

정책 우선순위 자체는 해당 도메인의 승인 계약을 따른다. 화면에 범위가 세분됐다고 언제나 개별 설정이 우선한다고 임의 확정하지 않는다.

### 3) 변경·발효·대체

초안→도메인 검증/영향시뮬레이션→업무 승인→유효정책 버전→수신자 실행 설정→발효/반영 확인→관측/미결 복구로 진행한다. 모의 입력은 실제 정책/주문/재고와 분리한다. 이전 버전 복원도 새 승인/효력이며 기발생 수불을 되돌리는 명령이 아니다.

### 4) 사례

가정: MFC 신규수요 보호량을0→2로 올렸으나 이미 고객 예약4개가 있다. 새 보호량이 기존4개의 예약을 해제할 권한이 되지 않는다. MFC의 신규 확보 한도와 보호 부족·OMS 약속 영향을 확인한다. SCM 정책 승인은 MFC 실행 설정 반영 성공과 별도다.

### 5) 종결 자료

선택된 정책/조건·효력,승인/반영된 대상,미반영의 실제 영향,기존 진행분의 적용 기준,재처리/재심사 담당과 원정책 계보를 남긴다. 미등록 정책은 샘플 값으로 채워 운영하지 않는다.

<a id="bo-10"></a>

## BO-10. 통합 승인함·재심사·철회

**입력:** 상품/가격/권한/공급/품질/손실/조정 등 종류와 원승인 객체, 검토 문안, 대상 행·수량/금액·단위·기간, 승인선·증빙을 받는다. 서로 다른 승인 종류의 결론을 재사용하지 않는다.

**처리:** 본인 처리 가능 목록 조회 → 원정본 최신 상태와 근거 비교 → 승인/부분승인/반려/보완 요청 → 도메인 승인 결과 연결 → 허용 실행 요청과 결과 추적 순이다. 승인 금액·수량·기간을 결론에 명시하고 미승인분 사유를 남긴다.

**재심사:** 가정: 요청 승인 당시 CDC 가용 100이 현재 40으로 바뀌고 해당 값이 승인 구간에 영향을 주면 이전 화면의 승인 버튼으로 통과시키지 않는다. 최신 근거로 재심사하며 기존 실제 확보·출발은 보존한다. 상위 승인자의 대행도 허용 범위 안에서만 인정한다.

**철회·불명:** 실행 전 철회는 원시스템의 미실행/점유 해제 확인이 필요하다. 이미 실행된 3개를 승인 철회로 0개로 만들지 않는다. 승인 저장 불명은 원승인 조회 후 기존 결과를 반환한다. 동일 버전 동시 승인은 하나의 유효 결정으로 수렴해야 한다.

**완료:** 업무 승인과 미승인/잔량·전달 의무가 설명되면 심사 단계 완료다. 실제 재고·환불·운송 완료와는 별도다.

### 1) 승인 종류별로 확인할 핵심

| 승인 종류 | 결정하는 것 | 결정하지 않는 것 |
|---|---|---|
| 상품/가격 | 특정 변경안·효력·조건의 허용 | 새 SKU 발급·고객청구 성공 |
| SCM 공급 | 유효 원요청의 승인량/미충족·조건 | CDC 확보·출발·입고 |
| 품질 해제/처분 | 근거 있는 대상 실물의 허용 행위 | 실제 폐기·현물 전기 |
| 재고 조정/손실 | 조사된 원사건·차이/잔량에 대한 집행 허용 | 누락원거래 삭제·상대수령 대체 |
| 고객 환불/예외 | OMS가 판단할 사유·금액/수량·위임된 추가승인 | PG 성공·회수/재고 증가 |

### 2) 심사자의 실제 순서

1. 해당 업무의 원정본·최신 버전·기결정/철회를 조회한다.
2. 요청자와 결재선·대행/한도·자기승인 분리를 확인한다.
3. 전후 값·수량/금액/단위·근거·영향 대상과 현재 상태를 비교한다.
4. 미확인 항목을 나눠 필요한 증빙 보완을 요청한다. 보완 대기는 반려나 승인과 다르다.
5. 승인·부분승인·반려의 대상행과 수량·조건·효력·근거를 확정한다.
6. 원도메인에서 유효 승인 ID가 확정됐는지 확인하고 공통 승인함에 같은 결과를 연결한다.
7. 후속 실행/전달을 요청하고 단계별 결과·미실행 잔량을 관리한다.

### 3) 상태별 다음 행동

| 상태 | 담당자의 다음 행동 |
|---|---|
| 보완 요청 | 요청자가 증빙/문안을 새 버전으로 제출,기존 승인 재사용 안 함 |
| 부분 승인 | 승인행/미승인행을 분리,미충족 사유·재요청 자격 확인 |
| 승인 완료/전달 실패 | 원승인 조회·전달만 복구 |
| 승인 만료/미실행 | 새 실행 차단,기점유·진행 결과를 원조회 |
| 승인 철회/실행 경합 | 원결과와 진행실물 확인,미실행 범위만 유효 철회 |
| 기집행 뒤 근거 변경 | 과거 실적 보존,잔량 재심사·필요 정정 승인 |

### 4) 복합 승인 사례

가정: 공급 승인60이 있어도 품질 차단LOT12를 출발시키는 권한은 생기지 않는다. 원공급 의무60을 보존하고 WMS 적격 확보 결과·SCM 대체/미충족을 확인한다. 품질 해제 승인과 공급승인을 합쳐 단일 무제한 승인으로 만들지 않는다.

<a id="bo-11"></a>

## BO-11. 주문·결제·현장·배송 통합 조회와 CS 접수

**입력:** 담당 권한 안의 주문번호, 고객 인증/문의 근거, 배송·포장·결제·클레임 참조, 상담 사유를 받는다. 전체 고객 검색과 개인정보 원문 열람은 별도 권한이다.

**조회:** OMS 주문/행·원가격·고객 선택 → PG 승인/취소 확인 상태 → MFC 예약·준비·인계/부족 → Delivery 배송별 실제 결과 → 클레임·회수·환불 의무를 연결한다. 도메인별 원천/버전/확인시각을 표시하고 서로 다른 상태를 한 “완료”로 합치지 않는다.

**접수:** 문의를 새/기존 사건에 연결하고 원하는 결과·증빙·연락 결과를 남긴다. 주문 조회만으로 신규 취소·회수·재배송을 발행하지 않는다. 상담원의 통화 성공은 고객 동의의 내용·대상/금액·시각을 별도 기록해야 하며 동의 범위를 확장하지 않는다.

**예외:** PG 승인 확인/OMS 확정 지연이면 “주문 확인 중”과 원시도 조회 조치를 표시한다. 고객앱 실패 화면만으로 미결제라고 단정하지 않는다. 분할배송 일부 완료는 나머지 의무를 유지한다. 고객 탈퇴 접수 뒤에도 미결 거래를 처리하며 재가입 계정에 과거 개인정보를 자동 연결하지 않는다.

**완료:** 상담 접수·담당/다음 조치·고객 안내가 기록되면 접수 단계 완료다. 상담 종료와 주문/금전/회수 의무 종결은 구분한다.

### 1) 주문 한 건에서 대조할 자료

| 자료 묶음 | 반드시 구별할 내용 |
|---|---|
| 고객·원주문 | 당시 주소/연락처·동의·지정MFC·SKU/수량·원가격·품절 선택 |
| 결제 | 원결제시도·PG 승인액/상태·누적 취소·진행/불명·잔액 |
| 현장/재고 | MFC 현물예약·슬롯·작업·실피킹/부족·유효포장·실인계·commit |
| 배송 | 배송별 구성·현재 기사/배정버전·실픽업·전달·미전달·원증빙 |
| 구매 후 | 원클레임·진행 점유·승인/거절·회수/검수·환불/교환 이행 |
| 상담/사건 | 과거 문의/안내·고객 선택·담당·원결과 조회·남은 의무 |

### 2) 상담 접수부터 후속 요청까지

1. 고객/문의자의 관계와 본인/대리 요청 허용 범위를 확인한다. 인증 방식·대리접수 정책 미등록을 무시하지 않는다.
2. 담당 주문·요청 범위만 조회하고 기존 사건/같은 피해의 중복 접수를 찾는다.
3. 원하는 결과와 실제 사실을 구별한다. “환불 받고 싶다”는 환불 승인 사실이 아니다.
4. 결제·준비·인계·배송·클레임의 원천 결과/확인시각을 대조한다.
5. 증빙/시각·피해 품목/수량·보관/안전·고객 동의를 기록하고 담당 도메인을 정한다.
6. CS에게 위임된 요청만 OMS/Delivery 등으로 전달한다. 상담원의 입력으로 원장을 변경하지 않는다.
7. 확정 결과와 확인 중인 항목을 구분해 안내하고 다음 조치/담당을 약속한 근거로 남긴다.

### 3) 상태 설명의 예

| 실제 확인된 상태 | 고객/운영 표시 |
|---|---|
| PG 승인,OMS 확정 대기 | 결제 사실 확인·주문 확인 중,신규 결제 권유 안 함 |
| MFC 준비 완료,기사 미확보 | 상품 준비와 배송 배정 대기 분리 |
| 배송2개 중1개 전달 | 일부 전달·남은 배송/수량·다음 조치 |
| 배송 완료 후 파손 신고 | 기존 전달 이력 유지·별도 클레임 진행 |
| 환불 요청 승인,PG 불명 | 환불 승인/결과 확인 중,환불 완료 아님 |

### 4) 고객정보 변경의 경계

주소록 수정은 Commerce의 현재 저장 정보만 바꾼다. 결제 후 원주문 주소·연락처·요청사항은 변경하지 않는다. 예약 주문의 허용된 시간 변경은 BO-12의 별도 절차로 OMS에 요청한다. 고객 탈퇴/재가입·운영 제한 이력은 계정/주문/개인정보의 각 정책으로 판단하며 새 계정에 과거 주문을 임의 귀속시키지 않는다.

<a id="bo-12"></a>

## BO-12. 고객 취소·현장 중지·인계 경합 조율

**입력·조건:** 원주문/행·유효 포장 버전, 취소 사유·대상량, 고객의 사전 품절 선택, 권한·OMS 판단, MFC/Delivery의 실제 인계 결과를 확인한다. 고객 임의 부분 취소를 새로 허용하지 않는다.

**정상 처리:** OMS에 취소 적격 요청 → MFC 원작업/포장 중지·실인계 판정 조회 → 미인계 유효 범위만 취소 조정 → MFC 복귀/품질·예약 결과와 Delivery 배정 정리 확인 → OMS의 원가격 취소/Payment 결과 → 고객 안내 순이다. 접수시각만으로 취소가 인계보다 먼저였다고 판단하지 않는다.

**분기:** 미피킹은 유효 중지/예약 해제를 확인한다. 피킹·포장 후에는 현재 실물·복귀/검수·판매 제외를 확인하며 해제만으로 즉시 재판매하지 않는다. 인계 선확정/진행·불명이면 출고 전 취소 성공을 보류하고 원사실을 조회한다. 이미 넘긴 실물은 OMS의 회수/반품 경로로 연결한다.

**부분 사례:** 주문 4개, P1=2/P2=2 중 P1만 인계됐으면 P1의 2개를 되살리지 않는다. P2도 해당 사유/권한·정책상 취소 가능 범위를 OMS가 판단한다. CS가 전체 주문 상태를 직접 취소로 덮지 않는다.

**복구·완료:** 중지 성공/응답 유실은 원판정 조회다. 새 취소·환불을 반복하지 않는다. OMS 취소량, 실제 인계/미인계량, MFC 권리/실물, Delivery 배정과 Payment 결과가 대사돼야 해당 취소가 완료된다.

### 1) 취소 가능량의 판정 자료

원주문행의 주문량,유효 인계 누계,기확정 취소,열린 미인계 잔량,진행중 취소/클레임 점유,최신 포장구성·현재 기사배정,현장 중지/실인계 판정 세대를 확인한다. 수량이 미인계라는 이유만으로 모든 부분취소가 허용되는 것은 아니다. 사유·고객 사전 품절 선택·OMS 정책을 함께 검사한다.

### 2) 단계별 처리표

| 확인 사실 | OMS 요청/현장 조치 | 수량·금전의 후속 |
|---|---|---|
| 피킹 전·유효 중지확정 | 신규 작업 시작 차단·원예약 해제 | 현물 불변,PG 취소는 별도 |
| 피킹/포장 후·미인계확정 | 실물 판매제외/복귀대기·유효 포장 정리 | 해제 후에도 실제복귀/품질 전 신규가용 선복구 금지 |
| 인계 진행/단말응답불명 | 같은 포장/원실행 결과 조회 | 취소 성공·예약 해제·새 기사 인계 보류 |
| 실인계 확정 | 해당량 출고전취소 불가 | OMS 반품/회수 자격 판단·원출고 보존 |
| 일부 인계 | 인계/미인계 범위별 심사 | 전체주문을 한 상태로 복원하지 않음 |

### 3) 취소 정상 절차와 실패 지점

1. 원취소 의도/버전을 조회해 기접수·기확정·중복 피해를 확인한다.
2. OMS가 사유·수량/정책상 적격을 판단하고 MFC 중지/인계 판정을 요청한다.
3. MFC/Delivery의 원포장별 사실과 재고 확정 ID를 확인한다. 취소 요청 접수 ACK로 인계 차단을 확정하지 않는다.
4. 유효 미인계량의 작업·실물·예약/슬롯·배송 배정 정리를 각 담당에서 수행한다.
5. OMS가 원가격 취소 의도·잔여 이행을 정하고 Payment 결과를 대사한다.
6. 일부 단계가 불명이면 이미 끝난 단계는 보존하고 불명 대상만 원조회한다.
7. 고객 안내에는 취소된 수량·계속 이행할 수량·환불 성공/확인 중을 나눠 보여 준다.

### 4) 예약 시간 변경의 별도 업무

결제 후 주소/방식 변경은 금지하고,예약배달의 **상품준비 시작 전 예약 시간만** OMS가 심사한다. 새 슬롯·MFC 여력·현재 현물예약/LOT기한·Delivery 가능조건을 확인해 새 슬롯을 임시 확보한다. 준비 시작과 시간변경의 확정 순서를 판정한다. 변경 성공 뒤 기존 슬롯 해제·주문버전/준비·배차계획을 갱신한다. 실패/준비 선확정이면 새 임시 슬롯만 정리하고 기존 시간·금액·원예약을 유지한다. 새 결제/중복 피킹을 만들지 않는다.

### 5) 경합 사례

가정: 주문4개 중 P1의2개를 라이더가 실제 받았고 P2의2개는 포장대에 있다. 상담원이 전체 취소를 누른 시각이 빨라도 P1은 출고전취소로 복원하지 않는다. P2도 정책상 허용 사유·현장 중지/실물·원예약 결과를 확인한다. 통화중/기사GPS 정차만으로 “아직 안 넘김”을 단정하지 않는다.

<a id="bo-13"></a>

## BO-13. 환불 심사·원결제 취소·불명 대사

**책임·입력:** CS는 사유·증빙·원주문/품목·수량을 제출하고 OMS가 적격과 환불 금액/의도를 판단한다. Payment는 PG 실제 취소를 처리한다. BackOffice는 유효한 위임·추가승인과 원결과를 연결한다.

**금액 제한:** `추가 취소 가능액 = 최초 승인액 − 누적 성공 취소액 − 진행/결과불명 취소 점유액`. OMS의 승인된 의도 금액과 이 한도 안에서만 요청한다. 같은 피해 수량을 품절·반품·미배송 사유로 중복 환불하지 않는다.

**처리:** 원주문 가격/배달팁·봉투·사유/대상 검증 → OMS 환불 의도/승인 결과 확인 → 필요 권한 심사 → 원의도/원PG 거래로 실행 요청 → 실제 성공/실패/불명 조회 → 원주문/품목 환불 결과와 고객 안내 확인 순이다. 현재 가격으로 재계산하거나 전체 취소 후 잔여 상품 재결제를 기본 처리하지 않는다.

**가정:** 최초 승인 30,100원, 성공 취소 10,000원, 불명 점유 5,000원이면 새 요청 가능 상한은 15,100원이다. 불명 5,000원의 결과를 확인하기 전 상한을 20,100원으로 보지 않는다. 이 산식은 승인된 환불 사유 자체를 만들어 주지 않는다.

**예외:** PG 성공/OMS 표시 실패는 원취소 결과로 표시·통지만 복구한다. 승인만 있고 PG 결과가 없으면 완료 안내하지 않는다. 무승인 추가 청구·배달팁 추징·임의 계좌 환급·쿠폰 보상을 새로 도입하지 않는다.

**완료:** 원의도·실취소 거래·누적 금액·품목 수량·잔액·통지/미결이 맞아야 한다. 현금 흐름과 회수/재고는 별도 축이다.

### 1) 환불 요청서와 실제 금전 상태

| 구분 | 관리 항목 |
|---|---|
| 사유/대상 | 원주문·품목·피해 수량·원클레임/품절·기진행 점유·심사 근거 |
| 원금액 | 당시 SKU단가·수량·상품액·확정 배달팁/봉투값·PG 승인액 |
| 환불 의도 | OMS 의도 ID/버전·승인량/승인액·필요 승인·환불 개시조건 |
| PG 실행 | 원승인 거래·취소 요청ID·성공/실패/불명·금액·확인시각 |
| 잔여 | 성공누계·진행/불명 점유·추가 가능액·미집행 의도·다음담당 |

신청량/승인량/실취소량과 신청액/승인액/PG성공액은 각각 다르다. CS가 임의 금액을 입력해 PG 취소 요청을 만드는 대신 OMS가 원주문과 피해·진행 점유를 검증한 의도를 사용한다.

### 2) 1차 기본가격 거래의 심사

가정: A20,000원+B10,000원,무료배달·봉투100원으로30,100원이 결제됐다. B의 현장 부분품절이 고객의 유효 선택에 따라 승인되면 OMS가 원B상품액10,000원 취소를 판단하고 PG 성공 후 잔액20,100원을 표시한다. 상품액이30,000원 아래가 됐다는 이유로 배달팁을 새로 추징하지 않는다. 전체취소의 봉투100원 환불과 부분 사유별 비용은 원정책/승인을 따른다.

과거 할인 거래가 실제 존재하면 당시 불변 안분/정책을 OMS가 해석한다. 새 1차 거래에 과거 할인 엔진을 활성화하거나 과거 결제액을 현재 기본단가로 재작성하지 않는다.

### 3) 실행/복구 결정표

| 상태 | 허용 | 차단 |
|---|---|---|
| 환불 의도 미승인 | 증빙 보완/권한 심사 | PG실행 |
| 의도 승인·개시조건 미충족 | 회수/검수 등 필요한 결과 확인 | 승인만으로 환불완료 |
| PG 미실행 확인·조건 충족 | 원의도·원키로 허용 실행 | 같은 피해 새의도 중복생성 |
| PG 결과불명/처리중 | 원거래 조회·해당금액 점유 유지 | 점유를 빼고 새 취소 요청 |
| PG 성공·OMS 반영 지연 | 원성공 ID로 OMS 표시/통지 복구 | PG 취소 재실행 |
| PG 실패 확정 | 실패사유·재실행 적격/승인 재검사 | 새계좌 송금으로 무승인 우회 |

### 4) 누적 한도와 다른 피해의 동시 요청

가정: 승인30,100원−성공10,000원−불명5,000원=새 상한15,100원이다. 새로운 정당한 의도가8,000원이면 한도 안에서 심사할 수 있지만 같은 피해5,000원을 다른 이름으로 요청하면 중복이다. 원의도와 실제 피해 수량을 함께 검사한다. 서로 다른 환불의 동시 실행도 Payment/OMS 원거래 한도를 원자적으로 검증해야 한다.

### 5) 고객 안내·종결

성공액·확인중액·미승인/미실행 의도·남은 결제액과 후속 확인 담당을 구별한다. PG성공이 고객 계좌 입금시각과 같은지 별도 계약 없이 단정하지 않는다. 회수/재고·기사비의 미결은 환불과 별도 유지한다. 미등록 환불 개시점·금전 보상 예외는 상신하며 기본 부분품절/반품 PG부분취소 지원 자체를 미지원으로 돌리지 않는다.

<a id="bo-14"></a>

## BO-14. 반품·교환·회수·후속 이행 심사

**입력:** 원주문/행·실제 전달시각·상품 종류·대상량, 사유·증빙/인지시각, 기접수·진행 수량, 고객 요청과 현재 보관 상태를 받는다. 미배송 신고는 실제 받은 상품의 반품과 구분한다.

**정책 참조:** 일반 교환/반품 7일, 신선 냉장·냉동 24시간, 하자/오배송/광고 상이 **교환**의 수령 3개월 또는 인지 30일 조건은 OMS의 현재 문서 기준을 사용한다. 특례의 반품 적용 범위 등 미정 부분은 심사로 남기고 임의 확대·축소하지 않는다. 시간 계산·달력 경계는 OMS 계약이 담당한다.

**처리:** OMS 자격/중복·대상 승인 → 회수 필요/예외 승인 확인 → Delivery 원클레임 회수 → 실제 수거·MFC 반납·검수 결과 분리 → OMS 환불/교환 판단 → 교환 승인 후 대체 현물 확보·새 이행 → Payment 결과와 고객 안내 순이다. 회수·후속 배송 주소는 원주소를 유지한다.

**비용·분기:** 단순 변심 교환 왕복 합계 9,000원과 상품/배송 문제 고객 부담 0원이라는 원정책을 참조한다. 왕복 각각 9,000원으로 계산하지 않는다. 일반 반품비·환불 개시점·철회/거절품 후속 처리는 승인 대기이며 교환비를 자동 전용하지 않는다.

**부분·재고:** 3개 신청 중 2개 승인/1개 거절이면 2개만 후속 요청한다. 수거 2개/MFC 인수 1개면 미반납 1개를 유지한다. 환불 2개가 성공해도 MFC 입고를 2개로 합성하지 않는다. 상온 미개봉 적격품 복구와 신선/냉장/냉동 회수품 재판매 금지 등 현행 정책을 MFC 품질 처리에 연결한다.

**완료:** 신청·승인/거절·실수거/인수·검수·환불/교환 이행·미결 수량/비용이 설명돼야 한다. 수거 완료만으로 사건 전체를 끝내지 않는다.

### 1) 접수·자격·승인·실행을 나눈다

| 단계 | 확인할 내용 | 다음 결과 |
|---|---|---|
| 접수 | 원주문/행·상품 실제수령·요청량/사유·기신청·증빙/인지시각 | 접수/보완,접수만으로 승인 아님 |
| 자격 | 상품별 실제 수령기준 기한·특례 사유·중복 수량·기존 클레임 | 적격/부적격/추가심사 |
| 심사 | 승인/거절량·원사유·회수 필요/예외·비용·환불개시조건 | OMS 유효 클레임 결정 |
| 회수 | 실제 수거량·센터 반납/인수량·미수거/미반납·보관 | Delivery/MFC 원결과 |
| 검수 | 실제 품목/LOT·상태·원출고 대응·재판매/처분 정책 | MFC/품질 판정 |
| 금전/교환 | 원가격 환불·비용 처리·승인 교환품 현물확보/후속배송 | Payment/OMS/현장/Delivery 결과 |

### 2) 접수 기한의 경계 처리

분할배송은 대상 품목의 실제 전달시각이 기준이다. 신선 냉장/냉동24시간·일반7일과 하자/오배송/광고상이 교환의3개월 또는 인지30일 조건을 OMS가 계산한다. 경계시각까지 접수 가능,달력3개월을90일로 바꾸지 않는 현재 설계를 따른다. 인지시각·특례 반품 범위가 불명확하면 근거 보완 심사로 두며 일반기한만으로 자동 거절하지 않는다.

### 3) 회수·교환의 실제 처리

1. OMS가 대상·수량·사유·원주소·회수 필요/예외·비용·후속 이행을 결정한다.
2. Delivery가 원클레임으로 회수 의뢰를 받아 유효 기사/일정을 배정한다.
3. 실수거와 MFC 반납을 구분하고 부족/파손·보관 책임을 남긴다.
4. MFC가 실제 인수량만 반입/격리로 처리하고 검수/품질 판정을 연결한다.
5. 환불 개시조건을 충족한 범위를 OMS가 판단해 원금액 취소를 조정한다.
6. 교환품은 현재 적격 현물을 별도 확보하고 원교환 클레임에 연결한 새 이행으로 출고한다.
7. 고객 안내와 미수거·미반납·검수/금전/후속배송의 열린 의무를 대사한다.

### 4) 사례·비용·정정

가정: 신청3 중2승인/1거절,기사수거2/MFC인수1이면 후속 대상은 승인2이고 반입은1이다. 미반납1을 찾기 전 MFC현물2·검수2를 만들지 않는다. 환불이 먼저 가능한 예외도 승인된 개시조건이 있어야 한다.

단순변심 교환 왕복 총9,000원은 원교환 비용이며 일반 반품비에 자동 전용하지 않는다. 수거 뒤 철회·거절품 재전달·교환품 품절의 고객 선택/비용은 미결정 계약에 따라 심사한다. 교환품 품절을 무단 다른SKU 대체로 해결하지 않는다.

### 5) 재고·금전 종결의 독립성

고객수거·센터인수·검수·재판매/폐기·환불/교환배송은 각각 완료 근거를 갖는다. 상온 미개봉 적격품만 정책상 검수 후 복구하고 신선/냉장/냉동 회수품은 현재정책에서 재판매하지 않는다. `반품 완료`라는 한 칸으로 미반납·미환불을 숨기지 않는다.

<a id="bo-15"></a>

## BO-15. 품질 차단·리콜·해제·영향 추적

**입력:** 제조 LOT 원문/내부 참조·SKU·센터/위치·BOX/PLT/포장·운송 구획, 발견 사실·노출 기간·증빙·실물량·관련 주문과 지정 승인자를 받는다. 제조 LOT의 텍스트가 같아도 다른 배치를 무조건 합치지 않는다.

**처리:** 안전상 영향 신규 사용 제한 요청 → CDC/MFC/운송 중/미출고 주문의 영향 범위 추적 → 원천별 차단/품질/예약부족 결과 확인 → 실물 보관·추가 조사/고객 대응 담당 지정 → 지정 품질 승인에 따른 일부 해제/처분 판단 → 실제 결과와 남은 영향 대사 순이다.

**권리:** 차단된 예약은 기존 주문/공급 약속을 삭제하는 것이 아니다. WMS/MFC가 적격 연결과 BLOCKED 의무를 구분하고 OMS/SCM이 원약속과 대체 가능성을 판단한다. BackOffice가 안전량·타주문 예약·예정 공급을 가져와 강제 대체하지 않는다.

**부분 사례:** 보류 5개 중 근거가 있는 3개만 해제하면 정상 3/보류 2다. 이후 보류분 중 실제 폐기 1개가 확인되면 정상 3/보류 1/폐기 1로 연결한다. 해제 승인·폐기 승인·실제 폐기를 같은 시점의 재고 차감으로 합치지 않는다.

**복구·완료:** 센서 정상·창고 냉각 회복·사진 등록은 상품 품질 해제 승인이 아니다. 과거 정상 버전이 늦게 와도 최신 차단을 해제하지 않는다. 영향 대상별 제한/해제·예약/실물·고객/공급 대응·남은 보관 책임이 맞아야 해당 범위 종결이다.

### 1) 품질 사건의 대상 범위

SKU·제조 LOT 원문/내부명/센터 로컬키,실제 배치 계보,대상 센터/LOC·BOX/PLT/포장·운송 구획,기간·수량/단위·현재위치,원품질정책/증빙·최신 제한을 함께 본다. 제조LOT문자열·기한만 같다는 이유로 다른 배치를 병합하지 않는다. 이미 고객에게 전달된 대상은 현물 보관품과 별도 영향 주문으로 추적한다.

### 2) 차단에서 영향 업무 조율까지

1. 최초 발견 사실과 안전상 영향 범위를 기록하고 필요한 신규 사용/출발/인계를 제한한다.
2. 원LOT 계보로 CDC 현물·운송중·MFC 수령/현물·미인계 포장·고객 실출고를 추적한다.
3. 대상별 실제 수량·품질/위치·원예약·원장/전달 상태를 확인한다.
4. WMS/MFC가 적격 연결 상실·BLOCKED 의무를 확정하고 OMS/SCM이 약속 영향을 판단한다.
5. 조사 자료·노출 이력·실물 검수·권한에 따라 지정 품질 담당이 부분 해제/보류/처분을 결정한다.
6. 실제 허용 실행과 원장 결과를 확인하고 고객/공급 후속 의무를 연결한다.

### 3) 해제·처분의 분기

| 확인 상태 | 결정 |
|---|---|
| 시설 정상·상품 노출/기한 불명 | 상품 HOLD 유지·근거 보완 |
| 일부 실물만 적격 근거 확보 | 해당량만 해제,잔여 보류 |
| 처분 승인만 존재 | 실물 보관/실제 실행 대기,현물 차감 없음 |
| 실제 처분 일부 확인 | 확인분만 원센터 전기·미집행 승인잔량 유지 |
| 예약품 품질 차단 | 원고객/공급 약속 유지·대체/부족 결과 연결 |
| 과거 정상 통지가 늦게 도착 | 최신 차단 유지·과거 관측이력 보존 |

### 4) 중첩 영향과 수량 예 [가정]

같은10개가 리콜·실사·온도 차단을 동시에 받으면 대상 실물의 합집합을 확인한다. 10+10+10을 총30개로 보고하지 않는다. 보류5→적격3/보류2→보류분 실제폐기1이면 최종 정상3·보류1·폐기1이다. 각 단계의 승인·실행 시점과 원수량을 보존한다.

### 5) 원인 미확정·종결

귀책 확정 전에도 안전한 보관·필요 고객/현장 안내를 진행한다. 품질 해제는 손실/환불·공급 승인이나 판매준비 완료를 대신하지 않는다. 영향하위사건별 담당/원결과가 있어야 종결하며,새 영향 배치/고객 피해가 나오면 기존 범위와 새 범위를 구분해 재개한다.

## BO-16. 재고 차이·실사·승인조정 심사

**입력:** CDC/MFC를 구분한 위치·SKU/LOT·단위, 장부 기준선/시각·원장 버전, 초계수/독립 재계수, 진행 MOV/입고/인계·원실행/commit 조회, 원인 조사·조정안을 받는다. 총량만 맞추는 조정은 허용하지 않는다.

**처리:** 원센터의 실사 통제/계수 확인 → 기준선 전후 실제 이동·미전기·중복 조사 → 원거래 복구가 가능한 차이는 먼저 복구 → 남은 차이·예약/품질 영향·평가 근거 심사 → 승인된 대상/잔량의 ADJ를 원센터에 요청 → 확정 결과와 잠금/미결 확인 순이다.

**사례:** A 장부 10/실물 8인데 B로 MOV 2개가 실제 끝났고 전기만 누락됐다면 원 MOV를 복구해 A8/B+2로 맞춘다. ADJ−2를 추가하지 않는다. 이전에 −2 조정이 승인됐어도 근거가 바뀌면 집행 전 재심사한다.

**부분·불명:** 조정 −5 승인 중 −3 확정/응답 유실이면 원결과 조회 후 남은 −2만 현재 근거로 판단한다. 중간에 실물 2개를 찾으면 잔량을 기계적으로 실행하지 않는다. 음수 예약이나 원약속 삭제로 차이를 숨기지 않는다.

**완료:** 계수·기준선·원거래 복구·승인/집행/잔량·예약/품질 영향·원장 결과가 연결돼야 한다. 재고 가치/금전 보상·회계 전기는 별도 담당이며 임계값을 임의 설정하지 않는다.

### 1) 조정 심사 전에 갖출 근거

센터·위치/SKU/LOT·단위,기준시각/원장 버전,초계수/독립 재계수,실사 중 진행 허용/금지업무,원입고/MOV/고객인계/반입/폐기·현재실물 위치,원실행/commit 조회 결과,원인 분류·예약/품질 영향·금액 평가근거를 받는다. 평가액은 근거/단가시점이 없으면 미평가이며 임의 금액 기준으로 승인선을 선택하지 않는다.

### 2) 차이 원인별 선행 조치

| 차이 | 우선 처리 |
|---|---|
| 실물 이동 완료·전기 누락 | 같은 원MOV/인계/입고 결과 조회·누락 복구 |
| 같은 사건 중복전기 의심 | 원실행 유일성·기확정 결과 조사·승인정정 |
| 위치A−/B+ 오기 | 실제 위치/구성 정정,센터 총량손실 ADJ로 대체하지 않음 |
| 단위/상하위 포장 중복 | 원SKU 단위·LPN 전개/환산·중복 계수 조사 |
| 재계수 뒤에도 실제 차이 | 원인불명/확정손실·예약영향을 구분해 조정 심사 |

### 3) 실제 심사·집행 순서

1. 실사 통제 범위·계수 기준선과 진행 작업의 실제 위치를 확인한다.
2. 초계수·다른 담당의 재계수를 대조하고 증빙 차이를 조사한다.
3. 원거래 누락/중복·현재 귀속/단위를 확인해 복구할 원거래를 먼저 처리한다.
4. 기준선 대사 후 남은 차이를 새 근거로 산정한다. 이전 차이/승인량을 그대로 유지하지 않는다.
5. 담당 승인자가 조정 종류·대상행·수량·기간/조건·예약/품질 영향을 심사한다.
6. CDC는 WMS,MFC는 자체 명령으로 승인 범위만 집행한다.
7. 원ADJ 결과·승인잔량·잠금/권리·전달의무와 고객/공급 영향을 확인한다.

### 4) 부분집행과 근거 변경 [가정]

−5 승인 중−3 전기된 뒤 응답이 끊기면 원ADJ 조회로−3을 확인한다. 잔여−2를 집행하기 전 현재 실물/원거래를 다시 본다. 2개가 새로 발견되면 원승인 근거를 재심사하고 새−5 또는 무조건−2를 실행하지 않는다. 집행된−3의 타당성도 바뀌면 원조정의 별도 정정을 심사하며 과거 실적을 삭제하지 않는다.

### 5) 불명 상태의 운영자 조치

원거래 조회 불가·실물 위치 불명·잠금 실패면 영향 범위 신규 사용/중복 실행을 제한하고 보관/조사 담당을 둔다. 예약을 음수로 만들거나 기존 약속을 삭제해 잔고를 맞추지 않는다. 원인/집행/잔량·제한 해제 근거가 모두 설명돼야 심사를 종결한다.

## BO-17. 폐기·운송손실·수령 경합 심사

**입력:** 폐기/운송 미수령/분실 의심을 구분하고 원출발·원수령·대상 행·수량·단위·현재 위치·보관 책임·품질/조사·승인 참조를 받는다. 격리 현물과 미수령 Transit은 다른 물량이다.

**폐기:** 지정 승인자의 품질/처분 근거와 실제 실행 증빙을 분리한다. CDC는 WMS, MFC는 자체 원장에 실제 처분분만 차감한다. 승인 5/실제 3이면 3만 전기하고 미실행 2를 유지한다. 사진만으로 승인 전량을 차감하지 않는다.

**운송손실:** 출발 12/확정 수령 10이면 우선 미정산 2다. 원출발·실상차·인계·원수령 처리/미통지·단위·오배송을 조사하고 지정 승인과 공동 대상 조정 계약이 있을 때 손실을 확정한다. “방금 추가 수령 없음” 조회나 WMS 로컬 버전 검사만으로 수령과 손실의 동시 처리를 막았다고 보지 않는다.

**미지원 계약:** 수령/손실의 동일 잔량 조정이 상대와 합의되지 않았다면 자동 손실 종결을 보류한다. 실수령 사실·안전 보관을 기록하는 것까지 막지 않으며 MFC 전기 허용/정정은 공동 계약으로 결정한다. BackOffice가 양쪽 원장을 대신 잠근 것으로 표시하지 않는다.

**늦은 발견·완료:** 손실 승인 뒤 같은 실물을 찾으면 원손실·실수령 계보로 승인 정정을 심사한다. 동일 잔량을 수령과 손실 양쪽으로 해소하지 않는다. 실제 처분/미수령·기확정 수량·잔량·상대 상태·다음 담당이 대사돼야 완료다.

### 1) 서로 다른 세 사건

| 유형 | 실물/원장 상태 | 필요한 심사 |
|---|---|---|
| 센터에 존재하는 격리/불량품의 폐기 | 현물은 있고 적격 사용 불가 | 품질/처분 승인·실제 폐기·센터 전기 |
| 미수령/운송 차이 | 원출발은 있으나 수령/손실 정산 미완료 | 출발/수령·단위·인계·미통지·손실 조사 |
| 센터 내 분실/실사 차이 | 장부와 관측 실물 차이 | 원거래 복구·재계수·잔여 차이 조정 |

하나의 “손실 처리”로 세 사건을 합치지 않는다. 이미 받은 격리품과 아직 받지 못한 Transit은 위치/소유 원장·대상 물량이 다르다.

### 2) 운송손실 심사의 단계

1. 원출발행·SKU/단위·기확정 수령/정정·승인손실·대사후 잔량을 조회한다.
2. TMS 상차/인계·MFC 실제수령/미전기·미통지·오배송·단위오류를 조사한다.
3. 동일 잔량의 수령·손실 경합을 조정할 공동 계약/담당과 지원 상태를 확인한다.
4. 계약과 증빙이 충족되면 손실 승인자·대상량·근거·효력/조건을 확정한다.
5. 유효 조정 범위의 원WMS 손실/미정산 결과와 MFC 원수령 상태를 다시 대사한다.
6. 새로운 수령 사실이 있으면 대상 재심사/승인정정으로 연결한다.

### 3) 경합 사례 [가정]

출발12·확정수령10·미정산2에서 “추가수령 없음” 조회 직후 MFC가2를 실제 받는다. 조회 응답은 잠금이 아니므로 그 조회만 믿고 손실2를 확정하면 이중 해소 위험이 있다. WMS 로컬 버전만으로 MFC의 새 수령을 막았다고 주장하지 않는다. 공동 대상/잔량 조정 계약이 미지원이면 자동 손실 종결을 보류하고 실제수령·안전보관 사실은 남긴다.

### 4) 누적 결과와 정정

원출발행별 q=r+l+t를 같은 단위/정정 버전으로 검사한다. 원수령10→8 정정은−2의 차이만 반영해 Transit을2→4로 바꾸며 이전10을 다시 빼지 않는다. 손실 뒤 실제 발견은 원손실의 정정과 새 실물 귀속을 함께 심사한다. 새 ADJ로 차이만 숨기지 않는다.

### 5) 처분 집행의 완료

폐기 승인수량·실제 처분수량·원센터 commit·남은 실물/보관 책임·승인 잔량·미전달을 확인한다. 손실/폐기 평가액과 고객 환불·운송비 귀책 심사는 별도 의무다. 원수량 정산만 맞췄다고 품질/금전 사건 전체를 끝내지 않는다.

## BO-18. SCM 공급 심사·미출발 잔량·추가 공급 관제

**입력:** SCM 원요청/TRF·행/버전, 필요 사용시각·추천/원수요·정책, CDC 적격/확보, MFC 수용/기존 공급, TMS 편성 가능성과 승인선을 조회한다. 계산·희소 배분은 SCM 내부 결과를 사용한다.

**처리:** 요청/근거의 최신성·중복 공급 확인 → 위임된 공급 승인자가 SCM 계약으로 심사 → 승인/부분승인/반려·미충족 기록 → WMS 확보/TMS 편성의 독립 결과 확인 → 출발·수령·품질·사용준비·행정 잔량 추적 순이다. 승인함에서 확정해도 SCM 원승인을 참조한다.

**사례:** 요청100/승인60/확보48이면 미승인40과 승인미확보12를 분리한다. 실제출발48 이후 승인60 중 남은12는 CDC 실물·작업·예약 정리와 SCM 수동 잔량종료로 처리한다. 같은 TRF의 두 번째 12개 출발을 열지 않는다. 원승인을 48로 조용히 줄이지 않는다.

**추가 공급:** 미수령·격리·준비 지연을 새 부족과 대사한다. 원공급/기존 공급과 원수요를 연결한 별도 요청·승인이 필요하며 불명 중 새 TRF를 자동 생성하지 않는다. 추천/알림은 현재 수동 요청을 대체하지 않는다.

**완료:** SCM 결정·WMS 권리/실출발·MFC 수령/준비·미출발/미수령·추가요청 계보가 설명돼야 한다. 50%·6시간/2시간 등의 후보는 채택/분모·측정 기준 승인 전 운영 자동 규칙으로 사용하지 않는다.

### 1) 공급 승인 화면의 근거 묶음

원요청/필요 사용시각·수동제출 사유,SCM 계산 스냅샷/정책과 미충족,유효 기존공급·고객약속·준비 가능 현물,CDC 적격/원예약·확보,목적MFC 공간/수령/검수·준비창,TMS 단일출발/구획/기한 가능성을 함께 본다. 모든 원천이 같은 시각이라고 가정하지 않는다.

### 2) 결정별 운영자 동작

| 상황 | 승인자가 판단할 것 | 후속 책임 |
|---|---|---|
| 추천만 있고 요청 없음 | 현재 수동요청 원칙의 제출 여부 | MFC 요청·SCM 접수 |
| 요청량>사업 승인 후보 | 미승인량·우선순위/사유 | SCM 사업결정 |
| 승인됐으나 CDC 미확보 | 대안/기한·원승인 유지 | WMS 확보 결과,SCM 영향 |
| 확보됐으나 TMS 미편성 | 원확보 유지/정리·다음 가능 조건 | SCM 변경심사·WMS/TMS |
| 출발 후 미수령/격리 | 원수요·기존 공급과 새 부족 구분 | MFC/WMS 원결과·SCM 추가공급 |

### 3) 승인→이행의 세부 절차

원요청/버전·중복공급 조회→권한/추가승인·정책/신선도 확인→사업 승인/부분승인·미충족 확정→WMS 확보/TMS 편성·MFC 수용 결과 확인→실출발 구성 동결→TIN/Transit/품질/준비 수량 대사→미출발 잔량정리·필요 추가요청 심사로 진행한다. BackOffice에서 클릭해도 SCM의 원사업승인 하나를 사용한다.

### 4) 잔량의 구체 사례 [가정]

요청100/승인60/확보48/실출발48이면 미승인40,승인 미출발12,실출발48을 분리한다. 출발48 중 MFC가46(정상44/격리2)을 받으면 미정산2와 품질2·준비대기를 별도 추적한다. 원승인60=실출발48+승인된 미출발잔량종료12가 될 수 있으나 출발률은48/60=80%다. 종료12를 수령/출발에 더하지 않는다.

### 5) 추가공급과 승인 기준의 현재 제한

같은 TRF 두 번째 실제출발은 금지다. 부족이 남으면 원수요·기존승인/미수령·격리/대체를 연결한 별도 요청/승인을 검토한다. 과거50% 추가승인·6h/2h 후보는 채택·분모/측정시점·다품목 기준 없이는 자동 실행하지 않는다. 원결과 불명에서 재고를 다시 확보하는 새TRF를 만들지 않는다.

## BO-19. TMS 간선 지연·사고·실출발 대사

**입력:** 승인 TRF/화물 버전, TMS 운행/정차·실차/기사/구획·계획/ETA/실제 시각, WMS 상차/TOUT, MFC 수령창·인계/수령, 사고 위치·온도·보관 책임을 받는다.

**처리:** 실제 안전·화물 위치 확보 → 출발 전/후 구분 → TMS 계획/배정·WMS 화물·MFC 가능성 대조 → 허용된 변경/재예측 요청 → SCM 공급/고객 영향 담당 연결 → 운송 사실·원장 결과·미수령/품질 의무 대사 순이다. 본사 관제가 별도의 경로/배차 엔진을 만들지 않는다.

**출발 불명:** 실제 출발했으나 TOUT이 불명이면 기발생 사실과 재사용 제한을 보존하고 원출발 전기를 조회한다. 정상 누락 복구와 무허가/승인 초과의 사고 전기 심사를 구분한다. 상차/GPS/통화만으로 출발 성공을 합성하지 않는다.

**사고 범위:** 출발 후 목적지 전환·자동 CDC 반송·자동 환적/재출발은 초기 미지원이다. 필요한 안전 조치를 기록하고 책임자에게 상신하되 같은 TRF의 새 실제출발로 우회하지 않는다. 차량 수리나 운행 종료만으로 품질/수량 사건을 닫지 않는다.

**완료:** 운행·정차·실출발 구성·인계/수령·WMS 응답·남은 실물/품질/비용 의무와 담당이 설명돼야 한다. 간선과 고객 Delivery는 별도 사건/명령이다.

### 1) 출발 전후의 권한 경계

| 단계 | BackOffice가 요청할 수 있는 조치 | 주관자 |
|---|---|---|
| 후보/미배정 | 미편성 사유 보완·지원되는 후보 재계산 | TMS |
| 배정/미상차 | 실차/기사·구획·시간/시설의 유효 대안 검토 | TMS,현장 자원 담당 |
| 상차/미출발 | 원화물 확인·유효 가상 하차/복귀·재검증 결과 연결 | CDC WMS·TMS |
| 실제 출발 후 | 안전·현재위치/보관·ETA 영향·지원되는 일정 조율 | TMS,목적MFC·품질/SCM |
| 인계/수령 후 | 원인계/수령·TOUT/Transit 불명 조회·정정 심사 | TMS·MFC·WMS |

화면을 DRAFT로 되돌려 실제 출발을 지우거나 원TRF 새 출발을 만드는 조치는 허용하지 않는다.

### 2) 사고 접수의 최소 자료

원운행/정차·실차/기사·배정세대,TRF/행·원출발 구성·BOX/PLT/SKU/LOT/단위,발생/발견시각·좌표/신선도·현재 실물/보관 책임,온도/봉인·실상차/인계·증빙·신고자를 확인한다. GPS 마지막 위치를 현재 위치로 확정하지 않는다.

### 3) 대응의 상세 순서

안전 확보→실제출발/미출발·현재실물 확인→영향 화물/품질/수령창·후속 운행/자원 조사→TMS 지원조치/ETA 재예측→SCM 공급약속·MFC 수령 준비와 연결→WMS 원출발/전기 결과 대사→하위 의무별 담당/종결로 진행한다. 운행 수리·기술 복구가 품질 해제나 원장 성공을 뜻하지 않는다.

### 4) 다이관 부분 성공 [가정]

한 차량에 TRF A/B를 싣고 실제 출발했으나 A TOUT만 확정/B는 불명이라면 A 원결과를 유지하고 B 원출발을 조회한다. 차량 단위 성공으로 B를 강제 성공시키거나 B화물을 CDC 신규가용으로 돌리지 않는다. 정상 누락이면 같은 원출발의 누락 전기를 복구하고 무허가/초과 사실은 사고 전기 승인 계약으로 보존한다.

### 5) 미지원 대응과 담당 인수

환적·구조운송·CDC 반송·타MFC 전환이 필요해도 현재 자동 기능으로 승인하지 않는다. 사람/상품 안전을 위한 실제 조치·누가 어디서 보관하는지·노출·인수자를 기록해 책임자에게 넘긴다. 지원되지 않는 사실을 원TRF 두 번째 정상출발이나 임의 ADJ로 맞추지 않는다.

## BO-20. Delivery 도움 요청·배차 제한·오배송 조율

**입력:** 원주문/배송/포장·유효 배정 라이더/버전, 실픽업·전달/수거·반납 증빙, 현재 위치/신선도·안전 문제·고객 연락 결과를 받는다. 고객과 기사에게 각각 필요한 최소 정보만 보여 준다.

**처리:** 안전 확보 → 실제 실물 위치/현재 수행과 유효 기사 확인 → Delivery의 허용 재배정/중단·도움 요청 처리 → MFC 준비/유효 포장·인계 권한 확인 → OMS 고객 약속·취소/클레임 판단 연결 → 실제 결과/추가 비용·통지 대사 순이다. 라이더 제한과 고객 환불은 별도 판단이다.

**오배송:** 원주소·실제 전달 위치·포장·증빙·귀책을 조사한다. 결제 후 주소 변경 금지를 우회하는 새 주소 입력 기능은 두지 않는다. 회수/후속 이행은 OMS 승인과 Delivery 실행을 따른다. 원배송 이력을 삭제하거나 수행 사실 없는 완료/회수를 만들지 않는다.

**라이더 제한:** 신고만으로 고의·무면허·GPS 조작을 확정하지 않는다. 증빙·소명·정책에 따라 신규배차 제한/일시 중지 등 유효 결정을 Delivery에 요청한다. 진행 상품의 안전 보관·인계·미지급 의무는 계속 추적한다. 재배정 후 구기사의 새 인계 권한은 무효화하되 구기사의 이미 발생한 사실을 버리지 않는다.

**완료:** 실제 수행·MFC 인계/반납·OMS 후속 판단·고객 안내·소명/비용의 남은 의무가 설명돼야 한다. 외부 참고의 보상금·연락 횟수·요금은 PMart 채택 근거 없이 자동 적용하지 않는다.

### 1) 도움 요청을 분류할 기준

| 상황 | 사실 확인 | 연결할 판단 |
|---|---|---|
| 기사 미확보/수락 지연 | 현재 배차 의뢰·제안/수락·준비예상 | Delivery 유효 배차/조율·OMS 약속 영향 |
| 픽업 전 오포장/파손 | 유효 PKG·MFC 실물/품질·기사 인수 여부 | MFC 재검수/재포장·OMS 부족 판단 |
| 픽업 후 파손/전달불가 | 실픽업·현재 보관/위치·고객 연락·증빙 | OMS 후속판단·Delivery 안전/승인회수 |
| 오배송/주소 불일치 | 원주소·실전달 위치·포장·지도/기사/고객 사실 | 원배송 보존·회수/클레임·귀책 분리 |
| 중복/비지정 기사 픽업 | 현재배정 세대·QR/포장·실제인수 | MFC/Delivery 원인계 판정·권한 차단 |

### 2) 운영자의 상세 순서

1. 실제 안전·상품 보관과 현재 수행자를 확인하고 필요한 신규 인계/배차를 제한한다.
2. 원배송/포장·배정버전·이미 확정된 인수/전달/회수 결과를 조회한다.
3. 고객 연락은 허용된 원연락 경로로 수행하고 시도/연결·동의 내용을 구별해 기록한다.
4. Delivery가 지원하는 조율·재배정/중지 요청과 MFC 유효포장/인계 판정을 연결한다.
5. 고객 취소·환불·교환/회수는 OMS의 사유/정책·실제 단계에 따라 판단받는다.
6. 수행료/추가비용·귀책/소명과 고객 대응을 별도 의무로 관리한다.
7. 실제 결과·고객 안내·남은 실물/금전/보관 담당을 확인한다.

### 3) 라이더 상태와 진행 물품

신규배차 제한·일시중지·계약종료는 서로 다른 결정이다. 현재 권한/증빙·소명·효력을 확인해 Delivery의 원상태에 반영한다. 제한되더라도 이미 받은 상품·회수품·미지급 실적을 삭제하지 않는다. 속도만으로 무면허,오래된GPS로 고의 위치조작,부정후기만으로 공제를 확정하지 않는다.

### 4) 재배정 경합 사례 [가정]

기사A→B로 변경됐는데 A 단말이 늦게 QR을 제출하면 현재 배정·실물·원인수 결과를 조회한다. A가 이미 실제 인수한 사실이 있으면 단순 무효 스캔으로 버리지 않고 추가 B인계를 보류해 조사한다. 아직 인수하지 않았다면 A 신규 인계권한을 차단하고 현재 유효 B/포장만 허용한다.

### 5) 완료 조건

오배송 조사·실제 후속수행·MFC 반납/원장·OMS 고객판단·라이더 소명·비용·통지의 완료/미결이 각각 설명돼야 한다. 외부 참고의5시간·연락2회·층별500원 등의 문구는 PMart 채택/현재계약 없이 자동 규칙으로 실행하지 않는다.

## BO-21. 수행료·운송비·보상/이의 근거 심사

**입력:** 원Delivery 수행/TMS 운행·정차, 실제 완료/대기·추가 작업 증빙, 요율/계약 버전·포함 항목, 귀책·소명·원청구/기지급·정정 이력을 받는다. 재고 손실액·고객 환불·기사 수행료·회계 지급액을 구별한다.

**처리:** 원실적과 대상 대사 → Delivery/TMS 계산 근거 확인 → 포함 항목 중복·수량/시간 단위 검토 → 승인된 추가비용/공제 심사 → 비용 근거/승인 결과를 지급 담당에 전달 → 수신/심사/실지급/이의 상태 추적 순이다. 지급 담당·회계 시스템의 실제 계약은 확인 필요다.

**가정:** 기본 운행에 첫 정차가 포함된 계약에서 총2정차이면 추가정차는1회다. 대기40분이어도 유료대기 조건/공제·최소단위가 없으면 40분 요금을 임의 확정하지 않는다. 요율 미등록은 0원이나 무료가 아니라 산정 불가다.

**부분·정정:** 고객 환불 성공으로 기사 공제를 자동 실행하지 않는다. 지급 후 근거 변경은 원지급을 덮지 않고 정정/이의 의무로 연결한다. 근거 전송 불명은 원청구 조회이며 새 청구를 반복하지 않는다. 쿠폰 보상·임의 계좌 지급 등 제외/미정 방식은 실행하지 않는다.

**완료:** 근거·승인·청구 전달·실지급 결과 또는 미지급 담당이 대사돼야 해당 단계 완료다. 실제 지급 계약이 없으면 “근거 심사/지급 확인 대기”까지만 표시한다.

### 1) 금액의 근거를 행별로 나눈다

원수행/운행·정차·실행일,비용항목·계산단위·요율/계약버전·포함/공제조건,기본료·추가작업 증빙,요청/심사·승인액·원청구/기지급·이의/정정액·담당을 받는다. 기사 신고액·TMS/Delivery 산정액·본사 심사액·실지급액이 다르면 차이와 사유를 남긴다.

### 2) 근거별 심사

| 항목 | 확인 | 미충족 처리 |
|---|---|---|
| 기본 운행/수행료 | 유효 계약·실제 수행·기청구 | 산정불가/중복 조사 |
| 추가정차 | 기본료 포함 범위·실제 정차·허용 증빙 | 포함항목 이중 청구 차단 |
| 대기/추가작업 | 시작/종료·원인·계약 공제·단위·승인 | 시간만으로 임의 요금 확정 금지 |
| 귀책/공제 | 실제 사실·소명·정책·원수행 | 후기/환불만으로 자동 공제 금지 |
| 지급 뒤 정정 | 원청구·실지급·정정 근거/승인 | 원기록 보존·새 정정/이의 의무 |

### 3) 처리 단계

원실적 조회→원계약/요율 적용근거 검사→중복/포함·누락/단위 대사→증빙 보완/이의·담당 심사→승인된 비용근거 확정→지급 담당 전송/원청구 조회→실지급 확인/미지급 의무 분리 순이다. 근거 생성·승인·회계 처리·실지급을 하나의 승인 버튼으로 완료하지 않는다.

### 4) 사례와 부분실패 [가정]

첫정차 포함/총2정차면 추가정차는1회다. 대기40분이라도 계약의 유료대기 조건·기본 포함·공제·최소단위가 없으면40분 전체에 임의 단가를 곱하지 않는다. 근거80건 중70건 전달/10건불명이면 원청구10건만 조회하며70건을 새청구로 보내지 않는다.

### 5) 정산 이의와 업무 종결

당사자에게 공개할 계산 근거·이의 접수/검토·결론/정정과 실지급 상태를 구분한다. 이의 신청이 기지급 사실을 지우지 않으며 고객 환불·재고 손실을 수행료와 무승인 상계하지 않는다. 실제 지급 연계가 미구현이면 근거/심사와 미확인 지급 담당까지만 기록한다.

<a id="bo-22"></a>

## BO-22. 통합 사건 분류·담당 배정·공동 해결

**입력:** 신고 원천·원객체·발생/발견시각·영향 범위·증빙·안전/고객/실물/금전 상태를 받는다. 중복 신고와 새 피해를 구분한다.

**처리:** 기존 사건/원계보 검색 → 주유형과 총괄 담당 지정 → 도메인별 하위 의무 생성/연결 → 조치/승인/증빙 보완 요청 → 원시스템 결과 수집 → 종결 검토 순이다. 하위 작업을 새로 만드는 것이 필요한지 기존 작업 참조인지 구분한다.

**가정:** 간선 냉장 이탈로 MFC가 10개 중2개를 격리하면 TMS 노출 증빙, MFC 품질/현물, WMS Transit 대사, SCM 대체 공급, 영향 OMS 고객 약속의 의무를 연결한다. TMS 사고를 닫았다고 격리2와 고객 부족을 해결 완료로 바꾸지 않는다.

**담당 경합:** 여러 운영자가 같은 사건을 처리할 때 현재 담당/버전·진행 조치를 표시한다. 동일 행에 모순된 승인/실행을 동시에 발행하지 않는다. 사건 잠금 만료가 실제 진행 작업 중지의 증거는 아니다. 이관은 수신자의 담당 인수와 다음 조치가 있어야 완료다.

**종결·재개:** 원인 미확정이어도 가능한 안전/고객 조치를 진행할 수 있다. 최종 종결에는 대상별 의무 해결 또는 명시적인 후속 사건/담당 인수가 필요하다. 늦은 실제 수령·결제·피해가 나오면 근거를 추가하고 영향 범위를 재개한다.

### 1) 사건 접수서의 필드

신고유형·신고자/원채널·발생/발견시각,원주문/배송/포장·TRF/출발/수령·품질/조정 참조,영향 SKU/LOT·수량/단위·금액,현재 실물/위치/보관 책임,안전/고객약속 위험,증빙·원천 확인상태,총괄/하위 담당과 다음조치를 받는다. 데이터 미상은 추정 값으로 채우지 않는다.

### 2) 접수·중복·담당 확정

1. 원ID·발생 사실·피해 범위로 기존 사건과 중복 여부를 비교한다.
2. 같은 신고는 원사건에 추가 증빙/연락으로 연결하고,실제 다른 피해는 새 하위 의무/사건으로 보존한다.
3. 총괄 담당이 원인 확정 전 안전·보관·고객 안내의 우선 조치를 정한다.
4. 도메인별 기존 사고/클레임·작업을 찾아 참조하거나 필요한 신규 의무를 발행한다.
5. 담당 수락·기한 근거·다음 행동·현재 불명과 증빙 요청을 기록한다.
6. 각 결과를 받아 상호 충돌·미해결을 검토하고 종결/이관/관찰을 결정한다.

### 3) 하위 의무의 최소 단위

| 의무 | 직접 완료 근거 |
|---|---|
| 상품 안전/보관 | 원센터/운송의 현재 위치·보관 책임·제한 결과 |
| 고객 대응 | 유효 안내·선택/동의·OMS 처리 결과 |
| 수량/원장 | 원실행/수령/전기·정정·잔량 대사 |
| 금전 | 원환불/청구·실거래/지급·진행 점유 |
| 조사/승인 | 근거·권한자 결정·미승인 범위 |
| 전달/인수 | 수신자별 원결과 확인·담당 인수 |

### 4) 사건 병합/분리와 종결

병합은 조회/조율의 상위 관계를 바꾸는 것이며 원주문·원실행·환불/손실을 합산 전기하는 작업이 아니다. 분리할 때 기존 승인·실제 처리·담당·실물/금액이 어느 의무에 남는지 고정한다. 하위 의무가 열린 채로 종료한다면 명시적 후속 사건과 수신자의 인수 근거를 표시한다. `상대 처리 중`을 `해결 완료`로 바꾸지 않는다.

### 5) 예시

가정: 냉장 사고1건이 공급 미수령2·MFC격리2·고객 품절 환불·기사비 이의를 만든다. 이 네 의무의 대상량/금액·원장·담당은 독립적이다. 차량 수리 완료나 고객 통화 완료가 네 의무의 종결 근거가 되지 않는다.

<a id="bo-23"></a>

## BO-23. 원결과 불명·미전달·대사 불일치 복구

**입력:** 원요청/실행·멱등키·대상/버전·승인, 실제 수행 증빙, 기확정 ID·원장/거래 결과, 수신자별 전달 상태를 받는다. “재처리” 버튼 하나로 모든 종류를 묶지 않는다.

**판정 순서:** (1) 아직 요청 전인지, (2) 접수/진행 중인지, (3) 실제 수행/전기 성공인지, (4) 미반영이 확인됐는지, (5) 불명인지 나눈다. 원시스템 조회 → 성공이면 같은 결과 반환/후속만 복구 → 미반영 확인이면 원명령의 허용 재시도 → 불명이면 담당 상신·추가 실행 제한 순이다.

**유형별 조치:** PG 성공/OMS 표시 실패는 표시·통지 복구, MFC TIN 성공/CDC 통지 실패는 원수령 결과 재전달/대사, 실제 MOV40/전기 불명은 실물 재사용 제한·원전기 조회, 승인 저장 성공/메일 실패는 메일만 복구한다. 각각 새 결제·새 TIN·새 MOV·새 승인을 만들지 않는다.

**순서·멱등:** 같은 키/다른 본문은 충돌이다. 새 메시지 ID여도 같은 실제 사건이면 추가 효과가 없어야 한다. 반대로 동일 내용의 실제 다른 부분수령은 원실행·허용 잔량으로 구분한다. 오래된 버전은 최신 결과를 되돌리지 않는다. 보존기간 이후 사건도 조회 불가를 미실행으로 해석하지 않는다.

**완료:** 복구한 단계·원결과·추가 효과·미결 제한/담당이 설명돼야 한다. 상대 서비스가 원조회/멱등 계약을 제공하지 않으면 강행 재실행하지 않고 공동 계약 미지원으로 남긴다.

### 1) 재처리 버튼을 나눌 기준

| 버튼/명령의 의미 | 선행 확인 | 추가 업무 효과 |
|---|---|---|
| 원결과 재조회 | 원요청/원실행·현재 권한 | 없음,확정 사실 확인 |
| 미전달 재전송 | 원승인/원결과 성공·대상 수신자 미확인 | 원업무 재실행 없음 |
| 조회 사본 재구축 | 재구축 기준·확정 원사건·읽기 경로 | 원장/물리 명령 재생 없음 |
| 미반영 명령 재시도 | 원결과 미반영 확인·원키/잔량·권한/승인 유효 | 해당 명령의 허용 효과만 |
| 업무 정정/누락 복구 | 실제 사실·기전기·정정 승인·현재 제약 | 원사건과 연결한 승인 범위 |

### 2) 장애를 진단하는 순서

1. 화면 표시와 원정본 결과를 분리하고 요청이 실제로 발행됐는지 확인한다.
2. 원요청/실행·멱등키·본문/예상버전·승인과 실제 증빙을 수집한다.
3. 상대가 접수했는지,실행중인지,확정/거절인지,결과불명인지 조회한다.
4. 확정 성공이면 같은 결과를 반환하고 미표시/미전달만 복구한다.
5. 미반영이 확인된 범위는 원계약의 재시도·현재 권한/제한·원잔량을 검사한다.
6. 불명이면 원결과 확인과 영향 대상 추가실행 제한을 유지한다. 재시도 횟수 소진을 실패 확정으로 해석하지 않는다.
7. 복구한 단계·기반영/추가량·다음 확인 담당과 증빙을 남긴다.

### 3) 원문에 이미 있는 결제 확인 절차

Commerce §8.4의 PG 결과불명 기본 절차는 **1분 간격5회 조회→담당자 상신→15분 간격 후속 조회**다. 이는 실제 승인/취소 사실 확인을 위한 현재 문서 기준이며5회 실패를 PG실패로 확정하는 규칙이 아니다. 이 절차를 임의 새 SLA로 바꾸거나 조회 중 재고/슬롯/첫구매 자격을 자동 해제하지 않는다. 다른 도메인의 재조회 주기까지 이 수치를 복제하지 않는다.

### 4) 반대되는 두 중복 사례

같은 실제 MOV4를 event A/B로 두 번 보고하면 원실행 증거로 추가효과0이다. 실제 다른 부분수령4와4는 내용이 같아도 원수령/실행이 다르고 유효잔량이8이면 각각 처리 가능하다. eventId 동일성·내용 동일성만으로 실제 사건 동일성을 대신하지 않는다.

### 5) 복구를 중지하고 심사할 조건

원결과 조회 불가,상이 본문 동일키,예상버전 충돌,원승인/권한 만료,실제 수행/전기 불일치,원잔량 초과,새 안전제한,지원되지 않는 정정은 자동재시도를 중지하고 원인/담당을 상신한다. 새ID 발급·DB 직접 수정·가짜성공으로 통과시키지 않는다.

<a id="bo-24"></a>

## BO-24. 고객·현장·운송 담당 알림과 동의 기록

**입력:** 원사건·고객/수신 담당·채널/수신 설정·메시지 종류·확정 상태·버전, 안내/동의 필요 내용·기한을 받는다. 연락처는 허용된 원주문/계정 정보만 사용한다.

**처리:** 업무 결과/변경 내용 확인 → 권한·수신/민감 정보·템플릿 검증 → 같은 원사건의 알림 생성/전송 → 전달/실패/읽음 상태 기록 → 필요한 고객 선택/동의는 대상·수량·금액·시각과 별도 접수 → OMS 등 주관자에 결과 연결 순이다.

**표현:** 불명은 “확인 중”, 승인됐으나 미집행이면 “승인/처리 대기”로 구분한다. 실제 PG 성공 전에 환불 완료를 안내하지 않는다. 새 ETA와 원약속을 구분하고 간선 ETA를 고객 배송 도착시간으로 안내하지 않는다.

**예외·완료:** 알림 실패는 업무를 재실행하지 않고 통지만 복구한다. 읽음/전화 연결은 동의나 환불/배차 성공이 아니다. 무응답을 자동 동의로 간주하는 새 정책을 만들지 않는다. 업무 상태·안내·응답/동의·미전달 담당이 연결되면 해당 알림 의무가 정리된다.

### 1) 안내와 고객 선택의 데이터

원사건/버전·수신 대상·채널·수신설정·템플릿/문안 버전,안내 종류·품목/수량/금액·약속시각,허용 연락처·민감정보 범위,전송/실패/읽음,고객이 선택한 내용·동의 대상/시각·원응답을 구분한다. 메시지 전송 성공은 고객 동의의 증거가 아니다.

### 2) 발송·수정·재전달 절차

1. 원시스템에서 확정된 업무 결과/현재 불명 상태를 확인한다.
2. 고객에게 제공할 사실·필요 선택·다음 조치와 허용 문구를 정한다.
3. 수신자/주소·수신설정/업무성 안내 정책·개인정보 범위를 검사한다.
4. 원사건·채널별 전송 의도를 기록하고 같은 안내의 중복 발송을 관리한다.
5. 전달 실패면 통지만 재시도하고 업무 명령은 반복하지 않는다.
6. 결과가 정정되면 과거 안내/정정 문구를 연결해 새 안내를 발행한다.
7. 고객 선택은 원주문/클레임 버전·대상·금액에 연결해 OMS 등에서 현재 적격을 검증한다.

### 3) 안내 표현의 판정표

| 확인 결과 | 안내할 것 | 안내하면 안 되는 것 |
|---|---|---|
| 취소 접수/현장 확인중 | 취소 가능/인계 확인 중 | 취소/환불 완료 |
| PG 성공 확인 | 확인된 성공액·원거래 상태 | 미확인 은행 입금시각 확약 |
| 간선 ETA 지연 | 공급/담당 현장의 영향 정보 | 고객배송 ETA로 동일시 |
| 일부 배송 전달 | 전달분·남은 배송/대상 | 주문 전체 전달완료 |
| 회수1/승인2 | 실수거/미수거·센터인수 상태 | 전량 회수/검수 완료 |

### 4) 고객 무응답과 종료

무응답을 동의·자동 대체·회수 포기·환불 철회로 처리하려면 명시적 정책이 필요하다. 미등록이면 원의무/담당을 유지한다. 통화 연결·읽음·전송 성공은 연락 활동의 완료일 뿐 원주문/금전/실물 업무의 완료가 아니다.

## BO-25. 개인정보 열람·내보내기·감사 증빙

**입력:** 업무 목적·담당 사건/주문·필요 필드·조회/파일 범위, 현재 권한·보존/마스킹 정책을 받는다. 운영자 계정, 고객, 라이더, 간선 기사 개인정보를 별도 주체로 구분한다.

**처리:** 목록 기본 마스킹 → 실제 담당 범위 검사 → 원문 열람/다운로드의 추가 권한·사유 확인 → 필요한 필드만 제공 → 행위자·대상·범위·시각·결과 기록 순이다. 로그인 권한만으로 전체 주소·위치·주민정보·계좌·증빙을 일괄 제공하지 않는다.

**내보내기:** 필터·기준시각·원천 신선도·열/행 범위·수신 목적을 고정한다. 다운로드 생성 뒤 권한이 회수되면 접근 시 현재 권한을 다시 검사한다. 화면 조회 권한과 대량 파일 권한은 분리한다. 개인 데이터가 일반 로그/오류 메시지에 무제한 남지 않게 한다.

**보존·예외:** 구체 보존기간·익명화·파기·감사 자료 잠금은 정책 승인 대상이다. 미정 값을 영구 보존이나 즉시 파기로 해석하지 않는다. 탈퇴·계정 회수만으로 미결 결제/분쟁 증빙을 지우지 않으며 필요한 업무 권한으로 참조한다.

**완료:** 제공 목적·최소 범위·접근 기록·보존/제한과 미정 항목이 설명된다. 기술 감사자도 자기 접근 기록을 삭제하거나 증빙을 소급 변경하지 않는다.

### 1) 개인정보를 목적별로 제한

| 목적 | 기본 노출 | 추가 확인 |
|---|---|---|
| 운영 현황/수요·공급 | 고객 식별 최소화·집계/마스킹 | 주소 원문 불필요 |
| 담당 주문 상담 | 주문 필요한 고객/연락 정보 | 실제 담당/문의 자격·열람 사유 |
| 배송 도움/오배송 | 원주소·허용 연락·필요 증빙 | 현재 사건·수행·목적 범위 |
| 라이더 자격/비용 | 승인된 심사 필드 | 계약/자격·계좌 원문은 별도권한 |
| 감사/복구 | 원ID·행위/결과·마스킹 증빙 | 광범위 원문 자동 제공 금지 |

### 2) 열람·다운로드의 처리

목적/원사건 선택→현권한·담당/센터·필드 범위 검사→필요 원문만 열람→행위/대상/결과 감사 기록→내보내기라면 별도 승인·필터/열/기준시각 고정→생성 뒤 다운로드 시 현재권한 재검사→보존/접근 제한 적용 순이다. 파일 링크를 안다는 이유만으로 다른 담당이 내려받지 못해야 한다.

### 3) 조회/감사 장애

민감정보 접근의 감사 기록이나 현재 권한을 확인할 수 없으면 해당 원문 열람·반출을 보류하고 승인된 대체 절차로 상신한다. 기술 복구 계정에 업무 전체 정보/금전 실행권한을 자동 부여하지 않는다. 일반현황 조회와 민감정보 원문을 한 장애 영향으로 묶어 무조건 전체 허용/차단하지 않는다.

### 4) 보존·파기·법적 확인의 현재 지위

목적별 보존기간·분쟁 보존·파기/익명화·접근 로그 보호·내보낸 파일 회수/기한은 담당 정책/계약 승인 항목이다. 현재 문서는 특정 법정기간·인증수단을 확정하지 않는다. 미결 환불/분쟁의 근거를 탈퇴만으로 지우지 않고,미정이라고 영구 보존도 자동 선택하지 않는다.

### 5) 완료 근거

열람/제공 대상·목적/권한·원문 범위·수신/다운로드 결과·감사·접근/보존 상태가 연결돼야 한다. 사용자 화면에서 이력을 수정해 원감사 행위자·시각·결과를 바꾸는 기능은 두지 않는다. 잘못된 기록의 정정은 원기록과 정정 근거를 함께 남긴다.

## BO-26. 대량 변경·파일 입력·일괄 승인

**입력:** 승인된 작업 종류, 행별 원객체/예상 버전·전후값·단위·효력·사유, 업로더·파일 해시·기존 배치 ID를 받는다. CSV/XLSX 업로드 자체는 변경 적용이 아니다.

**처리:** 형식/중복·권한·존재/단위 검사 → 행별 영향·전후 비교와 오류/미정 표시 → 검토된 행 집합 승인 → 행별 현재 버전 재검사 → 각 정본 명령 → 행별 성공/실패/불명·미전달 결과 반환 순이다. 업로드 후 파일이 바뀌면 기존 승인으로 실행하지 않는다.

**부분 사례:** 가격 100행 중80행 적용/10행 거절/10행 불명이면 80행을 다시 보내지 않는다. 거절10행은 보완·새 버전 승인, 불명10행은 원결과 조회다. 전체 파일 “실패”로 초기화하거나 이미 적용된 가격을 무조건 역변경하지 않는다.

**제한·완료:** 재고 잔고·PG 성공·배송 완료를 파일로 덮는 경로는 제공하지 않는다. 승인/일괄 실행의 최대 범위·검토 인원은 승인 입력이며 임의 1,000행 같은 값을 운영 정책으로 두지 않는다. 행별 원승인·실제 결과·잔량/미결이 추적될 때 배치가 정리된다.

### 1) 업로드 행과 승인 대상 고정

배치 ID/파일 해시·양식버전,행 번호·원객체/예상버전,변경전/후·SKU/센터·수량/금액/단위·효력,사유·원승인/요청자·검증결과를 관리한다. 표시상 행번호와 원업무 행ID는 다르며 정렬/재업로드로 연결을 잃지 않는다.

### 2) 미리보기와 적용

1. 파일 형식/필수열·중복키·인코딩/단위·권한을 검사하고 원파일을 참조로 고정한다.
2. 원정본 현재값과 비교해 추가/수정/변경없음·오류/불명을 행별 분류한다.
3. 작업자는 오류를 보완하고 실제 적용할 행 집합을 선택한다.
4. 승인자는 그 파일 해시·행 집합·전후값/효력·부분실패 처리 방식을 심사한다.
5. 실행 직전에 원객체/정책·권한/승인·버전을 다시 검사한다.
6. 각 도메인 원명령/멱등키로 실행하고 행별 결과를 기록한다.
7. 성공/거절/불명·미전달의 대상별 보고와 복구를 진행한다.

### 3) 변경/실패 분기

| 상황 | 처리 |
|---|---|
| 승인 뒤 파일/행집합 수정 | 원승인 적용 불가·새 검토 |
| 실행 전 원객체 버전 변경 | 해당행 충돌·재심사,구화면 값 덮기 금지 |
| 같은 배치 재업로드/응답유실 | 원배치/행 결과 조회 |
| 100행 중80성공/10거절/10불명 | 성공80유지·거절10보완·불명10조회 |
| 전체철회 요청/일부기적용 | 미실행 행 중지,기적용은 별도유효 정정심사 |

### 4) 실물/금전 대량 덮어쓰기의 배제

상품/가격/정책 변경의 승인된 일괄 처리와 재고/PG/배송완료 CSV 덮어쓰기는 다르다. 원업무에 지원하는 명령이 없는 동작을 파일 업로드로 우회하지 않는다. 최대행수·배치동시수·검토자 수는 승인 입력이며 문서 예시100행을 운영 기본한도로 고정하지 않는다.

### 5) 완료

처리 대상 전체행이 성공/거절/보완/불명/미실행으로 빠짐없이 설명되고,원명령/확정 결과·정정·미결담당·승인 범위가 대사돼야 한다. 전체 배치의 요약상태만 성공으로 바꾸지 않는다.

<a id="bo-27"></a>

## BO-27. 교대·일일 마감·사건 종결과 재개

**입력:** 대상 센터/업무·기준시각/버전, 진행 사건, 미확정 실물·결제·출발·수령, 보관 책임·수신자별 미전달·다음 조치·담당을 받는다.

**교대:** 전임의 이미 확정한 실적·열린 잔량·구단말 실행 가능 여부 확인 → 신규 중복 실행 차단 → 후임 권한/근무 확인 → 실물/원장·원승인·제한과 증빙 인수 → 후임 수락·다음 조치 기록 순이다. 전임의 늦은 실물 보고는 버리지 않고 원사건으로 조사한다.

**마감:** 발생시각과 전기시각을 모두 보존한다. 어제 발생/오늘 전기 사건은 승인된 귀속 기준에 따라 원마감/정정 버전을 연결하며 어제 기록을 조용히 덮지 않는다. 센터 총량만 맞아도 중복4/누락4가 상쇄될 수 있으므로 행·원실행별 대사가 필요하다.

**종결·예외:** 차량 종료·영업 종료·상담 종료는 품질/미수령/환불 의무 종료가 아니다. 미결의 보관 위치·담당·확인 기한·원결과 조회가 남아야 한다. 실제 사실이 종결 근거를 뒤집으면 새 정정/재개 이력으로 연결한다.

**완료:** 전임/후임·실물·권리·미결·다음 조치가 인수됐을 때 교대 완료다. 일일 마감은 당시 기준선이 고정됐다는 뜻이며 모든 거래가 해결됐다는 뜻이 아니다.

### 1) 교대 인계서

대상 센터/업무·사건/작업/원요청,현재 실물 수량·단위·위치/보관 책임,완료/미실행 잔량·승인/원예약/제한,구단말/전임의 추가실행 가능 여부,불명 원거래/미전달·다음 확인,고객 약속/연락 결과,후임·인수시각을 남긴다. 단순 담당자 이름 교체로 끝내지 않는다.

### 2) 교대의 상세 순서

1. 전임의 현재 실적/원전기와 구시도의 추가 실행 가능성을 조회한다.
2. 가능한 중복실행을 차단하고,이미 끝난 실물/권리와 열린 잔량을 분리한다.
3. 후임의 현권한·근무/센터 범위·증빙 접근을 확인한다.
4. 실물/보관·원승인/잔량·불명/제한·고객/금전 의무를 인수한다.
5. 후임이 대상별 다음 조치/기한근거를 수락하면 교대 완료로 기록한다.
6. 이후 전임의 늦은 보고는 원실행에 연결해 조사하고 후임 잔량을 재평가한다.

### 3) 마감과 운영 종결의 구분

| 업무 | 고정하는 것 | 남길 수 있는 것 |
|---|---|---|
| 일일 마감 | 대상/기간·포함사건·기준시각·원장/집계버전 | 장기 미수령·PG불명·품질·미지급 |
| 교대 | 인수한 의무·실물/권리·담당/다음조치 | 해결되지 않은 원사건 |
| 사건 종결 | 해결/정정 또는 명시적인 후속 인수근거 | 후속이 열려 있으면 이관 상태를 표시 |
| 재개/마감 정정 | 늦은 사실·원기준과 정정계보 | 과거 마감/기발생 사실 |

### 4) 늦은 전기의 수용 사례 [가정]

어제23:50 실제 출발/오늘00:10 전기이면 발생일과 전기일·마감 귀속 정책을 모두 보존한다. 과거 일자를 조용히 고치거나 오늘 전기를 새 물리출발로 만들지 않는다. 원마감에 포함되지 않았던 사건이면 승인된 정정 버전으로 연결한다.

### 5) 감사·종결

총계만 맞아도 중복4/누락4가 상쇄될 수 있으므로 원행/실행별 확인을 남긴다. 전임/후임 모두 부재이면 미인수 상신 상태로 두며 담당 없는 의무를 종결하지 않는다. 알림읽음·영업종료·차량수리 완료는 인수/원거래 해결의 증거가 아니다.

## BO-28. 통합 현황·업무 지표·조회 재구축

**입력:** 원천별 주문/공급/센터/운송/사건 결과, 기준시각·원ID·정정/중복 관계·지표 정의 버전을 받는다. BackOffice는 운영 판단에 필요한 현황을 보여 주며 BI 분석 모델을 대신 확정하지 않는다.

**표시:** 신규 접수 가능성, 주문별 미이행/인계/환불, 센터 제한·적격/예약부족, 공급 미확보·미출발·미수령/준비대기, 간선/고객 배송 지연, 승인 대기·장기 불명·미인수 의무를 구분한다. 총 현물·적격·신규 가용·예정 공급을 같은 “재고” 한 칸으로 합치지 않는다.

**지표:** 승인60/출발48의 출발률은80%이며 미출발잔량12의 행정 종료로 분모를48로 바꿔100%로 만들지 않는다. 수령46/정상44/준비량은 별도다. 분모0은 정의에 따라 N/A 등으로 표시하며 무조건100%로 처리하지 않는다. 목표/SLA·반올림·제외 기준은 승인된 정의를 사용한다.

**재구축:** 조회 사본/집계 손상은 확정 원사건으로 읽기용 결과를 재구축한다. INITIAL_BALANCE·MOV·TOUT·TIN·PG 취소·배송 명령을 다시 실행하지 않는다. 오래된 백업 이후 실제 출발/수령 누락은 상대 원결과·실행 증빙으로 확인하고 승인 복구한다.

**완료:** 지표가 원천 행까지 추적되고 신선도·미정의·불명을 구분하며 재구축의 운영 추가 효과가 없어야 한다. 이 문서의 계산 사례와 수용 사례는 실제 시스템 시험 결과로 표시하지 않는다.

### 1) 관제 현황의 지표 사전

| 지표 | 분자/분모 또는 기준 | 해석 주의 |
|---|---|---|
| 승인 대기 | 현재 유효한 미결 심사행·종류/담당 | 중복알림을 여러 승인으로 세지 않음 |
| 불명 실행 | 원요청별 원결과 미확인 대상/금액/수량 | 타임아웃 횟수와 실제 사고 수는 다름 |
| 공급 출발률 | 유효 원승인 기준량 대비 실제출발 | 잔량행정종료로 분모 축소 금지 |
| 수령/정상/준비율 | 각 실제량을 당시 승인/약속 기준과 비교 | 정상품질=판매준비 아님 |
| 미해결 의무 | 열린 하위 의무·대상/단위·담당/경과 | 이관/종결/해결을 구분 |
| 고객 이행 | 주문행/배송별 전달·미전달·취소·환불 | 부분완료를 전체완료로 합성하지 않음 |

### 2) 조회·합산의 검증

지표 정의/대상·기간→원천 버전/기준시각·단위→원사건 중복/정정→분자/분모/제외→표시 반올림→원행 드릴다운 순으로 확인한다. 분모0·미등록 기준·미수신은 N/A/미정/불명으로 구분한다. 소수표시·제외 규칙이 승인되지 않으면 임의 성과율을 확정하지 않는다.

### 3) 원수령과 Transit의 시차 사례 [가정]

MFC TIN10은 확정됐고 CDC Transit10이 아직 대사전이면 같은 수령을 두번 합산할 위험이 있다. 원receipt/출발행·기전기/대사 상태를 연결해 물량 중복을 판정한다. 연결 불가이면 전사 총계 확정 대신 기준시각·불명 범위를 표시한다. MFC 현물이나 CDC Transit을 관제 화면에서 임의10 감소시키지 않는다.

### 4) 조회 장애와 재구축

조회 사본 손상→영향 화면/기준선 표시→확정 원사건·정정버전 확보→읽기용 재구축→원행/총계·중복/누락 검사→현업 확인 후 조회 재개로 진행한다. 원TOUT/TIN/MOV·PG취소를 읽기 재생과 함께 다시 호출하지 않는다. 백업 이후 실제사건은 상대 원결과/증빙·승인 복구로 확인한다.

### 5) 실제/모의·지표/원장 구분

모의 정책·샘플 주문/수량·수용사례 기대결과를 운영 실적과 섞지 않는다. BI가 재정의한 지표는 버전/정정으로 제시하되 기존 원거래를 수정하지 않는다. 운영자 조치는 지표에서 원사건으로 이동해 해당 도메인의 현재 권한/승인·조건을 다시 확인한 뒤 요청한다.

### 6.2 요청·응답의 최소 내용

**요청:** 인증 행위자·대행/권한 범위, `requestId/idempotencyKey`, 업무 종류·원객체/행·예상 버전, 승인 참조·효력/조건, 대상 센터/SKU/LOT/포장·수량/금액·단위, 사유·원증빙·상관관계, 발행 시각과 필요한 유효기간.

**응답:** 원요청 참조, 접수/검증/업무 반영의 구분, 반영된 원결과/commit/PG 거래·버전, 확정량/미실행량·단위 또는 금액, 거절/보류/불명 사유, 현재 제한, 조회 참조·다음 담당/조치. 단순 HTTP 성공·메시지 ACK를 업무 성공으로 매핑하지 않는다.

**업무 오류 종류 제안:** `FORBIDDEN`, `CONFIG_REQUIRED`, `STALE_VERSION`, `APPROVAL_REQUIRED`, `EVIDENCE_REQUIRED`, `IDEMPOTENCY_CONFLICT`, `DOMAIN_REJECTED`, `UNKNOWN_RESULT`, `PARTIAL_APPLIED`, `UNSUPPORTED_ACTION`. 실제 코드·응답 형식은 공동 계약에서 확정한다. 원시스템 오류를 모두 “다시 시도”로 바꾸지 않는다.

### 6.3 승인 이후 데이터 변경

구성·목적센터·수량·단위·가격·정책·권한/대행·품질 제한이 바뀌면 승인/실행 유효성을 다시 평가한다. 과거 증빙과 이미 완료한 실제 사실은 보존한다. 예전 승인 ID가 존재한다는 이유만으로 현재 무효 포장·새 화물·새 금액을 실행하지 않는다.

권한이 취소됐거나 승인 만료 뒤 실제 수행 사실이 확인되면 일반 정상 실행 허가와 기발생 사실 보존을 분리한다. 담당 사고/정정 경로로 처리하고 허가 시각을 소급 작성하지 않는다.

## 8. 수량·금액·상태를 잘못 합치지 않는 기준

### 8.1 주문·배송·환불

동일 주문행/단위에서 `원주문량 = 유효 인계 누계 + 출고 전 확정 취소 누계 + 미인계 잔량`을 OMS 기준으로 참조한다. 반품은 과거 인계를 지우지 않는 후속 사건이다. 배송별 전달·수거·센터 인수·검수·환불의 진행/확정 수량은 각각 표시한다. 실제 다른 부분실행은 반영하되 같은 피해/실행을 두 번 소비하지 않는다.

PG 승인·취소의 성공과 처리 중/불명 점유를 분리한다. 환불액과 고객 회수비·라이더 수행료·간선비·재고 손실 평가액을 하나의 보상 금액으로 상계하지 않는다. 승인된 별도 계약 없이 차액 송금이나 과거 청구 변경을 만들지 않는다.

### 8.2 센터 공급

동일 승인 버전/SKU/단위에서 SCM 기준:

```text
원승인량 = 실제출발 + 유효 승인취소 + 미출발잔량종료 + 열린 미출발
출발량 q = MFC 확정수령 누계 r + 승인 운송손실 l + 대사후 미정산 t
수령량 r = 정상 수령 + 격리/미판정 수령
```

승인60·출발48·잔량종료12를 출발60으로 표시하지 않는다. 출발12·수령10(정상8/격리2)·손실0이면 대사후 미정산2다. 격리2는 이미 받은 실물이고 미수령2와 다르다. 정상8이 자동 판매준비8은 아니다. TIN 성공/CDC 확인 지연의 잠정 Transit은 대사후 수량과 구분한다.

### 8.3 재고 변수

WMS의 H(총 현물)·E(적격)·Rg(적격에 연결된 이관예약)·Bq(차단된 기존 약속 의무)·S(안전보호), MFC의 H_book·E·R_active·R_blocked·S_protect, SCM의 H(사용준비 적격현물)·C(고객약속)는 의미가 다르다. 통합 화면의 열 이름·설명·원천을 유지한다. Rg>E 같은 부정합을 신규가용0으로 숨기지 않는다.

현물 보유·품질·현재 위치·예약·실행점유·원장 반영·사용준비·통지를 구분한다. 예약품 내부 MOV는 원권리를 계승하며 같은 물량을 예약+외부 수요로 중복 차감하지 않는다. BackOffice는 원천 계산 결과와 입력 정의를 비교하고 이 공식을 독자 재고 원장으로 집행하지 않는다.

## 9. 전체 연결 사례 — 하나의 공급 사고와 고객 주문 영향 [가정]

1. SCM 요청100/승인60·CDC 확보48, TMS 한 운행에 해당 TRF 화물48을 준비한다. BackOffice는 미승인40·승인 미확보12를 분리해 본다.
2. 실제 출발48의 유효 사실에 WMS가 CDC 현물−48·연결 예약−48·Transit+48을 확정한다. 상차만으로 먼저 차감하지 않는다. 남은12는 실물/권리 정리와 SCM 잔량종료 대상으로 남긴다.
3. TMS에서 일부 구획의 온도 이탈을 신고한다. 통합 사건 C1을 만들고 TMS 증빙, MFC 품질, WMS 수령 대사, SCM 공급 영향의 하위 의무를 연결한다. 실제 안전 조치를 먼저 기록한다.
4. MFC는46을 실제 받아 정상44/격리2로 자체 TIN+46을 확정한다. CDC 통지가 지연돼도 다시 입고하지 않는다. WMS가 같은 원수령 결과를 확인하면 Transit은48→2다.
5. 수령 차이2는 미정산 조사다. 격리2를 폐기한 것으로 보거나 미수령2와 합쳐 손실4를 만들지 않는다. 수령/손실 공동 계약 없이 자동 손실 종결하지 않는다.
6. 격리된 실물에 기존 고객 예약이 연결돼 있으면 MFC가 이행부족과 현재 대체 결과를 OMS에 회신한다. OMS는 고객 약속과 사전 품절 선택·환불 가능성을 판단한다. BackOffice CS는 승인된 후속 요청과 안내를 연결한다.
7. 가정상 고객 환불 의도5,000원이 승인됐지만 PG 결과가 불명이면 환불 의무는 확인 중이다. 품질 사건/공급 부족과 별개로 원PG 결과를 조회한다. 새 환불5,000원을 중복 발행하지 않는다.
8. SCM은 새 부족을 기존 공급/원수요와 대사한 뒤 필요한 추가공급을 별도 심사한다. 원TRF의 두 번째 출발을 만들지 않는다.
9. TMS 운행이 끝나도 품질2·미수령2·PG불명·SCM잔량의 의무는 남는다. 담당별 해결/명시적 인수 근거를 모아 사건 종결 여부를 판단한다.

이 사례의 수량·금액·사건번호는 설명용이다. 실제 운영 재고·손실·환불이나 실행된 통합시험을 뜻하지 않는다.

## 13. 승인함·사건함·실행함이 함께 관리할 행 단위

### 13.1 하나의 총괄 상태로 줄이지 않는 데이터

| 구분 | 필요한 필드/의미 | 변경 주체 |

| 결정 | 원승인 ID·승인/반려행·허용행위·량/액/단위·효력/조건 | 권한 승인자·원도메인 승인 정본 |

실제 물리 사건/품질/금전의 단위는 원도메인의 행으로 유지한다. 사건 단위의 합계는 설명용이며 다른 SKU·개/팩·원·건을 혼합 합산하지 않는다. `완료 건수`도 무엇이 완료됐는지 승인/실행/전달/사건 정의를 표시한다.

### 13.2 승인량·실행량·잔량의 기록

가정: 승인행 A가5개이고 원실행E1으로2개·E2로1개가 실제 확정됐다면 누적3/열린2다. E2의 같은1개가 새메시지로 다시 도착해도 누적3을 유지한다. 실제 다른 E3으로1개를 집행하려면 현재승인/잔량·실물/품질을 확인한다. 누적3이라는 응답을 신규3으로 더하지 않는다.

승인량을 감액/철회할 때에는 기집행량·진행/불명 집행·미실행 취소·열린 잔량을 분리한다. 기집행3인데 새승인2로 덮어 음수 잔량−1을 만드는 정상 변경은 거절/재심사한다. 실제 잘못 집행한 사건은 숨기지 않고 사고/정정 의무로 보존한다.

### 13.3 행정 완료와 실제 해결

| 표현 | 사용 조건 |
|---|---|
| 심사 완료 | 원유효결정·미승인 범위와 전달의무가 명확함 |
| 실행 완료 | 주관 시스템의 확정 결과·대상/수량/금액과 잔량이 맞음 |
| 전달 완료 | 지정 수신자별 계약상 확인된 결과가 있음 |
| 담당 이관 완료 | 새담당이 열린 의무/보관·다음조치를 수락함 |
| 사건 해결 | 필요한 하위 의무가 해결됐거나 명시적 후속 의무로 연결돼 그 상태가 공개됨 |
| 사건 기록 종료 | 당시 결론/인수·증빙이 고정됨. 늦은 사실의 재개/정정은 가능 |

원고객 환불이 끝나도 미반납 실물이 있으면 실물 의무는 남는다. 원운행이 종료돼도 PG불명·품질이 남을 수 있다. 행정 종료를 실물/금전 성공으로 승격하지 않는다.

## 14. 승인선·다중 검토·반려·재상신의 업무 규칙

### 14.1 승인선 선택

승인선은 업무종류·대상센터/상품군·변경 영향·수량/금액/위험·유효 정책으로 결정한다. 구체 임계값·필수 검토자·대행/긴급 예외는 승인 입력이다. 미등록일 때 일반 관리자에게 자동 위임하거나 과거50%/10만원 등의 기준을 복원하지 않는다.

검토자는 사실/기술/품질/현장 가능성을 회신하고 승인자는 그 근거로 허용 결정을 한다. 검토자 전원이 확인했다는 이유만으로 최종 결재가 생기지 않는다. 품질 검토와 가격 승인은 대체 관계가 아니다.

### 14.2 제출·보완·부분승인의 변화

1. 초안에는 수정이 가능하나 제출할 때 대상행·원버전·전후값/효력·근거를 고정한다.
2. 보완 요구는 어떤 필드/증빙이 왜 부족한지 명시한다. 이미 승인된 다른행까지 지우지 않는다.
3. 요청자가 보완하면 새 심사버전을 만들고 구검토/승인의 재사용 가능성을 판단한다. 대상/조건에 영향이 있으면 재검토한다.
4. 부분승인은 허용행·허용량과 거절/보완행·사유를 나눠 원정본에서 확정한다.
5. 재상신은 원요청 계보를 보존하고 같은 수량/금액의 열린 점유·기승인을 조회한다.
6. 반려는 허용하지 않는 결정이며 실제이미발생한 사실을 부정/삭제하는 행위가 아니다.

### 14.3 재심사가 필요한 변화

대상 SKU/단위·구성/목적센터·수량/금액,현재 권한/대행·승인 정책,안전 제한/기한,원사건의 실제 수행·기전기/잔량이 달라지면 승인 유효성을 다시 판단한다. 단순 메모 오탈자 등 결론에 무관한 정정은 원문안과 정정 이력을 남기되 허용 범위를 확대하지 않는다.

### 14.4 동시 결재와 실행 경합

동일 원승인버전에 두 승인자가 서로 다른 결론을 제출하면 원승인 정본이 현재버전과 유일성을 확인한다. 먼저 확정된 유효 결과를 반환하고 후속자는 최신 결과를 보고 재심사해야 한다. 화면 잠금이나 총괄 사건의 담당 잠금은 상대 원장/PG/실물의 잠금이 아니다.

철회가 접수됐으나 원실행이 진행/불명이라면 먼저 원결과를 확인한다. 철회성공이라는 공통 UI표시만으로 작업/원예약/금액점유를 풀지 않는다. 기발생 사실은 보존하고 미실행범위만 정리한다.

## 15. 정책·기준정보 변경의 영향 평가와 발효

### 15.1 변경 전에 평가할 대상

|---|---|
| 현재 고객 노출 | SKU/기본가격·일반콘텐츠·권역/운영 제한·검색 사본 |

### 15.2 변경 종류에 따른 적용

일반 기본가격은 유효 원초안/확정 주문의 원가격을 보존한다. 일반 영업일/권역 변경은 원주문 약속을 소급 변경하지 않는다. 안전/리콜은 진행 물량에도 최신 영향 제한을 적용하되 과거 정상/실행사실을 삭제하지 않는다. 신원/권한 회수는 새 행위를 막고 기존 의무·감사/인수를 유지한다.

### 15.3 반영 일부 실패와 되돌리기

승인·발행·효력·소비자 반영을 대상별로 나눈다. 일부 시스템이 구버전을 사용하면 신규 실행 적격과 영향 범위를 표시하고 원결과 조회·미전달 복구를 수행한다. 구버전으로 되돌리는 것 역시 새 승인/효력이며 확정한 주문/수불을 역실행하는 롤백이 아니다. 도메인간 같은DB원자성은 가정하지 않는다.

### 16.3 실패를 다르게 안내한다

### 16.4 감사의 업무 의미

누가 어떤 범위의 어떤 승인을 근거로 무엇을 요청했고,실제 어느 원결과가 발생했는지 재현할 수 있어야 한다. 원명령 실패/불명도 기록하며 성공만 남기지 않는다. 개인정보 원문·인증 비밀·불필요한 계좌/주소를 일반 오류로그에 복제하지 않는다. 고위험 변경의 현재권한/승인·감사 의도를 확인할 수 없으면 해당 새 변경을 보류하고 기실행 원결과 조회/안전보관을 유지한다. 구체 감사 저장/장애 대응 계약은 보안·각 도메인과 승인한다.
